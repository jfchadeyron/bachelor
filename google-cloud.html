Google Cloud Platform : initiation complète

Un cours pratique pour débutants — sans carte bancaire, en exploitant émulateurs locaux, Docker et Google Cloud Shell.

🎯 Niveau débutant 🐳 Pré-requis : Docker 💳 Aucune CB requise ⏱️ ~10-15h de pratique
À lire avant de commencer

Ce cours est conçu pour vous permettre d'apprendre Google Cloud sans activer de facturation. Pour cela nous nous appuyons sur trois piliers :

  1. Google Cloud Shell : un terminal gratuit dans le navigateur (5 Go, 50h/semaine) avec gcloud préinstallé — accessible avec un simple compte Google.
  2. Les émulateurs locaux officiels fournis par Google (Firestore, Pub/Sub, Datastore, Spanner, Bigtable…) : ils reproduisent fidèlement le comportement du cloud sur votre machine.
  3. Docker (que vous connaissez !) pour simuler des services comme Cloud Storage (fake-gcs-server), Cloud Run (runtime local), ou déployer kubectl via Minikube.

À la fin, vous saurez lire/écrire toutes les commandes gcloud courantes, comprendre l'architecture GCP, et déployer des projets réels dès que vous activerez le niveau gratuit.

1. Introduction à Google Cloud

1.1 Qu'est-ce que Google Cloud Platform (GCP) ?

Google Cloud Platform est la plateforme cloud publique de Google, équivalent d'AWS (Amazon) ou Azure (Microsoft). Elle expose sous forme de services managés l'infrastructure qui fait tourner Google Search, Gmail, YouTube… Vous louez de la puissance de calcul, du stockage, des bases de données, des API d'IA, etc., à l'usage (pay-as-you-go).

GCP regroupe plus de 200 services. Les plus utilisés tombent dans quelques grandes familles :

1.2 Pourquoi apprendre GCP quand on connaît Docker ?

Votre connaissance de Docker est un atout majeur. GCP a misé très tôt sur les conteneurs (Google a inventé Kubernetes !), ce qui fait que plusieurs services sont fondamentalement des "Docker managés" :

  • Cloud Run : vous donnez une image Docker, Google la lance et gère le scaling automatique. C'est presque docker run, mais avec HTTPS, auto-scaling, observabilité…
  • Artifact Registry : un Docker registry privé managé (comme Docker Hub mais chez Google).
  • GKE : un cluster Kubernetes managé, idéal si vous utilisez déjà docker-compose et voulez scaler.
  • Cloud Build : un CI qui construit vos images Docker depuis Git.

2. Concepts fondamentaux

2.1 La hiérarchie des ressources

Avant d'écrire la moindre commande, il faut comprendre comment GCP organise ce que vous créez. Tout ce que vous faites dans GCP existe à l'intérieur de cette hiérarchie :

Organization (ex: entreprise.com)
    └── Folder (ex: équipe-data)
          └── Project (ex: my-first-project-2026) ← le conteneur principal
                ├── Ressources (VM, buckets, BDD, etc.)
                └── Permissions IAM

Le Project — l'unité centrale

Le projet est le concept le plus important. Absolument toute ressource GCP appartient à un projet. Un projet c'est :

  • Un nom lisible (ex: "Mon Premier Projet")
  • Un Project ID unique mondialement (ex: my-first-project-2026) — vous le verrez dans toutes les commandes
  • Un Project Number automatique (ex: 123456789012)
  • Un compte de facturation (optionnel tant que vous n'activez rien de payant)
  • Des API activées (par défaut, quasi rien — il faut activer chaque service)
⚠️ Bon à savoir Le Project ID est immuable et unique dans le monde entier. Choisissez-le bien. Il apparaîtra dans les URLs des services, dans les noms de buckets, etc.

2.2 Régions et zones

Google Cloud possède des datacenters partout dans le monde. On parle de :

  • Multi-regions : grandes zones géographiques (us, eu, asia) — utilisé pour certains services comme Cloud Storage.
  • Regions : une zone géographique précise (ex: europe-west1 = Belgique, europe-west9 = Paris).
  • Zones : un datacenter dans une région (ex: europe-west1-b). C'est là qu'une VM tourne réellement.
Multi-region "eu"
 └── Region europe-west9 (Paris)
        ├── Zone europe-west9-a
        ├── Zone europe-west9-b
        └── Zone europe-west9-c
Pourquoi c'est important ?
  • Latence : créez vos ressources proches de vos utilisateurs.
  • Coût : les prix varient entre régions (Iowa us-central1 est souvent le moins cher).
  • Haute disponibilité : pour des apps critiques, on déploie sur plusieurs zones d'une même région.
  • Conformité/RGPD : en Europe on privilégie europe-west1, europe-west9 (Paris), europe-west4 (Pays-Bas).

2.3 APIs et services

Chaque service GCP expose une API REST. Avant de pouvoir utiliser (par ex.) Cloud Storage dans un projet, il faut activer son API. C'est une mesure de sécurité et de clarté : dans un nouveau projet, aucune API n'est activée.

# Exemple : activer l'API Cloud Storage
gcloud services enable storage.googleapis.com

# Lister les API déjà activées
gcloud services list --enabled

# Lister toutes les API disponibles (long !)
gcloud services list --available

2.4 Modèle de tarification (rapide)

Même si on ne paiera rien dans ce cours, comprenez le principe :

  • Pay-as-you-go : vous payez à la seconde/minute/Go d'utilisation.
  • Free Tier : chaque mois, un quota gratuit (ex: 1 micro VM, 5 Go de Cloud Storage, 2M d'invocations Cloud Functions…). Il est permanent, pas juste un essai.
  • $300 de crédit offerts pendant 90 jours pour tout nouveau compte — mais il faut entrer une CB.
  • Sustained use / committed use : remises automatiques si vous utilisez en continu ou vous engagez.

4. Installation de la gcloud CLI

Le Google Cloud SDK (aussi appelé gcloud CLI) est l'outil en ligne de commande qui parle aux API Google Cloud. Il contient plusieurs binaires :

  • gcloud : la commande principale (VM, projets, IAM, déploiements…)
  • gsutil : spécifique à Cloud Storage (copies de fichiers)
  • bq : spécifique à BigQuery
  • kubectl : pour Kubernetes (si GKE installé)

4.1 Installation sur Linux / macOS

# Méthode universelle : script officiel
curl https://sdk.cloud.google.com | bash

# Recharger le shell
exec -l $SHELL

# Vérifier
gcloud version

Sur Ubuntu/Debian (paquet officiel)

# Ajout de la clé et du dépôt
sudo apt-get install -y apt-transport-https ca-certificates gnupg curl
curl https://packages.cloud.google.com/apt/doc/apt-key.gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/cloud.google.gpg
echo "deb [signed-by=/usr/share/keyrings/cloud.google.gpg] https://packages.cloud.google.com/apt cloud-sdk main" | \
  sudo tee /etc/apt/sources.list.d/google-cloud-sdk.list

# Installation
sudo apt-get update && sudo apt-get install google-cloud-cli

Sur macOS via Homebrew

brew install --cask google-cloud-sdk

4.2 Installation via Docker (le plus simple !)

Puisque vous connaissez Docker, voici la méthode sans rien installer sur votre machine :

# Lancer une image gcloud en mode interactif
docker run --rm -it \
  -v "$HOME/.config/gcloud:/root/.config/gcloud" \
  google/cloud-sdk:latest \
  bash

# Une fois à l'intérieur, tapez :
gcloud version

5. gcloud CLI : les bases

5.1 Anatomie d'une commande gcloud

Toutes les commandes suivent la même structure logique, façon verbe-sujet :

gcloud  [GROUPE]  [SOUS-GROUPE]  [VERBE]  [NOM]  [--FLAGS]
    │        │          │           │       │        │
    │        │          │           │       │        └─ options (--region, --project, etc.)
    │        │          │           │       └─ cible de l'action (nom de ressource)
    │        │          │           └─ action (create, list, describe, delete, update)
    │        │          └─ sous-catégorie (ex: "instances" pour Compute)
    │        └─ famille de service (compute, storage, run, iam, projects…)
    └─ binaire

Exemples visuels

gcloud compute instances list
# └─┬─┘ └──┬──┘ └───┬───┘ └─┬┘
#  bin  groupe  sous-grp  verbe

gcloud run services describe my-api --region=europe-west1
#            └───┬───┘ └──┬───┘  └┬─┘          └──────┬──────┘
#            sous-grp   verbe   nom            flag obligatoire

gcloud projects create apprentissage-gcp-2026 --name="Apprentissage"

5.2 Authentification — la première étape

Avant toute action, gcloud doit savoir qui vous êtes. Deux modes :

  • User credentials : vous vous connectez avec votre compte Google personnel (pour développer).
  • Service account : un "robot" avec un fichier de clé JSON (pour les scripts/CI).
# 1. Lancer l'authentification (ouvre le navigateur)
gcloud auth login

# 2. Configurer le projet par défaut
gcloud config set project MON_PROJECT_ID

# 3. Vérifier la configuration active
gcloud config list

# 4. Voir les comptes connectés
gcloud auth list

# 5. Changer de compte
gcloud config set account autre@gmail.com
gcloud auth login
Ouvre un navigateur pour une authentification OAuth2. Les credentials sont stockés localement dans ~/.config/gcloud/. À faire une seule fois par machine.
gcloud auth login --no-launch-browser
Utile sur serveur ou WSL : affiche une URL à copier dans un navigateur d'une autre machine.
gcloud config set project <id>
Définit le projet par défaut. Évite de devoir écrire --project=xxx dans chaque commande.
gcloud config list
Affiche la "configuration active" : compte, projet, région, zone par défaut.
gcloud config configurations list
Liste toutes les configurations (vous pouvez en créer plusieurs : pro, perso, client-X).

5.3 Application Default Credentials (ADC)

Quand votre code (Python, Go, Node…) veut appeler une API GCP, il utilise les ADC. C'est un mécanisme standard qui cherche des credentials dans l'ordre :

  1. Variable d'environnement GOOGLE_APPLICATION_CREDENTIALS (chemin vers un JSON de service account).
  2. Fichier ~/.config/gcloud/application_default_credentials.json.
  3. Métadonnées de la VM/Cloud Run/Functions (automatique en prod).
# Configurer les ADC (à faire une fois par machine)
gcloud auth application-default login
💡 Différence clé gcloud auth login authentifie la CLI gcloud.
gcloud auth application-default login authentifie votre code applicatif (via les SDK Python/Java/etc).
Il faut faire les deux sur une machine de dev.

5.4 Commandes universelles : create, list, describe, delete, update

Presque tous les services supportent ces 5 verbes. Apprenez-les une fois, réutilisez partout :

# CREATE : créer une ressource
gcloud compute instances create ma-vm --zone=europe-west1-b --machine-type=e2-micro

# LIST : lister (souvent avec filtre)
gcloud compute instances list
gcloud compute instances list --filter="status=RUNNING"
gcloud compute instances list --format="table(name, status, zone)"

# DESCRIBE : détails d'une ressource
gcloud compute instances describe ma-vm --zone=europe-west1-b

# UPDATE : modifier
gcloud compute instances add-tags ma-vm --zone=europe-west1-b --tags=http-server

# DELETE : supprimer
gcloud compute instances delete ma-vm --zone=europe-west1-b --quiet
--quiet / -q
Saute les confirmations interactives. Indispensable pour les scripts.
--format=json|yaml|table|value|csv
Change la sortie. value(nom) extrait un seul champ — très utile pour piper : FOR_ID=$(gcloud ... --format="value(id)").
--filter="EXPR"
Filtre côté client. Exemples : status=RUNNING, labels.env=prod, creationTimestamp>'2024-01-01'.
--project=<id>
Override le projet pour cette commande uniquement.
--verbosity=debug|info|warning|error
Niveau de log. debug affiche les requêtes HTTP envoyées, très pédagogique.

6. IAM & comptes de service

IAM (Identity and Access Management) est le système qui répond à la question : « Qui a le droit de faire quoi sur quelle ressource ? ». C'est la pièce la plus importante pour la sécurité.

6.1 Les 3 concepts fondamentaux

Une policy IAM se lit comme une phrase : "<MEMBER> has <ROLE> on <RESOURCE>".

1. Member (l'identité)

  • user:alice@gmail.com — un utilisateur Google.
  • group:team@example.com — un Google Group.
  • serviceAccount:svc@proj.iam.gserviceaccount.com — un service account (un "robot").
  • domain:example.com — tout utilisateur du domaine Workspace.
  • allUsers — tout le monde sur Internet (attention !).
  • allAuthenticatedUsers — n'importe qui avec un compte Google.

2. Role (ce qu'on peut faire)

Un rôle est un ensemble de permissions (ex: storage.buckets.create). Trois catégories :

  • Basic roles (anciens, très larges — à éviter en prod) : roles/owner, roles/editor, roles/viewer.
  • Predefined roles (ciblés par service) : roles/storage.admin, roles/run.invoker, roles/bigquery.dataViewer…
  • Custom roles : vous composez vos propres permissions.

3. Resource (sur quoi)

Une policy peut être attachée à différents niveaux (le plus haut "gagne" en cumul) :

Organization ──────── policy ✅
  └── Folder ──────── policy ✅
       └── Project ── policy ✅
            └── Bucket / VM / etc. ── policy ✅ (granularité fine)

6.2 Commandes IAM essentielles

# Voir la policy IAM d'un projet
gcloud projects get-iam-policy MON_PROJET

# Ajouter un rôle à un utilisateur
gcloud projects add-iam-policy-binding MON_PROJET \
    --member="user:alice@gmail.com" \
    --role="roles/viewer"

# Retirer un rôle
gcloud projects remove-iam-policy-binding MON_PROJET \
    --member="user:alice@gmail.com" \
    --role="roles/viewer"

# Lister les rôles disponibles
gcloud iam roles list --filter="name:storage"
gcloud iam roles describe roles/storage.admin
get-iam-policy <ressource>
Retourne la policy au format YAML/JSON : qui a quoi. Sortez-la pour l'auditer.
add-iam-policy-binding
Ajoute une paire member/role. Idempotent (ne fait rien si déjà présent).
--member=...
Le préfixe est obligatoire : user:, group:, serviceAccount:, etc.
--role=roles/XXX
Toujours préfixé par roles/. Tapez gcloud iam roles list --filter="name:..." pour chercher.
--condition=...
(Avancé) Conditionne la permission (ex: expire après une date, limite à une IP).

6.3 Les Service Accounts (comptes de service)

Un service account est une identité non-humaine. Votre VM, votre Cloud Function, votre app sur GKE, votre CI GitHub Actions… tout ce qui agit sur GCP sans humain utilise un SA.

# Créer un service account
gcloud iam service-accounts create mon-app-sa \
    --display-name="Service Account pour mon app" \
    --description="Lit les fichiers du bucket archives"

# Son email est : mon-app-sa@MON_PROJET.iam.gserviceaccount.com

# Lui donner un rôle
gcloud projects add-iam-policy-binding MON_PROJET \
    --member="serviceAccount:mon-app-sa@MON_PROJET.iam.gserviceaccount.com" \
    --role="roles/storage.objectViewer"

# Générer une clé JSON (à protéger !)
gcloud iam service-accounts keys create ma-cle.json \
    --iam-account=mon-app-sa@MON_PROJET.iam.gserviceaccount.com

# Utiliser cette clé dans votre code :
export GOOGLE_APPLICATION_CREDENTIALS=/chemin/ma-cle.json
python mon_script.py

# Lister les clés
gcloud iam service-accounts keys list \
    --iam-account=mon-app-sa@MON_PROJET.iam.gserviceaccount.com

# Supprimer une clé (en cas de fuite !)
gcloud iam service-accounts keys delete KEY_ID \
    --iam-account=mon-app-sa@MON_PROJET.iam.gserviceaccount.com
⚠️ Sécurité des clés Les fichiers JSON de clés SA sont comme des mots de passe. Ne les committez JAMAIS dans Git. Ajoutez *.json à votre .gitignore. En prod, privilégiez :
  • Workload Identity (sur GKE) : pas de clé du tout, l'identité est attachée au pod.
  • SA attachée à la VM/Cloud Run : l'auth est automatique via les métadonnées.
  • Workload Identity Federation : pour les CI externes (GitHub Actions).

7. Compute Engine : les machines virtuelles

Compute Engine (GCE) fournit des VM Linux/Windows à la demande. C'est le service IaaS de base — équivalent EC2 chez AWS.

7.1 Concepts clés

  • Instance : une VM en cours d'exécution.
  • Machine type : le gabarit (CPU, RAM). Ex: e2-micro (2 vCPU partagés, 1 Go) qui est le type du Free Tier.
  • Image : le template disque (Debian 12, Ubuntu 22.04, ...). Les images Google sont préfixées par leur "famille".
  • Boot disk : le disque système. pd-standard (HDD), pd-balanced, pd-ssd.
  • Metadata / startup script : un script exécuté au démarrage de la VM.
  • Network tags : labels utilisés par les règles de firewall.

8. Cloud Storage (avec émulateur local)

Cloud Storage (GCS) est le service de stockage d'objets — équivalent S3 chez AWS. On l'utilise pour stocker photos, backups, datasets, fichiers statiques d'un site web, etc.

8.1 Concepts

  • Bucket : un conteneur de fichiers. Son nom est unique au monde (comme un domaine).
  • Object : un fichier + métadonnées. Un object a une clé (le "chemin") et un contenu.
  • Location : région, dual-region ou multi-region (plus cher mais multi-continent).
  • Storage class : Standard (accès fréquent), Nearline (1x/mois), Coldline (1x/trimestre), Archive (1x/an, le moins cher mais latence de récupération).

8.2 L'outil gsutil / gcloud storage

Historiquement on utilise gsutil. Depuis 2022, Google pousse la commande gcloud storage (plus rapide grâce à des uploads parallèles en Go). Les deux coexistent, on montre les deux :

# === Créer un bucket ===
gcloud storage buckets create gs://mon-bucket-unique-2026 \
    --location=europe-west1 \
    --default-storage-class=STANDARD \
    --uniform-bucket-level-access

# === Upload ===
gcloud storage cp rapport.pdf gs://mon-bucket-unique-2026/docs/

# Upload récursif d'un dossier
gcloud storage cp -r ./mon-site/ gs://mon-bucket-unique-2026/

# === Lister ===
gcloud storage ls gs://mon-bucket-unique-2026/
gcloud storage ls -l gs://mon-bucket-unique-2026/docs/    # détaillé
gcloud storage ls -r gs://mon-bucket-unique-2026/**       # récursif

# === Télécharger ===
gcloud storage cp gs://mon-bucket-unique-2026/docs/rapport.pdf ./
gcloud storage cp -r gs://mon-bucket-unique-2026/docs/ ./backup/

# === Synchroniser (comme rsync) ===
gcloud storage rsync ./site/ gs://mon-bucket-unique-2026/site/ --recursive --delete-unmatched-destination-objects

# === Supprimer ===
gcloud storage rm gs://mon-bucket-unique-2026/docs/vieux.txt
gcloud storage rm -r gs://mon-bucket-unique-2026/old/    # dossier entier
gcloud storage buckets delete gs://mon-bucket-unique-2026/

# === Rendre public un fichier ===
gcloud storage objects update gs://mon-bucket-unique-2026/public/image.png --add-acl-grant=entity=AllUsers,role=READER
# OU (moderne, IAM)
gcloud storage buckets add-iam-policy-binding gs://mon-bucket-unique-2026 \
    --member=allUsers --role=roles/storage.objectViewer

# === Signed URL (lien temporaire sans rendre public) ===
gcloud storage sign-url gs://mon-bucket-unique-2026/private/file.pdf \
    --private-key-file=./sa-key.json \
    --duration=1h
--location=europe-west1
Région du bucket. Choisir proche des utilisateurs. Valeurs : régions (europe-west1), dual-region (eur4), multi-region (eu, us, asia).
--default-storage-class
STANDARD / NEARLINE / COLDLINE / ARCHIVE. Peut être changé par objet après coup.
--uniform-bucket-level-access
Recommandé : une seule policy IAM pour tout le bucket (pas d'ACL par objet, plus simple à auditer).
-r (ou --recursive)
Récursif. Indispensable pour dossiers.
gs://...
Le scheme de l'URI Cloud Storage (équivalent s3:// pour AWS).
rsync --delete-unmatched-destination-objects
Supprime les fichiers de destination qui ne sont plus à la source. Utile pour un miroir exact.

9. Cloud Run : déployer des conteneurs

Cloud Run est probablement le service GCP que vous utiliserez le plus, surtout en venant de Docker. Principe : vous donnez une image Docker, Google la lance en HTTPS, auto-scale de 0 à N, et facture à la requête.

9.1 Comment ça marche

Cloud Run attend un conteneur qui :

  1. Écoute en HTTP sur le port défini par la variable d'environnement $PORT (souvent 8080).
  2. Démarre en < 4 min.
  3. Est "stateless" (pas de session locale, pas d'écriture disque persistante).
Cloud Run vs Cloud Functions vs GKE
  • Cloud Functions : vous écrivez une fonction. Google construit le conteneur.
  • Cloud Run : vous fournissez un conteneur. Plus de flexibilité (langages, dépendances système), même simplicité.
  • GKE : vous gérez le cluster Kubernetes. Pour orchestration avancée.

9.2 Construire une app exemple en Python + Flask

# main.py
import os
from flask import Flask, jsonify

app = Flask(__name__)

@app.route("/")
def index():
    return jsonify(
        message="Hello Cloud Run !",
        env=os.environ.get("K_SERVICE", "local"),
        revision=os.environ.get("K_REVISION", "v1"),
    )

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.environ.get("PORT", 8080)))

# requirements.txt

gunicorn==21.2.0

# Dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Cloud Run passe un port dynamique dans $PORT
ENV PORT=8080
CMD exec gunicorn --bind :$PORT --workers 1 --threads 8 --timeout 0 main:app

10. Cloud Functions : Functions as a Service

Cloud Functions (CF) vous permet d'écrire juste une fonction — pas de Dockerfile à gérer. Google détecte le langage (Python, Node.js, Go, Java, PHP, Ruby, .NET) et empaquette le tout.

10.1 Deux types de triggers

  • HTTP : la fonction est appelée via une URL HTTPS (REST).
  • Event-driven : déclenchement par un événement : nouveau fichier dans un bucket, message Pub/Sub, écriture Firestore, log, etc.

Depuis 2023, Cloud Functions s'appelle Cloud Run functions (gen2) et est construit au-dessus de Cloud Run + Eventarc. Mais le SDK gcloud functions reste identique.

14. Pub/Sub (avec émulateur officiel)

Pub/Sub est le bus de messages asynchrones de GCP (équivalent Kafka / SQS+SNS). Modèle publish-subscribe : un publisher envoie à un topic, un ou plusieurs subscribers consomment via des subscriptions.

14.1 Concepts

  • Topic : le canal (ex: orders-created).
  • Subscription : un "tuyau" de lecture. Chaque subscription reçoit une copie de chaque message. Deux modes :
    • Pull : le consommateur demande les messages.
    • Push : Pub/Sub POST chaque message à une URL HTTPS.
  • Ack : le consommateur acquitte le message (sinon redelivery après ack deadline).
  • Dead Letter Topic : messages non ack après N tentatives.

14.2 Lancer l'émulateur

gcloud components install pubsub-emulator beta

# Démarrer
gcloud beta emulators pubsub start --host-port=localhost:8085

# Dans un autre terminal, configurer l'environnement pour les SDK :
export PUBSUB_EMULATOR_HOST=localhost:8085
export GOOGLE_CLOUD_PROJECT=demo-project

Ou via Docker :

docker run -d --name pubsub-emu \
    -p 8085:8085 \
    gcr.io/google.com/cloudsdktool/google-cloud-cli:emulators \
    gcloud beta emulators pubsub start --host-port=0.0.0.0:8085

14.3 gcloud Pub/Sub — syntaxe

# === Topics ===
gcloud pubsub topics create orders
gcloud pubsub topics list
gcloud pubsub topics describe orders
gcloud pubsub topics publish orders --message='{"id":1,"total":42}'
gcloud pubsub topics delete orders

# === Subscriptions ===
gcloud pubsub subscriptions create orders-worker \
    --topic=orders \
    --ack-deadline=30

# Pull en mode CLI (debug)
gcloud pubsub subscriptions pull orders-worker --auto-ack --limit=5

# Subscription push vers Cloud Run
gcloud pubsub subscriptions create orders-push \
    --topic=orders \
    --push-endpoint=https://my-cloud-run-xxx.run.app/ \
    --push-auth-service-account=invoker@MON_PROJET.iam.gserviceaccount.com
--ack-deadline=30
Délai (secondes) pour acquitter un message avant redelivery. 10 à 600.
--message-retention-duration=7d
Durée pendant laquelle les messages sont conservés si non ack (défaut 7 jours).
--dead-letter-topic=dead-orders
Topic où envoyer les messages non ack après --max-delivery-attempts tentatives.
--push-endpoint=URL
Active le mode push vers un endpoint HTTPS.
--expiration-period=never
Empêche la subscription d'expirer après 31 jours d'inactivité.

14.4 Exemple code Python

# publisher.py
import os
from google.cloud import pubsub_v1

os.environ["PUBSUB_EMULATOR_HOST"] = "localhost:8085"
PROJECT = "demo-project"

publisher = pubsub_v1.PublisherClient()
topic_path = publisher.topic_path(PROJECT, "orders")

# Créer le topic si besoin
try:
    publisher.create_topic(request={"name": topic_path})
except Exception:
    pass

# Publier
future = publisher.publish(topic_path, b'{"id":1,"total":42}')
print("Message publié, ID:", future.result())

# subscriber.py
import os
from google.cloud import pubsub_v1

os.environ["PUBSUB_EMULATOR_HOST"] = "localhost:8085"
PROJECT = "demo-project"

subscriber = pubsub_v1.SubscriberClient()
sub_path = subscriber.subscription_path(PROJECT, "orders-worker")

def handle(message):
    print(f"Reçu: {message.data.decode()}")
    message.ack()  # confirmer le traitement

future = subscriber.subscribe(sub_path, callback=handle)
print("En attente... Ctrl+C pour quitter")
try:
    future.result()
except KeyboardInterrupt:
    future.cancel()

17. Monitoring & Logging

Cloud Operations (ex-Stackdriver) regroupe les outils d'observabilité. Quatre briques principales :

  • Cloud Logging : tous les logs (stdout des VMs/pods/services, logs d'audit).
  • Cloud Monitoring : métriques + dashboards + alertes.
  • Cloud Trace : distributed tracing (OpenTelemetry).
  • Error Reporting : agrège les erreurs applicatives.

17.1 Cloud Logging

La bonne nouvelle : tout ce que votre app écrit sur stdout/stderr dans Cloud Run, Functions, GKE, est automatiquement capturé dans Cloud Logging.

# Lire les logs d'un service
gcloud logging read "resource.type=cloud_run_revision AND resource.labels.service_name=hello-service" \
    --limit=20 \
    --format=json

# Logs récents en direct (équivalent tail -f)
gcloud logging tail "resource.type=cloud_run_revision"

# Envoyer un log custom
gcloud logging write mon-log "Message de test" --severity=INFO

17.2 Logs structurés (JSON)

Pour des logs filtrables par champ, loggez du JSON sur stdout. Cloud Logging les parsera automatiquement :

import json, sys

def log(severity, message, **kwargs):
    entry = dict(severity=severity, message=message, **kwargs)
    print(json.dumps(entry), flush=True)

log("INFO", "Nouvel utilisateur", user_id=42, plan="free")
log("ERROR", "Échec DB", query="SELECT ...", duration_ms=2500)

Dans la console Logging, vous pourrez alors filtrer : jsonPayload.user_id=42.

17.3 Requêtes de logs (LQL - Logging Query Language)

# Erreurs récentes d'un service
resource.type="cloud_run_revision"
resource.labels.service_name="hello-service"
severity>=ERROR

# Logs d'une VM spécifique
resource.type="gce_instance"
resource.labels.instance_id="1234567890"
timestamp>="2024-11-01T00:00:00Z"

# Filtrer par champ JSON
jsonPayload.user_id=42
jsonPayload.duration_ms>1000
