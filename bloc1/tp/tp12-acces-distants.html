TP 12 : Mettre en place un bastion d'administration

Vous créez BST-LNX-01, le bastion d'Hexalog, seul point d'entrée des accès d'administration. Il a deux cartes : l'une dans le lab, l'autre en accès par pont sur le partage de connexion de votre téléphone, par laquelle votre PC le joint directement. SRV-LNX-01 n'accepte plus SSH que depuis le bastion, SRV-WIN-01 n'accepte plus le bureau à distance que depuis le bastion, votre PC passe par un rebond SSH et un tunnel. Vous rédigez la procédure d'accès et vous reconstituez une intervention à partir des journaux.

Contexte

Aujourd’hui, les redirections de ports du lab donnent un accès direct à SRV-LNX-01 (SSH) et à SRV-WIN-01 (RDP). L’audit demande qu’un seul point d’entrée soit exposé et que les serveurs refusent toute administration qui ne vient pas de ce point.

Comme en entreprise, le bastion a une patte dans chaque réseau : une carte côté serveurs (LAB-HEXALOG) et une carte côté administration. Dans le lab, la carte d’administration est en Accès par pont (vu au TP 2) : le bastion est branché, comme votre PC, sur le réseau du partage de connexion de votre téléphone, et reçoit son adresse du même DHCP, celui du téléphone. Votre PC le joint directement, sans redirection. Les serveurs n’ont aucune carte sur ce réseau : depuis le partage de connexion, seul le bastion est joignable, par votre PC mais aussi par tout autre appareil connecté au même partage (votre téléphone, un voisin à qui vous l’ouvrez). C’est le rôle d’un point d’entrée : il est exposé, donc il doit être durci.

Dans la suite, ADRESSE-BASTION désigne l’adresse que la carte en pont du bastion aura reçue (étape 1) : remplacez-la à chaque fois par la vôtre.

Architecture cible

Redirections de ports de LAB-HEXALOG en fin de TP :

Nom Hôte Invité Statut
web-srv 127.0.0.1:8080 10.10.10.20:80 conservée (service public)
ssh-srv 127.0.0.1:2222 10.10.10.20:22 supprimée
rdp-dc 127.0.0.1:33890 10.10.10.10:3389 supprimée

Aucune redirection ne remplace ssh-srv : votre PC joint le bastion directement, sur sa carte en pont.

Étape 1. Créer BST-LNX-01

  1. Clonez TPL-DEB13 en clone lié nommé BST-LNX-01, avec de nouvelles adresses MAC. RAM : 768 Mo suffisent.
  2. Dans Configuration → Réseau :
    • Adaptateur 1 : Réseau NAT → LAB-HEXALOG ;
    • Adaptateur 2 : cochez Activer la carte réseau, mode Accès par pont, nom : la carte par laquelle votre PC est connecté, c’est-à-dire la carte Wi-Fi reliée au partage de connexion de votre téléphone (et non une carte VirtualBox).
    Démarrez.
  3. La carte 1 reçoit une adresse provisoire du DHCP du lab ; la carte 2 n’est pas encore configurée. Dans la console VirtualBox, connecté en sysadmin :
Machine : BST-LNX-01 (console)
sudo preparer-clone.sh bst-lnx-01
sudo nano /etc/network/interfaces      # enp0s3 en statique : 10.10.10.30/24, passerelle 10.10.10.1

Dans le même fichier, ajoutez à la fin la carte 2. Elle prend son adresse auprès du DHCP de votre partage de connexion (ou de votre box à la maison), comme votre PC :

Fichier : /etc/network/interfaces (BST-LNX-01, ajout)
# Carte 2 : accès par pont (partage de connexion)
allow-hotplug enp0s8
iface enp0s8 inet dhcp

Ce DHCP ne donne pas qu’une adresse : il fournit aussi une passerelle (le téléphone) et des serveurs DNS. Il ne faut pas les laisser remplacer ceux du lab : le bastion aurait deux routes par défaut, et le client DHCP de Debian (dhcpcd) réécrirait /etc/resolv.conf avec les DNS du téléphone, qui ne connaissent pas hexalog.local. On le lui interdit pour cette seule carte, à la fin de son fichier de configuration :

Machine : BST-LNX-01 (console)
sudo nano /etc/dhcpcd.conf
Fichier : /etc/dhcpcd.conf (BST-LNX-01, ajout à la fin)
# Carte 2 (accès par pont) : une adresse, ni passerelle ni DNS
interface enp0s8
ipv4only
nogateway
nohook resolv.conf

La route par défaut reste donc celle de la carte 1 (10.10.10.1), qui donne Internet au bastion par le NAT du lab, et les DNS restent ceux du domaine. Puis :

Machine : BST-LNX-01 (console)
sudo nano /etc/resolv.conf             # même contenu que sur SRV-LNX-01 (TP 3, étape 2)
sudo reboot
  1. Après redémarrage :
Machine : BST-LNX-01 (console)
ip -br a                    # enp0s3 : 10.10.10.30/24 ; enp0s8 : une adresse du partage de connexion
ip route                    # une seule route par défaut : via 10.10.10.1 dev enp0s3
cat /etc/resolv.conf        # toujours 10.10.10.10 en premier
ping -c 2 srv-lnx-01
sudo apt update && sudo apt full-upgrade -y

Notez dans votre journal l’adresse de enp0s8 : c’est ADRESSE-BASTION. Elle vient du DHCP du téléphone et peut changer (partage de connexion relancé, autre téléphone, maison) : en début de séance, vérifiez-la avec ip -br a sur la console du bastion.

  1. Sur SRV-WIN-01, ajoutez l’enregistrement DNS : Outils → DNS → zone hexalog.local → clic droit → Nouvel hôte (A ou AAAA)… → nom bst-lnx-01, adresse 10.10.10.30 → Ajouter un hôte.

Étape 2. Supprimer les redirections d’administration

Dans le Gestionnaire de réseau (LAB-HEXALOG → Redirection de ports), supprimez ssh-srv et rdp-dc (si vous l’aviez créée au TP 5). Ne créez aucune redirection pour le bastion : il est joint directement sur sa carte en pont.

Machine : PC hôte (équivalent en ligne de commande)
VBoxManage natnetwork modify --netname LAB-HEXALOG --port-forward-4 delete ssh-srv
VBoxManage natnetwork modify --netname LAB-HEXALOG --port-forward-4 delete rdp-dc

Depuis le PC, vérifiez que l’ancien accès est fermé et que le bastion répond sur sa carte en pont :

Machine : PC hôte
ipconfig                                # votre adresse sur le partage de connexion (même réseau que le bastion)
ssh -p 2222 sysadmin@127.0.0.1          # refusé : la redirection n'existe plus
ping -n 2 ADRESSE-BASTION
ssh sysadmin@ADRESSE-BASTION

(Sur un PC Linux : ip -br a au lieu d’ipconfig, et ping -c 2.)

ssh vous demande de valider l’empreinte du bastion : pour votre PC, c’est une machine inconnue. Avant de répondre yes, comparez cette empreinte avec celle que donne la console du bastion (ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub) et notez la vérification dans votre journal. Retirez aussi de known_hosts l’ancienne entrée [127.0.0.1]:2222 (la clé de SRV-LNX-01 par l’ancienne redirection), devenue inutile :

Machine : PC hôte
ssh-keygen -R "[127.0.0.1]:2222"

Enchaînez avec l'étape 3

Dès maintenant, le bastion est joignable par tout appareil connecté à votre partage de connexion, et il accepte encore le mot de passe du lab, que toute la classe connaît. Passez directement à l’étape 3 : une fois durci, il n’acceptera plus que votre clé.

Étape 3. Durcir le bastion

  1. Déposez la clé du PC sur le bastion (le mot de passe est encore accepté) :
Machine : PC hôte Windows (PowerShell)
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | ssh sysadmin@ADRESSE-BASTION "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

(Sur un PC Linux : ssh-copy-id sysadmin@ADRESSE-BASTION.)

  1. Sur le bastion, appliquez le même durcissement qu’à la séance 10 : groupe ssh-users contenant sysadmin, fichier /etc/ssh/sshd_config.d/10-durcissement.conf, sudo sshd -t, redémarrage en gardant la session ouverte, test dans une nouvelle session.
  2. Pare-feu du bastion : il est le point d’entrée, il accepte SSH sur ses deux cartes, depuis le partage de connexion (votre PC) et depuis le lab (les postes internes). Dans une vraie entreprise : uniquement depuis le VPN ou les adresses des administrateurs (voir « Pour aller plus loin »).
Machine : BST-LNX-01 (sysadmin)
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp comment 'point entree administration'
sudo ufw enable
sudo ufw status verbose
  1. Vérifiez que le bastion ne route pas d’un réseau à l’autre : il relaie des connexions SSH authentifiées, il ne transmet pas de paquets entre ses deux cartes.
Machine : BST-LNX-01 (sysadmin)
sysctl net.ipv4.ip_forward          # net.ipv4.ip_forward = 0 (valeur par défaut de Debian)

Votre PC ne connaît d’ailleurs aucune route vers 10.10.10.0/24 : depuis le PC, ping -n 2 10.10.10.20 échoue. Le seul chemin vers les serveurs passe par une connexion SSH au bastion.

Snapshot 12-bastion-durci.

Étape 4. Rebondir vers SRV-LNX-01

Le problème. Depuis l’étape 2, la redirection 127.0.0.1:2222 n’existe plus : votre PC ne joint plus que le bastion, sur sa carte en pont (ADRESSE-BASTION). Votre PC n’est pas dans le réseau 10.10.10.0/24 : il ne peut plus joindre SRV-LNX-01 tout seul. Il doit passer par le bastion : PC → bastion → SRV-LNX-01. C’est ce qu’on appelle rebondir.

La mauvaise façon. Se connecter au bastion, puis, depuis le bastion, taper ssh 10.10.10.20. C’est alors le bastion qui se connecte à SRV-LNX-01 : il lui faudrait votre clé privée, copiée sur lui. Si le bastion était piraté, votre clé serait volée.

La bonne façon : ProxyJump. Le bastion se contente de faire passer la connexion jusqu’au port 22 de SRV-LNX-01. Le tuyau chiffré va directement de votre PC à SRV-LNX-01, glissé à l’intérieur du tuyau qui va jusqu’au bastion. Votre clé privée reste sur le PC et sert deux fois : une fois devant le bastion, une fois devant SRV-LNX-01. Rien à copier : votre clé publique est déjà sur SRV-LNX-01 (TP 10, étape 4) et sur le bastion (étape 3).

  1. Modifiez le fichier ~/.ssh/config du PC (créé au TP 10, étape 4). Il contient déjà un bloc Host srv-lnx-01 qui pointe vers 127.0.0.1, port 2222 : remplacez-le. À la fin, le fichier contient exactement ceci :
Fichier : ~/.ssh/config (PC hôte)
Host bastion
    # remplacez ADRESSE-BASTION par l'adresse de la carte en pont (étape 1)
    HostName ADRESSE-BASTION
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519

Host srv-lnx-01
    HostName 10.10.10.20
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump bastion

Remplacer, pas ajouter

Si l’ancien bloc Host srv-lnx-01 reste dans le fichier au-dessus du nouveau, SSH garde la première valeur trouvée pour chaque réglage : 127.0.0.1, port 2222. Il demande alors au bastion de se connecter à 127.0.0.1:2222, c’est-à-dire à lui-même, sur un port fermé. Résultat : channel 0: open failed: connect failed: Connection refused.

Ce que disent les deux blocs :

Réglage Signification
Host bastion un surnom : vous taperez bastion au lieu de l’adresse
HostName ADRESSE-BASTION l’adresse de la carte en pont du bastion, la seule que votre PC peut joindre (port 22, valeur par défaut). Si elle change (partage de connexion relancé, maison), modifiez cette ligne
Host srv-lnx-01 un second surnom
HostName 10.10.10.20 l’adresse de SRV-LNX-01 vue depuis le bastion : c’est lui qui ouvre la connexion réseau vers le serveur (port 22, valeur par défaut)
ProxyJump bastion « passe d’abord par bastion »
User et IdentityFile le compte sysadmin et votre clé perso-pc, la même pour les deux machines
  1. Testez chaque saut. Le mot hostname placé à la fin de la commande est exécuté sur la machine distante : elle affiche son nom, puis la connexion se ferme.
Machine : PC hôte
ssh bastion hostname             # attendu : bst-lnx-01
ssh srv-lnx-01 hostname          # attendu : srv-lnx-01

Si votre clé a une phrase de passe, elle est demandée deux fois : une fois pour le bastion, une fois pour SRV-LNX-01. C’est normal, votre clé sert deux fois.

  1. Validez l’empreinte de SRV-LNX-01. À la seconde commande, SSH demande d’accepter une empreinte : votre PC a connu SRV-LNX-01 sous le nom [127.0.0.1]:2222 (entrée retirée à l’étape 2), il le joint maintenant sous le nom 10.10.10.20, qu’il ne connaît pas encore. Comparez avec l’empreinte de la clé d’hôte de SRV-LNX-01 notée dans le tableau B du TP 10, puis répondez yes. C’est bien l’empreinte de SRV-LNX-01 qui s’affiche, et non celle du bastion : le bastion ne fait que relayer.

Sans le fichier config, la même connexion s’écrirait : ssh -J sysadmin@ADRESSE-BASTION sysadmin@10.10.10.20.

Étape 5. Fermer l’accès direct à SRV-LNX-01

Connecté à SRV-LNX-01 par le bastion :

Machine : SRV-LNX-01 (sysadmin, via le bastion)
sudo ufw status numbered
sudo ufw allow from 10.10.10.30 to any port 22 proto tcp comment 'administration via bastion'
sudo ufw status numbered                                   # repérez le numéro de l'ancienne règle 10.10.10.0/24
sudo ufw delete NUMERO
sudo ufw status verbose

Vérifiez :

Machine : CLI-LNX-01 (sysadmin)
nc -zv -w 3 srv-lnx-01 22          # délai dépassé : filtré
curl -I http://srv-lnx-01          # le service web reste public
Machine : PC hôte
ssh srv-lnx-01 hostname            # toujours possible via le bastion

Étape 6. Le bureau à distance par le bastion

  1. Sur SRV-WIN-01, si ce n’est pas déjà fait : Gestionnaire de serveur → Serveur local → Bureau à distance → Autoriser les connexions à distance à cet ordinateur → OK. Windows active alors les règles de pare-feu du Bureau à distance.

  2. Restreignez la portée de ces règles au seul bastion. Ouvrez Pare-feu Windows Defender avec fonctions avancées de sécurité (Outils, ou wf.msc) → Règles de trafic entrant. Pour les deux règles Bureau à distance - Mode utilisateur (TCP-Entrée) et (UDP-Entrée) : double-clic → onglet Étendue → Adresse IP distante : Ces adresses IP → Ajouter → 10.10.10.30 → OK, OK.

  3. Vérifiez le filtrage :

Machine : CLI-LNX-01 (sysadmin)
nc -zv -w 3 srv-win-01 3389        # délai dépassé
Machine : BST-LNX-01 (sysadmin)
sudo apt install -y netcat-openbsd
nc -zv -w 3 srv-win-01 3389        # succeeded
  1. Depuis le PC, ouvrez le tunnel (laissez la fenêtre ouverte) :
Machine : PC hôte
ssh -N -L 13389:10.10.10.10:3389 bastion
  1. Lancez Connexion Bureau à distance (mstsc) vers 127.0.0.1:13389 :
    • avec HEXALOG\n.fournier : refusé, pourquoi ?
    • avec HEXALOG\adm.nfournier : accepté.

Fermez la session RDP (Démarrer → Se déconnecter), puis le tunnel (Ctrl+C).

Étape 7. Reconstituer l’intervention

Faites une petite intervention réelle : via le bastion, sur SRV-LNX-01, sudo systemctl reload nginx. Puis rassemblez les preuves.

Machine : BST-LNX-01 (sysadmin)
sudo journalctl -u ssh --since "1 hour ago" --no-pager | grep -E 'Accepted|Failed|not allowed'
Machine : SRV-LNX-01 (sysadmin)
sudo journalctl -u ssh --since "1 hour ago" --no-pager | grep Accepted
sudo journalctl _COMM=sudo --since "1 hour ago" --no-pager

Sur SRV-WIN-01, dans l’Observateur d’événements :

  • Journaux Windows → Sécurité → Filtrer le journal actuel → ID 4624 : ouvrez les événements récents dont le Type d’ouverture de session est 10 (bureau à distance) ; relevez le Nom du compte et l’Adresse du réseau source (celle du bastion) ;
  • Journaux des applications et des services → Microsoft → Windows → TerminalServices-LocalSessionManager → Operational : ouverture (21), reconnexion (25) et fermeture (23, 24) des sessions de bureau à distance.

Présentez une chronologie de l’intervention : heure, machine, compte, origine, action, preuve (ligne de journal).

Un VPN WireGuard entre CLI-LNX-01 et le bastion

Machines : BST-LNX-01 et CLI-LNX-01
sudo apt install -y wireguard
wg genkey | tee prive.key | wg pubkey > public.key      # sur chaque machine
Fichier : /etc/wireguard/wg0.conf (BST-LNX-01)
[Interface]
Address = 10.99.0.1/24
ListenPort = 51820
PrivateKey = <clé privée du bastion>

[Peer]
PublicKey = <clé publique de CLI-LNX-01>
AllowedIPs = 10.99.0.2/32
Fichier : /etc/wireguard/wg0.conf (CLI-LNX-01)
[Interface]
Address = 10.99.0.2/24
PrivateKey = <clé privée de CLI-LNX-01>

[Peer]
PublicKey = <clé publique du bastion>
Endpoint = 10.10.10.30:51820
AllowedIPs = 10.99.0.0/24

Autorisez 51820/udp dans UFW sur le bastion, lancez sudo wg-quick up wg0 des deux côtés, puis sudo wg show et ping 10.99.0.1 depuis CLI-LNX-01. Pouvez-vous ensuite n’autoriser SSH sur le bastion que depuis 10.99.0.0/24 et depuis votre PC ?

Limiter SSH à votre PC sur la carte en pont

En entreprise, le bastion n’accepte que les adresses des administrateurs. Remplacez la règle ouverte à tous par deux règles : le lab (carte enp0s3) et votre seul PC (carte enp0s8). Gardez la règle du lab : l’évaluation finale passe par CLI-LNX-01.

Machine : BST-LNX-01 (sysadmin)
sudo ufw allow in on enp0s3 to any port 22 proto tcp comment 'lab'
sudo ufw allow in on enp0s8 from ADRESSE-PC to any port 22 proto tcp comment 'PC administrateur'
sudo ufw status numbered                 # repérez le numéro de l'ancienne règle 22/tcp
sudo ufw delete NUMERO

ADRESSE-PC est l’adresse de votre PC sur le partage de connexion (ipconfig, carte Wi-Fi). Un autre appareil du partage n’atteint plus du tout le port 22 de votre bastion (délai dépassé au lieu d’un refus). Revers : si l’adresse de votre PC change (partage relancé, maison), il faut modifier la règle depuis la console VirtualBox.

fail2ban sur le bastion

sudo apt install -y fail2ban python3-systemd, puis un fichier /etc/fail2ban/jail.d/sshd.local avec [sshd], enabled = true, backend = systemd, maxretry = 5, bantime = 15m. Faites ensuite jouer l’attaquant à un voisin connecté à votre partage de connexion : cinq mots de passe faux depuis son PC, puis sudo fail2ban-client status sshd sur le bastion montre son adresse bannie. Attention à votre propre PC : si son adresse est bannie, il n’a plus accès au bastion ; ajoutez-la à ignoreip.
