TP 12 : Mettre en place un bastion d'administration

Vous créez BST-LNX-01, le bastion d'Hexalog, seul point d'entrée des accès d'administration. SRV-LNX-01 n'accepte plus SSH que depuis le bastion, SRV-WIN-01 n'accepte plus le bureau à distance que depuis le bastion, votre PC passe par un rebond SSH et un tunnel. Vous rédigez la procédure d'accès et vous reconstituez une intervention à partir des journaux.

Durée2 h 45
Machines virtuellesBST-LNX-01, SRV-LNX-01, SRV-WIN-01, CLI-LNX-01, PC hôte

Contexte

Aujourd’hui, les redirections de ports du lab donnent un accès direct à SRV-LNX-01 (SSH) et à SRV-WIN-01 (RDP). L’audit demande qu’un seul point d’entrée soit exposé et que les serveurs refusent toute administration qui ne vient pas de ce point.

Architecture cible

Redirections de ports de LAB-HEXALOG en fin de TP :

Nom Hôte Invité Statut
web-srv 127.0.0.1:8080 10.10.10.20:80 conservée (service public)
ssh-srv 127.0.0.1:2222 10.10.10.20:22 supprimée
rdp-dc 127.0.0.1:33890 10.10.10.10:3389 supprimée
ssh-bst 127.0.0.1:2222 10.10.10.30:22 créée

Étape 1. Créer BST-LNX-01

  1. Clonez TPL-DEB13 en clone lié nommé BST-LNX-01, avec de nouvelles adresses MAC. RAM : 768 Mo suffisent.
  2. Adaptateur 1 : Réseau NAT → LAB-HEXALOG. Démarrez.
  3. La VM reçoit une adresse provisoire du DHCP du lab : on lui donne son adresse fixe. Dans la console VirtualBox, connecté en sysadmin :
Machine : BST-LNX-01 (console)
sudo preparer-clone.sh bst-lnx-01
sudo nano /etc/network/interfaces      # enp0s3 en statique : 10.10.10.30/24, passerelle 10.10.10.1
sudo nano /etc/resolv.conf             # même contenu que sur SRV-LNX-01 (TP 3, étape 2)
sudo reboot
  1. Après redémarrage : ip -br a, ping -c 2 srv-lnx-01, puis sudo apt update && sudo apt full-upgrade -y.
  2. Sur SRV-WIN-01, ajoutez l’enregistrement DNS : Outils → DNS → zone hexalog.local → clic droit → Nouvel hôte (A ou AAAA)… → nom bst-lnx-01, adresse 10.10.10.30 → Ajouter un hôte.

Étape 2. Changer les redirections

Dans le Gestionnaire de réseau (LAB-HEXALOG → Redirection de ports), supprimez ssh-srv et rdp-dc (si vous l’aviez créée au TP 5), puis ajoutez ssh-bst : TCP, 127.0.0.1, 2222 → 10.10.10.30, 22.

Machine : PC hôte (équivalent en ligne de commande)
VBoxManage natnetwork modify --netname LAB-HEXALOG --port-forward-4 delete ssh-srv
VBoxManage natnetwork modify --netname LAB-HEXALOG --port-forward-4 delete rdp-dc
VBoxManage natnetwork modify --netname LAB-HEXALOG --port-forward-4 "ssh-bst:tcp:[127.0.0.1]:2222:[10.10.10.30]:22"

Depuis le PC : ssh -p 2222 sysadmin@127.0.0.1. Un avertissement REMOTE HOST IDENTIFICATION HAS CHANGED apparaît. Expliquez-le dans votre journal, vérifiez l’empreinte du bastion depuis sa console (ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub), puis :

Machine : PC hôte
ssh-keygen -R "[127.0.0.1]:2222"

Étape 3. Durcir le bastion

  1. Déposez la clé du PC sur le bastion (le mot de passe est encore accepté) :
Machine : PC hôte Windows (PowerShell)
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | ssh -p 2222 sysadmin@127.0.0.1 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

(Sur un PC Linux : ssh-copy-id -p 2222 sysadmin@127.0.0.1.)

  1. Sur le bastion, appliquez le même durcissement qu’à la séance 10 : groupe ssh-users contenant sysadmin, fichier /etc/ssh/sshd_config.d/10-durcissement.conf, sudo sshd -t, redémarrage en gardant la session ouverte, test dans une nouvelle session.
  2. Pare-feu du bastion : il est le point d’entrée, il accepte SSH (dans une vraie entreprise : uniquement depuis le VPN ou les adresses des administrateurs).
Machine : BST-LNX-01 (sysadmin)
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp comment 'point entree administration'
sudo ufw enable
sudo ufw status verbose

Snapshot 12-bastion-durci.

Étape 4. Rebondir vers SRV-LNX-01

Modifiez le fichier ~/.ssh/config du PC :

Fichier : ~/.ssh/config (PC hôte)
Host bastion
    HostName 127.0.0.1
    Port 2222
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519

Host srv-lnx-01
    HostName 10.10.10.20
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump bastion
Machine : PC hôte
ssh bastion hostname
ssh srv-lnx-01 hostname          # validez l'empreinte de SRV-LNX-01 (vue à la séance 10)

La clé du PC est déjà autorisée sur SRV-LNX-01 depuis la séance 10 : c’est elle qui sert, de bout en bout.

Étape 5. Fermer l’accès direct à SRV-LNX-01

Connecté à SRV-LNX-01 par le bastion :

Machine : SRV-LNX-01 (sysadmin, via le bastion)
sudo ufw status numbered
sudo ufw allow from 10.10.10.30 to any port 22 proto tcp comment 'administration via bastion'
sudo ufw status numbered                                   # repérez le numéro de l'ancienne règle 10.10.10.0/24
sudo ufw delete NUMERO
sudo ufw status verbose

Vérifiez :

Machine : CLI-LNX-01 (sysadmin)
nc -zv -w 3 srv-lnx-01 22          # délai dépassé : filtré
curl -I http://srv-lnx-01          # le service web reste public
Machine : PC hôte
ssh srv-lnx-01 hostname            # toujours possible via le bastion

Étape 6. Le bureau à distance par le bastion

  1. Sur SRV-WIN-01, si ce n’est pas déjà fait : Gestionnaire de serveur → Serveur local → Bureau à distance → Autoriser les connexions à distance à cet ordinateur → OK. Windows active alors les règles de pare-feu du Bureau à distance.

  2. Restreignez la portée de ces règles au seul bastion. Ouvrez Pare-feu Windows Defender avec fonctions avancées de sécurité (Outils, ou wf.msc) → Règles de trafic entrant. Pour les deux règles Bureau à distance - Mode utilisateur (TCP-Entrée) et (UDP-Entrée) : double-clic → onglet Étendue → Adresse IP distante : Ces adresses IP → Ajouter → 10.10.10.30 → OK, OK.

  3. Vérifiez le filtrage :

Machine : CLI-LNX-01 (sysadmin)
nc -zv -w 3 srv-win-01 3389        # délai dépassé
Machine : BST-LNX-01 (sysadmin)
sudo apt install -y netcat-openbsd
nc -zv -w 3 srv-win-01 3389        # succeeded
  1. Depuis le PC, ouvrez le tunnel (laissez la fenêtre ouverte) :
Machine : PC hôte
ssh -N -L 13389:10.10.10.10:3389 bastion
  1. Lancez Connexion Bureau à distance (mstsc) vers 127.0.0.1:13389 :
    • avec HEXALOG\n.fournier : refusé, pourquoi ?
    • avec HEXALOG\adm.nfournier : accepté.

Fermez la session RDP (Démarrer → Se déconnecter), puis le tunnel (Ctrl+C).

Étape 7. Reconstituer l’intervention

Faites une petite intervention réelle : via le bastion, sur SRV-LNX-01, sudo systemctl reload nginx. Puis rassemblez les preuves.

Machine : BST-LNX-01 (sysadmin)
sudo journalctl -u ssh --since "1 hour ago" --no-pager | grep -E 'Accepted|Failed|not allowed'
Machine : SRV-LNX-01 (sysadmin)
sudo journalctl -u ssh --since "1 hour ago" --no-pager | grep Accepted
sudo journalctl _COMM=sudo --since "1 hour ago" --no-pager

Sur SRV-WIN-01, dans l’Observateur d’événements :

  • Journaux Windows → Sécurité → Filtrer le journal actuel → ID 4624 : ouvrez les événements récents dont le Type d’ouverture de session est 10 (bureau à distance) ; relevez le Nom du compte et l’Adresse du réseau source (celle du bastion) ;
  • Journaux des applications et des services → Microsoft → Windows → TerminalServices-LocalSessionManager → Operational : ouverture (21), reconnexion (25) et fermeture (23, 24) des sessions de bureau à distance.

Présentez une chronologie de l’intervention : heure, machine, compte, origine, action, preuve (ligne de journal).

Étape 8. La procédure d’accès administrateur

Rédigez la procédure d’accès aux serveurs d’Hexalog (modèle sur Modèles de livrables) : qui, comment (bastion, clés, comptes adm.*), d’où, quand, traces et durée de conservation, compte bris de glace, arrivée et départ d’un administrateur. Elle fait partie du dossier d’exploitation de la séance 14.

Dépannage

Symptôme Piste
ssh srv-lnx-01 : channel 0: open failed: administratively prohibited le bastion interdit le relais TCP : vérifier AllowTcpForwarding (sudo sshd -T | grep allowtcp)
ssh srv-lnx-01 : délai dépassé règle UFW de SRV-LNX-01 : l’adresse du bastion est-elle bien autorisée ?
Bloqué hors de SRV-LNX-01 après ufw delete la règle du bastion n’était pas en place : console VirtualBox, sudo ufw allow from 10.10.10.30 to any port 22 proto tcp
mstsc : impossible de se connecter à 127.0.0.1:13389 le tunnel est-il ouvert (fenêtre ssh -N active) ? règle RDP restreinte à une autre adresse ?
n.fournier est accepté en RDP il a été ajouté à un groupe d’administration : vérifier ses groupes (onglet Membre de)
mstsc : l’ordinateur distant n’accepte pas les connexions Bureau à distance non autorisé sur SRV-WIN-01 (étape 6, point 1)
ProxyJump non reconnu client SSH trop ancien : utiliser ssh -J bastion sysadmin@10.10.10.20

Un VPN WireGuard entre CLI-LNX-01 et le bastion

Machines : BST-LNX-01 et CLI-LNX-01
sudo apt install -y wireguard
wg genkey | tee prive.key | wg pubkey > public.key      # sur chaque machine
Fichier : /etc/wireguard/wg0.conf (BST-LNX-01)
[Interface]
Address = 10.99.0.1/24
ListenPort = 51820
PrivateKey = <clé privée du bastion>

[Peer]
PublicKey = <clé publique de CLI-LNX-01>
AllowedIPs = 10.99.0.2/32
Fichier : /etc/wireguard/wg0.conf (CLI-LNX-01)
[Interface]
Address = 10.99.0.2/24
PrivateKey = <clé privée de CLI-LNX-01>

[Peer]
PublicKey = <clé publique du bastion>
Endpoint = 10.10.10.30:51820
AllowedIPs = 10.99.0.0/24

Autorisez 51820/udp dans UFW sur le bastion, lancez sudo wg-quick up wg0 des deux côtés, puis sudo wg show et ping 10.99.0.1 depuis CLI-LNX-01. Pouvez-vous ensuite n’autoriser SSH sur le bastion que depuis 10.99.0.0/24 ?

fail2ban sur le bastion

sudo apt install -y fail2ban python3-systemd, puis un fichier /etc/fail2ban/jail.d/sshd.local avec [sshd], enabled = true, backend = systemd, maxretry = 5, bantime = 15m. Attention : toutes les connexions venant du PC par la redirection de ports arrivent avec la même adresse (celle du NAT). Si cette adresse est bannie, le PC n’a plus accès au bastion : ajoutez-la à ignoreip ou testez uniquement depuis CLI-LNX-01.
