TP 4 : Du schéma cloud au lab

Trois exercices qui s'enchaînent : critiquer une architecture cloud mal sécurisée, argumenter un choix entre IaaS et PaaS chiffres à l'appui, puis reproduire dans le lab le principe des sous-réseaux publics et privés et des groupes de sécurité.

Durée2 h 30
Machines virtuellesSRV-LNX-01, CLI-LNX-01
Cours associéSéance 4 : Cloud : lire une architecture IaaS/PaaS
Sommaire
  • Contexte
  • Partie A. Critiquer une architecture (45 min)
  • Partie B. Fiche de choix IaaS ou PaaS (45 min)
  • Partie C. Maquette dans le lab (1 h)
  • Partie D. Dans un vrai cloud (optionnel)
  • Livrables
  • Questions

Contexte

Hexalog veut ouvrir à ses clients une application web de suivi des colis (PHP + base MariaDB). Un prestataire a envoyé une proposition d’architecture et deux devis. Votre responsable vous demande un avis argumenté, puis une maquette dans le lab.

Organisation

  • Partie A : en TD, en binômes, au début de la séance 8 (mardi 13 octobre), avec le cours de la séance 4.
  • Partie B : à la maison ; la fiche de choix est à rendre le vendredi 16 octobre (séance 11).
  • Partie C : en séance 8 (mardi 13 octobre), juste après le TP 3 : Adresses fixes, intranet et redirections, car elle se fait sur SRV-LNX-01 en adresse fixe. Elle est indispensable pour la suite (TP 10, TP 12, évaluation finale).

Partie A. Critiquer une architecture (45 min)

Le prestataire propose le schéma suivant :

Et les règles de groupe de sécurité (identiques pour les deux VM) :

Sens Protocole Port Source
Entrant TCP 22 0.0.0.0/0
Entrant TCP 80 0.0.0.0/0
Entrant TCP 3306 0.0.0.0/0
Entrant TCP 3389 0.0.0.0/0
Sortant tout tout 0.0.0.0/0

Travail demandé :

  1. Décrivez les flux nécessaires au fonctionnement de l’application (qui parle à qui, sur quel port).
  2. Listez au moins cinq problèmes de sécurité ou de disponibilité dans cette proposition.
  3. Proposez une architecture corrigée : schéma (papier, diagrams.net ou Mermaid) et, pour chaque VM, un tableau de règles de groupe de sécurité réduit au strict nécessaire.
  4. Indiquez où placer un bastion et comment l’administrateur (IP fixe 203.0.113.50) se connecte.

Partie B. Fiche de choix IaaS ou PaaS (45 min)

Le prestataire chiffre deux options. Les montants sont des hypothèses de TD, pas des tarifs réels.

Poste mensuel Option IaaS Option PaaS
Hébergement de l’application VM web 2 vCPU / 4 Go : 45 € plateforme d’application web : 60 €
Base de données VM base 2 vCPU / 8 Go : 70 € base MariaDB managée, sauvegardes incluses : 110 €
Disques 2 × 5 € inclus
Adresse IP publique 4 € incluse
Sauvegardes 8 € incluses
Trafic sortant 2 € 2 €
Temps d’administration (45 €/h) 4 h par mois 1 h par mois
Disponibilité annoncée 99,5 % (une VM par rôle) 99,95 %

Travail demandé, sur la fiche de choix (modèle sur la page des modèles) :

  1. Calculez le coût mensuel d’hébergement, puis le coût mensuel complet (avec le temps d’administration) de chaque option.
  2. Calculez le TCO sur 3 ans de chaque option.
  3. Convertissez les deux SLA en durée d’indisponibilité maximale par mois.
  4. Comparez les options sur au moins cinq critères du cours (contrôle, exploitation, compétences, disponibilité, coût, dépendance…).
  5. Rédigez une recommandation argumentée de 10 lignes maximum pour la direction.
  6. Question de réflexion : votre recommandation change-t-elle si l’application a besoin d’un module PHP que la plateforme PaaS ne propose pas ?

Partie C. Maquette dans le lab (1 h)

On reproduit le principe « service public exposé, données privées, administration restreinte » :

C.1, La base de données « privée »

Machine : SRV-LNX-01 (sysadmin)
sudo apt install -y mariadb-server
systemctl status mariadb --no-pager
sudo ss -tlnp | grep 3306

Par défaut, MariaDB n’écoute que sur 127.0.0.1 : elle est joignable par les programmes de la machine, pas par le réseau. C’est l’équivalent d’une base dans un sous-réseau privé. Vérifiez depuis CLI-LNX-01 :

Machine : CLI-LNX-01 (sysadmin)
nc -zv -w 3 10.10.10.20 3306       # doit échouer
nc -zv -w 3 10.10.10.20 80         # doit réussir

C.2, Le « groupe de sécurité » avec UFW

Rédigez d’abord, dans votre journal, la politique souhaitée pour SRV-LNX-01 sous forme de tableau (sens, protocole, port, source, justification) : web ouvert à tous, SSH réservé au réseau du lab, tout le reste refusé. Puis appliquez-la :

Machine : SRV-LNX-01 (sysadmin)
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 80/tcp comment 'intranet public'
sudo ufw allow from 10.10.10.0/24 to any port 22 proto tcp comment 'administration depuis le lab'
sudo ufw enable
sudo ufw status verbose

C.3, Tester la politique

Test Depuis Commande Résultat attendu
Web PC hôte navigateur http://127.0.0.1:8080 page affichée
Web CLI-LNX-01 curl -I http://10.10.10.20 HTTP/1.1 200 OK
SSH CLI-LNX-01 nc -zv 10.10.10.20 22 succeeded
SSH PC hôte ssh -p 2222 sysadmin@127.0.0.1 à tester et expliquer
Base CLI-LNX-01 nc -zv -w 3 10.10.10.20 3306 échec
Port non autorisé CLI-LNX-01 nc -zv -w 3 10.10.10.20 8081 échec (délai dépassé)

Recopiez le tableau dans votre journal avec les résultats obtenus. Pour le test SSH depuis l’hôte, regardez dans sudo journalctl -u ssh -n 5 quelle adresse source voit le serveur et déduisez pourquoi la règle l’autorise ou non.

Observez les paquets refusés par UFW :

Machine : SRV-LNX-01 (sysadmin)
sudo journalctl -k | grep 'UFW BLOCK' | tail -n 5

Faites un snapshot 04-ufw-maquette et mettez à jour l’inventaire (services et ports ouverts).

Partie D. Dans un vrai cloud (optionnel)

Si un compte cloud étudiant est disponible (Azure for Students, AWS Academy, Google Cloud) :

  1. créez une VM Debian du plus petit gabarit, avec votre clé SSH publique (voir Séance 10 : SSH : accès sécurisé par clés ou utilisez ssh-keygen -t ed25519 sur votre PC) ;
  2. restreignez le groupe de sécurité : SSH depuis votre adresse publique uniquement ;
  3. connectez-vous, lancez hostnamectl et ip -br a : que remarquez-vous sur l’adresse de la carte réseau ?
  4. supprimez toutes les ressources créées (VM, disque, adresse IP) et faites une capture de la liste vide.

Les supports AWS et Google Cloud du site détaillent les étapes.

Livrables

  • Partie A : liste des problèmes, schéma corrigé, tableaux de règles par VM.
  • Partie B : fiche de choix complète avec calculs et recommandation.
  • Partie C : politique de filtrage rédigée, ufw status verbose, tableau de tests avec résultats obtenus.

Questions

  1. Dans la maquette, qu’est-ce qui joue le rôle de l’adresse IP publique ? Et du groupe de sécurité ?
  2. Pourquoi est-il préférable qu’une base de données n’écoute pas sur toutes les interfaces, même derrière un pare-feu ?
  3. Quelle est la différence entre un refus immédiat (Connection refused) et un délai dépassé (timed out) lors de vos tests ?
