TP 8 : Distributions et administration de SRV-LNX-01

Deux parties : une enquête en groupe sur une distribution Linux d'entreprise, présentée à l'oral, puis une série de tâches d'administration réelles sur SRV-LNX-01 : paquets, services, journaux, panne de configuration à diagnostiquer et ajout d'un disque de données.

Durée2 h 15 (+ recherche avant la séance)
Machines virtuellesSRV-LNX-01, CLI-LNX-01
Cours associéSéance 8 : Linux : distributions et administration
Sommaire
  • Partie A. Présenter une distribution (recherche avant la séance, 3 minutes d’oral)
  • Partie B. Administrer SRV-LNX-01 (1 h 40)
  • Vérifications
  • Questions
  • Dépannage

Partie A. Présenter une distribution (recherche avant la séance, 3 minutes d’oral)

Consigne

Par groupes de deux ou trois, vous présentez une distribution à la classe comme si vous deviez convaincre (ou dissuader) la DSI d’Hexalog de l’adopter pour ses serveurs. Distributions à répartir :

Debian, Ubuntu Server, Red Hat Enterprise Linux, Rocky Linux, AlmaLinux, SUSE Linux Enterprise Server, Fedora Server, Arch Linux, Alpine Linux

Grille de recherche (à remplir avant la séance 8)

Utilisez les sites officiels des projets et éditeurs, et citez vos sources.

Critère Votre réponse
Origine et organisation (entreprise, fondation, communauté)
Famille et distribution « parente »
Modèle de publication (version fixe, LTS, rolling)
Version actuelle et date de fin de support
Durée totale de support d’une version
Support commercial : existe-t-il, par qui, combien environ ?
Format de paquets et gestionnaire
Gestion du réseau par défaut (ifupdown, Netplan, NetworkManager…)
Système de fichiers par défaut, pare-feu par défaut
Usages typiques et exemples d’utilisateurs
Présence dans le cloud (images officielles AWS, Azure, OVHcloud…)
Certifications professionnelles associées
Points forts / points faibles pour Hexalog
Votre recommandation en une phrase

Présentation (3 minutes par groupe)

Deux ou trois diapositives au maximum, ou la grille projetée. Les autres groupes remplissent un tableau comparatif de toutes les distributions présentées : il sera utile pour l’échange final et pour votre dossier.

Échange final (5 min) : quelle distribution pour les serveurs d’Hexalog ? Et pour un conteneur ? Et pour le poste d’un développeur ?

Partie B. Administrer SRV-LNX-01 (1 h 40)

Avant la partie B

Le TP 3 : Adresses fixes, intranet et redirections doit être terminé (étapes 1 à 6 : adresses fixes, DNS, intranet, redirections web-srv et ssh-srv), puis la partie C du TP 4 : Du schéma cloud au lab. Ils se font au début du bloc pratique de cette séance.

Faites un snapshot 08-avant-admin de SRV-LNX-01. Connectez-vous en SSH depuis l’hôte (ssh -p 2222 sysadmin@127.0.0.1) : c’est plus confortable que la console (copier-coller).

B.1, Se repérer

Machine : SRV-LNX-01 (sysadmin)
cat /etc/os-release ; uname -r ; uptime
ls /etc | head -n 30               # tout est configuration texte
ls /var/log
sudo du -sh /var/log/* | sort -h   # qu'est-ce qui prend de la place ?
df -h /

B.2, Les paquets

Machine : SRV-LNX-01 (sysadmin)
cat /etc/apt/sources.list.d/debian.sources      # les dépôts configurés
sudo apt update
apt list --upgradable
apt show nginx | head -n 15                      # version, dépendances, description
dpkg -L nginx | head -n 20                       # fichiers installés par le paquet
sudo apt install -y htop tree
tail -n 20 /var/log/apt/history.log              # l'historique garde la trace de vos installations

Répondez dans le journal : quelle version de nginx est installée ? De quels paquets dépend-il ? Combien de mises à jour sont en attente ?

Installez les mises à jour de sécurité automatiques et vérifiez leur configuration :

Machine : SRV-LNX-01 (sysadmin)
sudo apt install -y unattended-upgrades
systemctl status unattended-upgrades --no-pager
cat /etc/apt/apt.conf.d/20auto-upgrades

B.3, Les services

Machine : SRV-LNX-01 (sysadmin)
systemctl status nginx --no-pager
systemctl is-enabled nginx ; systemctl is-active nginx
systemctl list-units --type=service --state=running --no-pager
systemctl --failed
systemctl cat nginx                               # comment systemd lance nginx

Arrêtez nginx et observez l’effet depuis CLI-LNX-01 :

Machine : SRV-LNX-01 (sysadmin)
sudo systemctl stop nginx
Machine : CLI-LNX-01 (sysadmin)
curl -I http://srv-lnx-01          # quel message ? à quelle étape du diagnostic correspond-il ?

Puis testez la différence entre stop et disable :

Machine : SRV-LNX-01 (sysadmin)
sudo systemctl start nginx
sudo systemctl disable nginx
sudo reboot
# après redémarrage :
systemctl is-active nginx          # ?
sudo systemctl enable --now nginx

B.4, Les journaux

Ouvrez deux sessions SSH sur SRV-LNX-01. Dans la première :

Machine : SRV-LNX-01 (session 1)
sudo tail -f /var/log/nginx/access.log

Depuis CLI-LNX-01, lancez plusieurs curl http://srv-lnx-01 et curl http://srv-lnx-01/nexiste-pas : observez les lignes qui arrivent (code 200 ou 404). Dans la seconde session :

Machine : SRV-LNX-01 (session 2)
journalctl -u nginx --no-pager
journalctl -p err -b --no-pager
journalctl --since "30 min ago" --no-pager | tail -n 30
journalctl -u ssh -n 10 --no-pager                # vos connexions SSH

B.5, Une panne de configuration

Vous allez provoquer vous-même une erreur, pour apprendre à la lire :

Machine : SRV-LNX-01 (sysadmin)
echo 'server { listen 8081 ' | sudo tee /etc/nginx/conf.d/test.conf
sudo systemctl restart nginx

Le redémarrage échoue. Sans supprimer le fichier tout de suite, diagnostiquez :

Machine : SRV-LNX-01 (sysadmin)
systemctl status nginx --no-pager
journalctl -xeu nginx --no-pager | tail -n 20
sudo nginx -t                                      # test de syntaxe : fichier et ligne en cause

Notez le message exact, le fichier et la ligne signalés, puis corrigez (supprimez test.conf), testez avec sudo nginx -t et redémarrez. Le site est-il de nouveau accessible depuis CLI-LNX-01 ?

Deuxième panne : un conflit de port.

Machine : SRV-LNX-01 (sysadmin)
sudo systemctl stop nginx
sudo python3 -m http.server 80 &                  # un autre programme prend le port 80
sudo systemctl start nginx                        # échec : pourquoi ?
sudo ss -tlnp | grep ':80'                        # qui occupe le port ?

Trouvez le numéro du processus, arrêtez-le (sudo kill NUMERO), puis redémarrez nginx.

B.6, Un disque de données pour /srv/partages

Éteignez SRV-LNX-01, ajoutez un disque VDI dynamique de 5 Go (SRV-LNX-01-DATA) sur le contrôleur SATA, redémarrez.

Machine : SRV-LNX-01 (sysadmin)
lsblk                                              # le nouveau disque : sdb, sans partition
sudo apt install -y parted
sudo parted /dev/sdb --script mklabel gpt mkpart data ext4 0% 100%
lsblk                                              # sdb1 apparaît
sudo mkfs.ext4 -L DATA /dev/sdb1
sudo mkdir -p /srv/partages
sudo blkid /dev/sdb1                               # relevez l'UUID

Vérifiez deux fois le nom du disque

parted et mkfs effacent le disque visé sans demander confirmation. Si vous vous trompez de disque (sda au lieu de sdb), vous effacez le système. Contrôlez avec lsblk : le disque à préparer est celui de 5 Go, sans partition.

Ajoutez la ligne de montage à /etc/fstab (remplacez l’UUID par le vôtre) :

Machine : SRV-LNX-01 (sysadmin)
sudo cp /etc/fstab /etc/fstab.bak
echo 'UUID=VOTRE-UUID  /srv/partages  ext4  defaults,nofail  0  2' | sudo tee -a /etc/fstab
sudo systemctl daemon-reload
sudo mount -a                                      # monte tout ce qui est dans fstab : aucune erreur attendue
df -h /srv/partages
sudo reboot
# après redémarrage :
df -h /srv/partages                                # toujours monté ?

B.7, Bilan et snapshot

Complétez l’inventaire de SRV-LNX-01 : version, services actifs et ports (sudo ss -tulpn), disques et points de montage, mises à jour automatiques. Faites un snapshot 08-admin.

Vérifications

Questions

  1. Quelle différence avez-vous constatée entre systemctl stop et systemctl disable ?
  2. Quel est le rôle de nginx -t ? Connaissez-vous d’autres services qui ont une commande de test équivalente ?
  3. Pourquoi l’option nofail dans /etc/fstab ?
  4. Que se passerait-il au redémarrage si vous aviez fait une faute de frappe dans l’UUID sans nofail ?

Dépannage

Symptôme Piste
mount -a affiche une erreur ligne fstab mal écrite : restaurer fstab.bak, recommencer
Le serveur démarre en emergency mode fstab incorrect sans nofail : saisir le mot de passe de sysadmin, corriger /etc/fstab, reboot
parted : /dev/sdb introuvable disque non ajouté ou VM non redémarrée : lsblk
python3 -m http.server 80 échoue nginx tourne encore : l’arrêter d’abord
apt : « Could not get lock » une autre installation (mises à jour automatiques) est en cours : attendre une minute
