SSH : accès sécurisé par clés, durcissement et transferts

SSH est la porte d'entrée de tous les serveurs Linux, et de plus en plus de serveurs Windows. Cette séance pose d'abord les bases de la cryptographie utilisées par SSH et par HTTPS (clé symétrique, paire de clés, signature, échange de clés), puis montre comment une connexion est protégée, comment le serveur et l'utilisateur prouvent leur identité, comment configurer clients et serveur, transférer des fichiers, durcir le service et prouver qui s'est connecté grâce aux journaux.

1. Ce que fait SSH

SSH (Secure Shell) permet d’ouvrir un terminal sur une machine distante à travers un canal chiffré. Il a remplacé Telnet, qui faisait circuler les mots de passe en clair. Il sert aussi à :

  • transférer des fichiers : scp, sftp, rsync ;
  • créer des tunnels : faire passer une autre connexion (RDP, web, base de données) dans le canal chiffré ;
  • rebondir par un bastion (séance 12) ;
  • automatiser : les outils comme Ansible pilotent les serveurs par SSH.

Le serveur écoute par défaut sur le port TCP 22. L’implémentation standard est OpenSSH : le client ssh et le serveur sshd. Le client OpenSSH est intégré à Windows 10, 11 et Windows Server ; le serveur est disponible comme fonctionnalité de Windows.

2. Client et serveur

Le client est le programme qui ouvre la connexion. Le serveur est le programme qui attend les connexions sur un port.

Client Serveur
Rôle demande la connexion écoute sur un port et répond
SSH ssh, scp, sftp (paquet openssh-client) sshd sur le port 22 (paquet openssh-server)
Web le navigateur, curl nginx sur les ports 80 et 443
Se vérifie avec ps, la commande qu’on vient de taper sudo ss -tlnp : le port est en écoute (LISTEN)

C’est un rôle tenu pour une connexion, pas une catégorie de machine :

  • SRV-LNX-01 est serveur quand vous vous y connectez, mais il devient client s’il lance ssh vers une autre machine ;
  • le reverse proxy de la séance 3 est serveur pour le navigateur et client pour le site interne ;
  • le sens des données ne change pas les rôles : avec scp sysadmin@srv-lnx-01:/etc/os-release . lancé sur CLI-LNX-01, le fichier va du serveur vers CLI-LNX-01, qui reste le client.

Dans le TP 10 :

Connexion Client Serveur
ssh sysadmin@srv-lnx-01 depuis CLI-LNX-01 ssh sur CLI-LNX-01 sshd sur SRV-LNX-01 (10.10.10.20:22)
ssh -p 2222 sysadmin@127.0.0.1 depuis le PC ssh sur le PC sshd sur SRV-LNX-01, atteint par la redirection 2222 → 22
scp sysadmin@srv-lnx-01:/etc/nginx/nginx.conf . scp sur CLI-LNX-01 sshd sur SRV-LNX-01

3. Les briques de la cryptographie

SSH et HTTPS utilisent les mêmes briques. Il faut les distinguer avant de voir comment elles s’assemblent.

Le chiffrement symétrique

Une seule clé secrète sert à chiffrer et à déchiffrer. Les algorithmes actuels sont AES et ChaCha20. Vous en utilisez déjà : une archive 7-Zip protégée par mot de passe, un disque chiffré par BitLocker.

  • Avantage : c’est très rapide. C’est lui qui chiffre toutes les données d’une session SSH ou HTTPS.
  • Problème : les deux côtés doivent posséder la même clé, sans qu’un espion puisse la lire en chemin. La réponse est l’échange de clés, plus bas.

La paire de clés (cryptographie asymétrique)

On génère ensemble deux clés liées mathématiquement (ssh-keygen le fait) :

  • la clé privée est secrète et ne quitte jamais l’appareil où elle a été créée ;
  • la clé publique se calcule à partir de la clé privée et peut être donnée à tout le monde. L’inverse est impossible en pratique : avoir la clé publique ne permet pas de retrouver la clé privée.

On dit « asymétrique » parce que les deux clés sont différentes et n’ont pas le même rôle. La commande ssh-keygen -y -f ~/.ssh/id_ed25519 recalcule la clé publique à partir de la clé privée.

Deux usages différents : chiffrer ou signer

Usage Clé privée Clé publique Ce que cela garantit Exemples
Chiffrement sert à déchiffrer sert à chiffrer un message destiné au propriétaire confidentialité : seul le propriétaire de la clé privée peut lire courriel chiffré (PGP, S/MIME), ancien échange « RSA » de TLS 1.2
Signature sert à signer sert à vérifier la signature authenticité (qui a signé) et intégrité (rien n’a été modifié). Le message reste lisible par tous authentification SSH, certificats HTTPS, dépôts Debian (apt vérifie la signature des listes de paquets)

Une signature fonctionne ainsi :

signature = Signer(clé privée, message)
Vérifier(clé publique, message, signature)  →  valide ou invalide
  • Sans la clé privée, impossible de fabriquer une signature valide.
  • Si un seul caractère du message change, la vérification échoue.
  • Une signature ne vaut que pour ce message : on ne peut pas la recopier sur un autre.

Signer, ce n'est pas « chiffrer avec la clé privée »

On lit souvent cette formule. Elle vient de RSA, où les deux opérations se ressemblent mathématiquement, mais elle est fausse en général. Ed25519, l’algorithme recommandé pour SSH et utilisé dans le TP, sait uniquement signer : on ne peut rien chiffrer avec une clé Ed25519. Dans une connexion SSH avec des clés Ed25519, aucune donnée n’est chiffrée avec une clé publique.

L’empreinte

Une empreinte (hash) est un résumé de taille fixe calculé par une fonction de hachage (SHA-256). Le même contenu donne toujours la même empreinte, et on ne peut pas revenir de l’empreinte au contenu. Vous l’avez vu avec les mots de passe de /etc/shadow (séance 9).

En SSH, l’empreinte d’une clé publique (SHA256:x6k…) sert à comparer deux clés d’un coup d’œil. Ce n’est pas une clé : elle ne permet ni de chiffrer ni de vérifier une signature.

L’échange de clés : obtenir le même secret sans le transmettre

Comment deux machines qui ne se sont jamais parlé obtiennent-elles la même clé symétrique, alors qu’un espion voit tout ce qui passe ? Par un échange de clés Diffie-Hellman :

  1. chaque côté tire au hasard une valeur secrète, qu’il garde ;
  2. chacun en calcule une valeur publique et l’envoie à l’autre ;
  3. chacun combine sa valeur secrète avec la valeur publique reçue : les deux obtiennent le même secret partagé, qui n’a jamais circulé.

L’espion a vu passer les deux valeurs publiques, mais sans l’une des valeurs secrètes il ne peut pas calculer le secret. Les valeurs secrètes sont tirées à chaque connexion puis effacées : l’échange est dit éphémère. Les clés de session (symétriques) sont ensuite calculées à partir du secret partagé.

Analogie : le mélange de peintures

Les deux côtés choisissent publiquement une couleur de base (jaune). Chacun ajoute en secret sa propre couleur (rouge pour l’un, bleu pour l’autre) et envoie le mélange obtenu. Chacun ajoute ensuite sa couleur secrète au mélange reçu : les deux obtiennent la même teinte finale (jaune + rouge + bleu). L’espion a vu passer le jaune, le mélange jaune-rouge et le mélange jaune-bleu, mais on ne sait pas « démélanger » une peinture.

L'échange de clés ne dit pas avec qui on parle

Un attaquant placé au milieu pourrait faire un échange Diffie-Hellman avec le client et un autre avec le serveur, puis relayer en lisant tout. C’est pourquoi le serveur signe l’échange avec sa clé privée (partie 5) : le client vérifie qu’il a bien fait l’échange avec le bon serveur.

Récapitulatif

Élément Ce que c’est Où il se trouve À quoi il sert
Clé de session (symétrique) clé secrète commune, calculée à chaque connexion en mémoire, des deux côtés ; jamais transmise, effacée à la fin chiffrer et protéger les données de la session
Clé privée moitié secrète d’une paire sur l’appareil de son propriétaire, jamais transmise signer (ou déchiffrer, selon l’algorithme)
Clé publique moitié diffusable d’une paire chez tous ceux qui doivent vérifier vérifier une signature (ou chiffrer, selon l’algorithme)
Empreinte résumé SHA-256 d’une clé publique affichée par ssh, ssh-keygen -lf, les journaux comparer deux clés à l’œil ; ce n’est pas une clé
Phrase de passe mot de passe qui protège le fichier de la clé privée connue de l’utilisateur seul déchiffrer localement la clé privée ; jamais envoyée au serveur

4. Les deux paires de clés de SSH

Dans une connexion SSH, chaque côté prouve son identité avec sa propre paire de clés. Les deux paires sont disposées en miroir :

Clé d’hôte Clé utilisateur
Identifie la machine serveur (SRV-LNX-01) une personne sur un appareil (sysadmin@cli-lnx-01, perso-pc)
Créée à l’installation d’openssh-server par l’utilisateur avec ssh-keygen
Clé privée sur le serveur : /etc/ssh/ssh_host_ed25519_key sur le client : ~/.ssh/id_ed25519
Clé publique copiée chez chaque client, dans ~/.ssh/known_hosts copiée sur le serveur, dans ~/.ssh/authorized_keys du compte
Prouve « je suis bien le serveur que tu connais » « je détiens une clé autorisée pour ce compte »
Vérifiée par le client le serveur

Les clés de session, elles, n’appartiennent à personne : elles sont calculées des deux côtés à chaque connexion.

La clé d’hôte et known_hosts

À la première connexion, le client ne connaît pas encore la clé d’hôte du serveur. Il affiche son empreinte et demande de la valider. On la compare avec l’empreinte lue sur le serveur lui-même (par la console, ou dans la documentation d’exploitation) :

Sur le serveur
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub     # empreinte à comparer avec celle affichée par le client

Si l’on répond yes, le client enregistre la clé publique complète du serveur dans ~/.ssh/known_hosts (pas seulement son empreinte). Ce principe s’appelle la confiance à la première utilisation (TOFU, Trust On First Use). Une ligne de known_hosts sous Debian :

Fichier : ~/.ssh/known_hosts
|1|c51TgRF/4M8RgPRlccYkQ8c/rlc=|AHf4+MO72jq5UwG0KDjZi/fh+vg= ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIK73t/jZ…
# nom du serveur, haché                                      algorithme  clé publique du serveur

Le nom du serveur est haché (réglage HashKnownHosts yes de Debian) pour qu’un intrus qui lirait le fichier ne découvre pas la liste des serveurs. Pour retrouver la ligne d’un serveur : ssh-keygen -F srv-lnx-01 (ajouter -l pour afficher son empreinte).

Aux connexions suivantes, le client vérifie que le serveur possède toujours la clé privée correspondant à la clé enregistrée. Si la clé a changé, il affiche un avertissement très visible (REMOTE HOST IDENTIFICATION HAS CHANGED) et refuse de se connecter. Cela arrive légitimement quand un serveur a été réinstallé ou cloné, mais cela peut aussi être une attaque de l’homme du milieu. On ne retire l’ancienne clé (ssh-keygen -R serveur) qu’après avoir vérifié la nouvelle empreinte auprès de l’administrateur du serveur.

5. Déroulement d’une connexion SSH

  1. Négociation. Après la connexion TCP, chaque côté annonce ses versions et les algorithmes qu’il connaît ; ils retiennent les premiers qu’ils ont en commun (ssh -Q kex et ssh -Q cipher listent ceux du client).
  2. Échange de clés. Les deux côtés font un échange Diffie-Hellman éphémère et obtiennent le même secret partagé. Ils calculent aussi l’identifiant de session : l’empreinte de tout ce qui a été échangé (versions, algorithmes, clé d’hôte, valeurs publiques, secret). Il est différent à chaque connexion.
  3. Authentification du serveur. Le serveur signe l’identifiant de session avec sa clé privée d’hôte. Le client vérifie la signature avec la clé publique enregistrée dans known_hosts. Cela prouve que le serveur possède bien la clé privée, et que les valeurs Diffie-Hellman n’ont pas été remplacées en chemin (elles font partie de ce qui est signé).
  4. Clés de session. Les deux côtés calculent, à partir du secret partagé, une clé de chiffrement pour chaque sens (client vers serveur, serveur vers client) et les valeurs qui protègent l’intégrité. Les algorithmes (chacha20-poly1305, aes256-gcm) chiffrent et détectent toute modification en chemin. Les clés sont renouvelées après un certain volume de données.
  5. Authentification de l’utilisateur, dans le canal déjà chiffré : par clé (partie 6) ou par mot de passe.
  6. Session. À la déconnexion, les clés de session sont effacées.

L'idée à retenir

Les clés à long terme (clé d’hôte, clé utilisateur) ne servent qu’à signer, c’est-à-dire à prouver une identité. Ce sont des clés éphémères (les clés de session) qui chiffrent les données. Conséquence : si la clé d’hôte du serveur est volée dans un an, les sessions enregistrées aujourd’hui resteront illisibles. C’est la confidentialité persistante (forward secrecy).

mlkem768x25519-sha256 est l’échange par défaut depuis OpenSSH 10 (la version de Debian 13) : il combine un Diffie-Hellman sur courbe elliptique (X25519) et un algorithme conçu pour résister aussi aux futurs ordinateurs quantiques (ML-KEM). Un client plus ancien, comme celui intégré à Windows, négociera un autre algorithme (sntrup761x25519-sha512 ou curve25519-sha256) : le principe reste le même.

6. L’authentification par clé

Le principe

Le serveur doit vérifier que le client possède la clé privée correspondant à une clé publique de authorized_keys, sans que la clé privée circule. Le client signe donc un message qui contient notamment :

  • l’identifiant de session (partie 5) ;
  • le nom du compte (sysadmin) ;
  • la méthode (publickey) et sa clé publique.

Le serveur vérifie la signature avec la clé publique trouvée dans authorized_keys du compte. Si elle est valide, l’utilisateur est authentifié.

Pourquoi signer l’identifiant de session plutôt qu’un texte fixe ? Parce qu’il change à chaque connexion. Une signature capturée ne peut pas être rejouée sur une autre connexion, et un faux serveur qui recevrait votre signature ne pourrait pas s’en servir auprès du vrai : leurs sessions n’ont pas le même identifiant. Le serveur n’a donc pas besoin d’envoyer un « défi » : l’identifiant de session en tient lieu.

En pratique, cela se fait en deux temps, visibles dans ssh -v et dans le journal du serveur (avec LogLevel VERBOSE, partie 10) :

Côté client (ssh -v) Côté serveur (journal) Ce qui se passe
Offering public key: … SHA256:rgHi… le client demande si cette clé est autorisée, sans signer
Server accepts key: … Postponed publickey for sysadmin … [preauth] la clé est dans authorized_keys ; le serveur attend la signature
Authenticated to … using "publickey". Accepted publickey for sysadmin … ED25519 SHA256:rgHi… le client a envoyé la signature, le serveur l’a vérifiée

Analogie : le spécimen de signature

Le serveur garde votre clé publique comme une banque garde le spécimen de votre signature : il lui sert à vérifier, pas à signer à votre place. À chaque connexion, vous signez un document différent (l’identifiant de session), ce qui empêche de réutiliser une ancienne signature. Limite de l’image : une signature manuscrite peut s’imiter, une signature numérique ne peut être fabriquée qu’avec la clé privée.

Une explication que l'on trouve encore

Dans la première version du protocole (SSH-1, abandonnée depuis longtemps), le serveur chiffrait un défi avec la clé publique RSA de l’utilisateur, qui devait le déchiffrer. Cette explication circule encore dans des documents anciens ; elle ne correspond pas à SSH 2, et elle est impossible avec une clé Ed25519, qui ne sait pas chiffrer.

La phrase de passe et l’agent

La phrase de passe chiffre (en symétrique) le fichier de la clé privée sur le disque. Quand ssh affiche Enter passphrase for key, c’est pour déchiffrer ce fichier sur votre poste : la phrase de passe n’est jamais envoyée au serveur, qui ne la connaît pas. La preuve : ssh-keygen -p change la phrase de passe sans qu’il faille toucher à authorized_keys.

L’agent SSH (ssh-agent) garde la clé privée déchiffrée en mémoire et signe à la place de ssh : la phrase de passe n’est demandée qu’une fois par session de travail.

Pourquoi c’est mieux qu’un mot de passe

Mot de passe Clé
Attaque par essais successifs (force brute) possible, surtout si le mot de passe est faible impossible en pratique
Faux serveur (hameçonnage, empreinte acceptée sans vérifier) le mot de passe est envoyé en entier, dans le canal chiffré, à la machine d’en face : l’imposteur le reçoit la signature ne vaut que pour cette session : l’imposteur ne peut pas la réutiliser sur le vrai serveur
Réutilisation sur plusieurs services fréquente, dangereuse chaque serveur ne connaît que la clé publique
Automatisation (scripts, Ansible) mot de passe à stocker quelque part naturelle
Retrait d’un accès changer le mot de passe partout supprimer une ligne de authorized_keys
Risque principal mot de passe deviné ou volé vol du fichier de clé privée : d’où la phrase de passe

Les algorithmes

  • Ed25519 : recommandé aujourd’hui, clés courtes et rapides. Signature uniquement.
  • RSA : encore très répandu, avec 3072 bits minimum. Sait signer et chiffrer (SSH ne s’en sert que pour signer).
  • ECDSA : courbes elliptiques normalisées par le NIST, accepté mais moins conseillé qu’Ed25519.
  • DSA : obsolète, n’est plus pris en charge par OpenSSH depuis la version 10.

Les fichiers

Fichier Côté Droits Contenu
~/.ssh/id_ed25519 client 600 clé privée de l’utilisateur, chiffrée par la phrase de passe
~/.ssh/id_ed25519.pub client 644 clé publique de l’utilisateur

Mise en place

Machine : poste client
ssh-keygen -t ed25519 -C "sysadmin@cli-lnx-01"      # génère la paire, demande une phrase de passe
ssh-copy-id -i ~/.ssh/id_ed25519.pub sysadmin@srv-lnx-01   # ajoute la clé publique sur le serveur
ssh sysadmin@srv-lnx-01                              # demande la phrase de passe de la clé (locale), pas le mot de passe du compte

ssh-copy-id se connecte une dernière fois avec le mot de passe du compte pour déposer la clé publique. Sous Windows, ssh-copy-id n’existe pas ; on envoie la clé avec une commande PowerShell (voir le TP). Pour ne pas retaper la phrase de passe à chaque connexion, on charge la clé dans l’agent : eval "$(ssh-agent)" puis ssh-add.

7. Et HTTPS ?

HTTPS, c’est HTTP transporté dans TLS (Transport Layer Security), sur le port 443. TLS assemble les mêmes briques que SSH. Avec TLS 1.3, la version actuelle :

  1. Le navigateur (client) envoie ses versions, ses algorithmes, le nom du site demandé (SNI, que le reverse proxy lit à la séance 3) et déjà sa valeur publique Diffie-Hellman.
  2. Le serveur répond avec sa valeur publique : les deux calculent le même secret partagé. La suite de l’échange est déjà chiffrée.
  3. Le serveur envoie son certificat, puis une signature de tout l’échange faite avec la clé privée correspondant au certificat.
  4. Le navigateur vérifie le certificat (signé par une autorité reconnue, au nom du site demandé, en cours de validité), puis la signature avec la clé publique contenue dans le certificat.
  5. Les données HTTP circulent chiffrées avec les clés de session (AES-GCM ou ChaCha20-Poly1305).

Le certificat et la chaîne de confiance

Un certificat contient une clé publique, une identité (les noms de domaine), des dates de validité et la signature d’une autorité de certification (AC). Il ne contient pas la clé privée, qui reste sur le serveur : dans nginx, ssl_certificate désigne le certificat et ssl_certificate_key la clé privée (séance 3).

L’AC qui a signé le certificat du site est elle-même certifiée par une AC racine, déjà présente dans le magasin de confiance du système ou du navigateur : c’est la chaîne de confiance. Le navigateur fait confiance à la clé publique du site parce qu’une autorité qu’il connaît s’en porte garante.

SSH et HTTPS côte à côte

Une explication dépassée

Beaucoup de cours et de vidéos expliquent que « le navigateur chiffre la clé de session avec la clé publique du serveur ». C’était l’échange « RSA », possible jusqu’à TLS 1.2. Il a été supprimé de TLS 1.3 parce qu’il n’offre pas la confidentialité persistante : quiconque obtenait plus tard la clé privée du serveur pouvait déchiffrer tout le trafic enregistré.

Certificat autosigné

Un certificat autosigné n’est garanti par aucune autorité (c’est le cas de Proxmox ou du bureau à distance par défaut). La connexion est bien chiffrée, mais l’identité du serveur n’est pas prouvée : c’est exactement comme répondre yes en SSH sans comparer l’empreinte.

Pour observer une connexion HTTPS depuis une VM du lab (elle sort sur Internet par le réseau NAT) : curl -v -o /dev/null https://deb.debian.org ou openssl s_client -connect deb.debian.org:443 -brief </dev/null. On y lit la version de TLS, les algorithmes négociés, le certificat présenté et le résultat de sa vérification.

8. Le fichier de configuration du client

Plutôt que de retenir ports, utilisateurs et adresses, on déclare des raccourcis dans ~/.ssh/config :

Fichier : ~/.ssh/config (poste client)
Host srv-lnx-01
    HostName 127.0.0.1
    Port 2222
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519

La commande ssh srv-lnx-01 utilise alors automatiquement tous ces paramètres, de même que scp et sftp.

9. Transférer des fichiers

Machine : poste client
scp rapport.txt sysadmin@srv-lnx-01:/tmp/              # envoyer
scp sysadmin@srv-lnx-01:/etc/os-release .               # récupérer (le poste reste le client)
scp -P 2222 rapport.txt sysadmin@127.0.0.1:/tmp/       # port avec un P majuscule pour scp
scp -r dossier/ srv-lnx-01:/tmp/                       # dossier complet (avec un alias du fichier config)
sftp srv-lnx-01                                        # session interactive : ls, cd, put, get, bye

scp et sftp passent par une connexion SSH ordinaire : mêmes clés, même chiffrement, mêmes journaux.

10. Durcir le serveur

Où configurer

Sous Debian, /etc/ssh/sshd_config commence par une ligne Include /etc/ssh/sshd_config.d/*.conf. Pour chaque paramètre, sshd retient la première valeur lue : un fichier placé dans sshd_config.d/ l’emporte donc sur le fichier principal. On y met ses réglages, sans toucher au fichier d’origine (les mises à jour du paquet se passent mieux).

Fichier : /etc/ssh/sshd_config.d/10-durcissement.conf
# Pas de connexion directe en root
PermitRootLogin no
# Clés uniquement
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
# Seuls les membres de ce groupe peuvent se connecter
AllowGroups ssh-users
# Limiter les essais et le temps pour s'authentifier
MaxAuthTries 3
LoginGraceTime 30
# Fonctions inutiles sur un serveur
X11Forwarding no
# Couper les sessions inactives (2 x 300 s)
ClientAliveInterval 300
ClientAliveCountMax 2
# Journaux détaillés (empreinte des clés utilisées)
LogLevel VERBOSE

La procédure sans risque

  1. Vérifier que la connexion par clé fonctionne déjà pour le compte d’administration.
  2. Faire un snapshot (ou avoir une console de secours).
  3. Écrire la configuration, puis la tester : sudo sshd -t (aucune sortie = pas d’erreur).
  4. Garder la session actuelle ouverte, redémarrer le service : sudo systemctl restart ssh.
  5. Ouvrir une nouvelle connexion dans un autre terminal pour vérifier. Seulement ensuite, fermer l’ancienne.
  6. Contrôler la configuration effective : sudo sshd -T | grep -i passwordauthentication.

Et changer le port 22 ?

Mettre SSH sur un autre port réduit le bruit dans les journaux (les robots visent le 22), mais n’apporte pas de sécurité réelle : un scan trouve le nouveau port en quelques secondes. La sécurité vient des clés, du filtrage par pare-feu, de la limitation des comptes autorisés et de la surveillance.

11. Les journaux : prouver qui s’est connecté

Sous Debian, les messages du serveur SSH se lisent avec journalctl -u ssh.

Machine : SRV-LNX-01
sudo journalctl -u ssh --since today --no-pager
sudo journalctl -u ssh -f                                  # en direct
sudo journalctl -u ssh --no-pager | grep -E 'Accepted|Failed|Invalid'
Message Signification
Accepted publickey for sysadmin from 10.10.10.101 port 51234 ssh2: ED25519 SHA256:x6k… connexion réussie par clé ; l’empreinte identifie quelle clé a signé
Postponed publickey for sysadmin from … [preauth] la clé proposée est autorisée, le serveur attend la signature (visible avec LogLevel VERBOSE)
Accepted password for … connexion réussie par mot de passe
Failed password for amartin from … mauvais mot de passe
Invalid user admin from 203.0.113.9 tentative sur un compte qui n’existe pas (typique des robots)
User amartin from … not allowed because none of user's groups are listed in AllowGroups compte refusé par la configuration
Connection closed by authenticating user … [preauth] abandon pendant l’authentification

Pour relier une connexion à une personne, on compare l’empreinte du journal avec celle de la clé publique de chacun : ssh-keygen -lf id_ed25519.pub. D’où l’intérêt d’une clé par personne et par appareil, et jamais de clé partagée.

12. À retenir

Points clés

  • Le client ouvre la connexion (ssh), le serveur écoute (sshd, port 22) ; c’est un rôle par connexion, pas un type de machine.
  • Clé symétrique : une seule clé pour chiffrer et déchiffrer, rapide ; ce sont les clés de session, calculées par un échange Diffie-Hellman et jamais transmises.
  • Paire de clés : la clé privée signe et ne quitte jamais l’appareil ; la clé publique vérifie et se diffuse. Signer n’est pas chiffrer : une signature prouve qui et garantit l’intégrité, elle ne cache rien.
  • Deux paires en miroir : la clé d’hôte prouve l’identité du serveur (sa clé publique est dans known_hosts du client) ; la clé utilisateur prouve celle de l’utilisateur (sa clé publique est dans authorized_keys du serveur).
  • L’authentification par clé est une signature de l’identifiant de session : elle ne se rejoue pas et ne sert à rien à un faux serveur.
  • La phrase de passe déchiffre la clé privée sur le poste ; elle ne part jamais vers le serveur.
  • HTTPS (TLS 1.3) : même mécanique ; la confiance dans la clé du serveur vient d’un certificat signé par une autorité, et non de known_hosts.
  • ssh-keygen -t ed25519, ssh-copy-id, ~/.ssh/config, droits 600/700.
  • Durcissement dans sshd_config.d/ : PermitRootLogin no, PasswordAuthentication no, AllowGroups ; toujours sshd -t et une session de secours ouverte.
  • journalctl -u ssh : Accepted publickey + empreinte = preuve de qui s’est connecté.
