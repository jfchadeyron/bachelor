SSH : accès sécurisé par clés, durcissement et transferts

SSH est la porte d'entrée de tous les serveurs Linux, et de plus en plus de serveurs Windows. Cette séance explique comment la connexion est protégée, pourquoi l'authentification par clé est préférable au mot de passe, comment configurer clients et serveur, transférer des fichiers, durcir le service et prouver qui s'est connecté grâce aux journaux.

1. Ce que fait SSH

SSH (Secure Shell) permet d’ouvrir un terminal sur une machine distante à travers un canal chiffré. Il a remplacé Telnet, qui faisait circuler les mots de passe en clair. Il sert aussi à :

  • transférer des fichiers : scp, sftp, rsync ;
  • créer des tunnels : faire passer une autre connexion (RDP, web, base de données) dans le canal chiffré ;
  • rebondir par un bastion (séance 12) ;
  • automatiser : les outils comme Ansible pilotent les serveurs par SSH.

Le serveur écoute par défaut sur le port TCP 22. L’implémentation standard est OpenSSH : le client ssh et le serveur sshd. Le client OpenSSH est intégré à Windows 10, 11 et Windows Server ; le serveur est disponible comme fonctionnalité de Windows.

2. Déroulement d’une connexion

Deux authentifications se succèdent :

  1. le serveur prouve son identité avec sa clé d’hôte : le client vérifie qu’il parle au bon serveur et pas à un imposteur ;
  2. l’utilisateur prouve son identité, par mot de passe ou par clé.

La clé d’hôte et known_hosts

À la première connexion, le client affiche l’empreinte (fingerprint) de la clé du serveur et demande de la valider. Si on répond yes, elle est enregistrée dans ~/.ssh/known_hosts. Aux connexions suivantes, le client compare : si la clé a changé, il affiche un avertissement très visible (REMOTE HOST IDENTIFICATION HAS CHANGED) et refuse de se connecter.

Cela arrive légitimement quand un serveur a été réinstallé ou cloné. Mais cela peut aussi être une attaque de l’homme du milieu. On ne supprime l’ancienne empreinte (ssh-keygen -R serveur) qu’après avoir vérifié la nouvelle auprès de l’administrateur du serveur :

Sur le serveur
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub     # empreinte à comparer avec celle affichée par le client

3. L’authentification par clé

Le principe

On génère une paire de clés liées mathématiquement :

  • la clé privée reste sur le poste de l’utilisateur, secrète, idéalement protégée par une phrase de passe ;
  • la clé publique peut être diffusée sans risque ; on la dépose sur chaque serveur, dans ~/.ssh/authorized_keys.

À la connexion, le serveur envoie un défi ; le client le signe avec la clé privée ; le serveur vérifie la signature avec la clé publique. La clé privée ne quitte jamais le poste.

Analogie : le cadenas et la clé

Vous fabriquez des cadenas identiques (clé publique) et vous en laissez un sur chaque serveur. Vous gardez la seule clé qui les ouvre (clé privée). N’importe qui peut voir le cadenas, cela ne l’aide pas à l’ouvrir. Si vous perdez la clé, on retire vos cadenas des serveurs.

Pourquoi c’est mieux qu’un mot de passe

Mot de passe Clé
Attaque par essais successifs (force brute) possible, surtout si le mot de passe est faible impossible en pratique
Hameçonnage, saisie sur un faux serveur le mot de passe est donné à l’attaquant la clé privée n’est jamais transmise
Réutilisation sur plusieurs services fréquente, dangereuse chaque serveur ne connaît que la clé publique
Automatisation (scripts, Ansible) mot de passe à stocker quelque part naturelle
Retrait d’un accès changer le mot de passe partout supprimer une ligne de authorized_keys
Risque principal mot de passe deviné ou volé vol du fichier de clé privée : d’où la phrase de passe

Les algorithmes

  • Ed25519 : recommandé aujourd’hui, clés courtes et rapides.
  • RSA : encore très répandu, avec 3072 bits minimum.
  • DSA : obsolète, n’est plus accepté par les versions récentes d’OpenSSH.

Les fichiers

Fichier Côté Droits Rôle
~/.ssh/id_ed25519 client 600 clé privée
~/.ssh/id_ed25519.pub client 644 clé publique
~/.ssh/known_hosts client 644 empreintes des serveurs connus
~/.ssh/config client 600 raccourcis et options de connexion
~/.ssh/authorized_keys serveur 600, dossier ~/.ssh en 700 clés publiques autorisées pour ce compte
/etc/ssh/sshd_config et /etc/ssh/sshd_config.d/*.conf serveur 644 configuration du serveur
/etc/ssh/ssh_host_*_key serveur 600 clés d’hôte du serveur

Si authorized_keys ou le dossier personnel sont modifiables par d’autres utilisateurs, sshd refuse la clé (option StrictModes) : c’est une cause fréquente d’échec.

Mise en place

Machine : poste client
ssh-keygen -t ed25519 -C "sysadmin@cli-lnx-01"      # génère la paire, demande une phrase de passe
ssh-copy-id -i ~/.ssh/id_ed25519.pub sysadmin@srv-lnx-01   # ajoute la clé publique sur le serveur
ssh sysadmin@srv-lnx-01                              # demande la phrase de passe de la clé, pas le mot de passe du compte

Sous Windows, ssh-copy-id n’existe pas ; on envoie la clé avec une commande PowerShell (voir le TP). Pour ne pas retaper la phrase de passe à chaque connexion, on charge la clé dans l’agent SSH : eval "$(ssh-agent)" puis ssh-add.

4. Le fichier de configuration du client

Plutôt que de retenir ports, utilisateurs et adresses, on déclare des raccourcis dans ~/.ssh/config :

Fichier : ~/.ssh/config (poste client)
Host srv-lnx-01
    HostName 127.0.0.1
    Port 2222
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519

La commande ssh srv-lnx-01 utilise alors automatiquement tous ces paramètres, de même que scp et sftp.

5. Transférer des fichiers

Machine : poste client
scp rapport.txt sysadmin@srv-lnx-01:/tmp/              # envoyer
scp sysadmin@srv-lnx-01:/etc/os-release .               # récupérer
scp -P 2222 rapport.txt sysadmin@127.0.0.1:/tmp/       # port avec un P majuscule pour scp
scp -r dossier/ srv-lnx-01:/tmp/                       # dossier complet (avec un alias du fichier config)
sftp srv-lnx-01                                        # session interactive : ls, cd, put, get, bye

6. Durcir le serveur

Où configurer

Sous Debian, /etc/ssh/sshd_config commence par une ligne Include /etc/ssh/sshd_config.d/*.conf. Pour chaque paramètre, sshd retient la première valeur lue : un fichier placé dans sshd_config.d/ l’emporte donc sur le fichier principal. On y met ses réglages, sans toucher au fichier d’origine (les mises à jour du paquet se passent mieux).

Fichier : /etc/ssh/sshd_config.d/10-durcissement.conf
# Pas de connexion directe en root
PermitRootLogin no
# Clés uniquement
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
# Seuls les membres de ce groupe peuvent se connecter
AllowGroups ssh-users
# Limiter les essais et le temps pour s'authentifier
MaxAuthTries 3
LoginGraceTime 30
# Fonctions inutiles sur un serveur
X11Forwarding no
# Couper les sessions inactives (2 x 300 s)
ClientAliveInterval 300
ClientAliveCountMax 2
# Journaux détaillés (empreinte des clés utilisées)
LogLevel VERBOSE

La procédure sans risque

  1. Vérifier que la connexion par clé fonctionne déjà pour le compte d’administration.
  2. Faire un snapshot (ou avoir une console de secours).
  3. Écrire la configuration, puis la tester : sudo sshd -t (aucune sortie = pas d’erreur).
  4. Garder la session actuelle ouverte, redémarrer le service : sudo systemctl restart ssh.
  5. Ouvrir une nouvelle connexion dans un autre terminal pour vérifier. Seulement ensuite, fermer l’ancienne.
  6. Contrôler la configuration effective : sudo sshd -T | grep -i passwordauthentication.

Et changer le port 22 ?

Mettre SSH sur un autre port réduit le bruit dans les journaux (les robots visent le 22), mais n’apporte pas de sécurité réelle : un scan trouve le nouveau port en quelques secondes. La sécurité vient des clés, du filtrage par pare-feu, de la limitation des comptes autorisés et de la surveillance.

7. Les journaux : prouver qui s’est connecté

Sous Debian, les messages du serveur SSH se lisent avec journalctl -u ssh.

Machine : SRV-LNX-01
sudo journalctl -u ssh --since today --no-pager
sudo journalctl -u ssh -f                                  # en direct
sudo journalctl -u ssh --no-pager | grep -E 'Accepted|Failed|Invalid'
Message Signification
Accepted publickey for sysadmin from 10.10.10.101 port 51234 ssh2: ED25519 SHA256:x6k… connexion réussie par clé ; l’empreinte identifie quelle clé a été utilisée
Accepted password for … connexion réussie par mot de passe
Failed password for amartin from … mauvais mot de passe
Invalid user admin from 203.0.113.9 tentative sur un compte qui n’existe pas (typique des robots)
User amartin from … not allowed because none of user's groups are listed in AllowGroups compte refusé par la configuration
Connection closed by authenticating user … [preauth] abandon pendant l’authentification

Pour relier une connexion à une personne, on compare l’empreinte du journal avec celle de la clé publique de chacun : ssh-keygen -lf id_ed25519.pub. D’où l’intérêt d’une clé par personne et jamais de clé partagée.

8. À retenir

Points clés

  • SSH : shell distant chiffré, port 22, transferts (scp, sftp), tunnels.
  • La clé d’hôte authentifie le serveur (known_hosts) ; un changement d’empreinte se vérifie avant d’être accepté.
  • Clé privée secrète sur le poste, protégée par une phrase de passe ; clé publique dans authorized_keys sur le serveur.
  • ssh-keygen -t ed25519, ssh-copy-id, ~/.ssh/config, droits 600/700.
  • Durcissement dans sshd_config.d/ : PermitRootLogin no, PasswordAuthentication no, AllowGroups ; toujours sshd -t et une session de secours ouverte.
  • journalctl -u ssh : Accepted publickey + empreinte = preuve de qui s’est connecté.

  4. Un collègue vous demande votre clé privée pour se connecter à votre place. Que répondez-vous ?

  7. Pourquoi placer ses réglages dans /etc/ssh/sshd_config.d/ plutôt que dans sshd_config ?
  8. Quelle commande teste la configuration du serveur SSH avant de le redémarrer ?
  9. Que faut-il absolument garder ouvert quand on désactive l’authentification par mot de passe ?
  10. Quelle ligne de journal prouve qu’un administrateur s’est connecté avec sa clé ?
Voir la correction
  1. Le serveur s’authentifie avec sa clé d’hôte ; l’utilisateur s’authentifie par clé ou mot de passe.
  2. Les empreintes des serveurs déjà acceptés ; côté client, ~/.ssh/known_hosts.
  3. Les clés publiques autorisées à se connecter à ce compte ; côté serveur, ~/.ssh/authorized_keys du compte.
  4. Non : chacun sa clé. On ajoute sa clé publique à lui dans authorized_keys.
  5. Si le fichier est volé, il est inutilisable sans la phrase de passe.
  6. Résistance à la force brute, pas de secret transmis au serveur, retrait facile, automatisation.
  7. Les fichiers inclus sont lus en premier et l’emportent ; le fichier d’origine reste intact pour les mises à jour.
  8. sudo sshd -t.
  9. Une session SSH déjà ouverte (ou une console), pour pouvoir corriger en cas d’erreur.
  10. Accepted publickey for <compte> from <IP> … ssh2: ED25519 SHA256:<empreinte>.
