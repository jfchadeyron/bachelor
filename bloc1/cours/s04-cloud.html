Cloud : lire une architecture IaaS et PaaS

Un schéma d'architecture cloud n'est qu'une infrastructure classique dessinée avec d'autres mots : réseaux virtuels, sous-réseaux, groupes de sécurité, adresses publiques. Cette séance vous apprend à le lire, à le relier à ce que vous avez construit dans VirtualBox et à argumenter un choix entre IaaS et PaaS.

1. Les briques d’une architecture IaaS

Région et zone de disponibilité

Un fournisseur cloud possède des datacenters regroupés en régions (Paris, Francfort, Irlande…). Chaque région contient plusieurs zones de disponibilité : des datacenters distincts, avec leur propre alimentation et leur propre réseau, reliés entre eux par des liens rapides. Répartir ses VM sur deux zones protège contre la panne d’un datacenter entier.

On choisit la région selon la latence (proche des utilisateurs), la réglementation (données en France ou dans l’Union européenne) et le prix (il varie d’une région à l’autre).

Réseau virtuel et sous-réseaux

Le réseau virtuel (VPC chez AWS et Google, VNet chez Azure) est un réseau privé isolé, dans lequel on choisit sa plage d’adresses (par exemple 10.0.0.0/16). On le découpe en sous-réseaux :

  • sous-réseau public : ses machines peuvent recevoir une adresse IP publique et être jointes depuis Internet (serveur web, bastion) ;
  • sous-réseau privé : ses machines n’ont pas d’adresse publique ; elles sortent éventuellement sur Internet par une passerelle NAT, mais personne ne peut les joindre de l’extérieur (bases de données, serveurs applicatifs).

Les autres briques

Brique Rôle

2. Lire un schéma d’architecture

Voici l’architecture qu’un prestataire propose à Hexalog pour son application de suivi des colis, en IaaS :

Pour lire un schéma, posez-vous toujours les mêmes questions :

  1. Qui entre, par où ? Les clients arrivent en HTTPS sur le répartiteur, l’administrateur en SSH sur le bastion. Rien d’autre n’est exposé.
  2. Quels flux internes ? Répartiteur vers web (port 80), web vers base (port 3306), bastion vers tout le monde (port 22).
  3. Qu’est-ce qui est isolé ? Les VM web et la base sont dans le sous-réseau privé, sans adresse publique.
  4. Où sont les points uniques de défaillance ? Deux VM web : la perte de l’une n’arrête pas le service. Une seule base : si elle tombe, tout s’arrête.
  5. Comment sortent-elles pour leurs mises à jour ? Par la passerelle NAT.

3. Les groupes de sécurité

Un groupe de sécurité est une liste de règles qui autorisent des flux. Tout ce qui n’est pas autorisé est bloqué. Il est stateful : si une connexion entrante est autorisée, la réponse sort automatiquement, sans règle supplémentaire.

Groupe de sécurité de la base de données :

Sens Protocole Port Source Commentaire
Entrant TCP 3306 groupe « web » seules les VM web interrogent la base
Entrant TCP 22 groupe « bastion » administration uniquement via le bastion
Sortant tout tout 0.0.0.0/0 par défaut, sorties autorisées

La source peut être une adresse, une plage (10.0.1.0/24), tout Internet (0.0.0.0/0) ou un autre groupe de sécurité, ce qui évite de manipuler des adresses qui changent.

Vous avez déjà écrit ce genre de table : les règles de filtrage de l’exemple du reverse proxy (séance 3, partie 7) jouent exactement le rôle d’un groupe de sécurité, avec les mêmes colonnes (source, destination, protocole et port, action).

L'erreur la plus fréquente

Une règle « TCP 22 (SSH) ou 3389 (RDP) depuis 0.0.0.0/0 » expose l’administration de la VM au monde entier. Des robots scannent Internet en permanence et tentent des milliers de mots de passe dans l’heure qui suit la création d’une VM. On restreint toujours l’administration à une adresse connue ou on passe par un bastion.

Le groupe de sécurité n’empêche pas d’activer aussi le pare-feu du système (UFW sous Linux, pare-feu Windows) : c’est la défense en profondeur. Si une couche est mal configurée, l’autre protège encore.

Premier contact avec UFW

UFW (Uncomplicated Firewall) est l’outil le plus simple pour gérer le pare-feu d’un serveur Debian ou Ubuntu. Il sera approfondi aux séances 10 et 12.

Machine : SRV-LNX-01 (sysadmin)
sudo apt install -y ufw
sudo ufw default deny incoming                              # tout refuser en entrée par défaut
sudo ufw default allow outgoing                             # autoriser les sorties
sudo ufw allow 80/tcp                                       # web ouvert à tous
sudo ufw allow from 10.10.10.0/24 to any port 22 proto tcp  # SSH depuis le réseau du lab seulement
sudo ufw enable
sudo ufw status numbered

Toujours autoriser SSH avant ufw enable quand on est connecté à distance, sinon on se coupe l’accès.

5. IaaS ou PaaS : comment choisir

Les critères

Critère IaaS PaaS
Contrôle total sur le système, les versions, les réglages limité aux options proposées
Exploitation mises à jour du système, sauvegardes, supervision à votre charge assurées par le fournisseur
Compétences administration système nécessaire surtout développement et paramétrage
Disponibilité à construire (plusieurs VM, répartiteur, réplication) souvent incluse ou activable (option haute disponibilité)
Coût affiché souvent plus bas souvent plus élevé
Coût complet (TCO) temps d’administration à ajouter temps d’administration réduit
Portabilité une VM Debian se déplace facilement dépendance plus forte au fournisseur (lock-in)
Cas typique logiciel avec besoins particuliers, migration d’un serveur existant (lift and shift) application web standard, base de données classique

Le SLA

Le SLA (Service Level Agreement) est l’engagement de disponibilité du fournisseur, avec des pénalités s’il n’est pas tenu. Pour un mois de 30 jours (43 200 minutes) :

SLA Indisponibilité maximale par mois
99 % 7 h 12 min
99,9 % 43 min
99,95 % 21 min 36 s
99,99 % 4 min 19 s

Le SLA d’une VM IaaS isolée est souvent plus faible que celui d’un service PaaS avec haute disponibilité. Pour atteindre le même niveau en IaaS, il faut plusieurs VM dans plusieurs zones.

Les coûts du cloud

  • À la demande : payé à la seconde ou à l’heure, sans engagement. Le plus cher à l’heure, le plus souple.
  • Engagement (instances réservées, plans d’économie) : 1 à 3 ans d’engagement contre une remise importante.
  • Capacité excédentaire (spot) : très bon marché, mais la VM peut être arrêtée à tout moment.

Ce qui est facturé : le temps de calcul, le stockage (Go par mois, y compris les snapshots), le trafic sortant, les adresses IP publiques, les services managés. Les pièges classiques : une VM de test oubliée, des snapshots jamais supprimés, des disques orphelins après suppression d’une VM. Les fournisseurs proposent des calculateurs de prix, des alertes de budget et des étiquettes (tags) pour savoir qui consomme quoi.

6. Se connecter à une VM cloud

  • Linux : pas de mot de passe. À la création, on fournit une clé SSH publique que le fournisseur injecte dans la VM (outil cloud-init). On se connecte avec l’utilisateur prévu par l’image (debian, ubuntu, ec2-user, azureuser…) et sa clé privée : ssh -i ma-cle debian@IP-publique.
  • Windows : connexion RDP avec le compte administrateur défini à la création (ou dont le mot de passe est récupéré sur la console).
  • Bonnes pratiques : n’ouvrir SSH ou RDP que depuis son adresse, ou passer par un bastion ; certains fournisseurs proposent un bastion managé (Azure Bastion) ou un accès sans port ouvert (AWS Systems Manager Session Manager).
  • Toujours supprimer ce qu’on a créé pour un test : VM, disques, adresses IP, snapshots.

7. À retenir

Points clés

  • Région et zones de disponibilité, réseau virtuel, sous-réseaux publics et privés, passerelle NAT, groupes de sécurité, adresses publiques, bastion, répartiteur de charge.
  • Un groupe de sécurité est un pare-feu stateful : on n’autorise que les flux nécessaires, jamais SSH ou RDP depuis 0.0.0.0/0.
  • Chaque brique cloud a un équivalent dans le lab : le lab est un petit cloud privé.
  • IaaS = plus de contrôle, plus d’exploitation. PaaS = moins d’exploitation, plus de dépendance. On compare avec le TCO, pas avec le prix affiché.
  • 99,9 % de disponibilité autorise environ 43 minutes de panne par mois.

Voir la correction
  1. Une région est une zone géographique ; elle contient plusieurs zones de disponibilité, qui sont des datacenters indépendants.
  2. Pour qu’elle ne soit pas joignable depuis Internet : seules les VM autorisées du réseau virtuel peuvent l’interroger.
  3. Par une passerelle NAT : elle sort sur Internet sans pouvoir être jointe de l’extérieur.
  4. Il suit les connexions : la réponse à une connexion autorisée est automatiquement autorisée.
  5. Le bureau à distance est ouvert au monde entier : risque d’attaques par mot de passe. Il faut limiter la source ou passer par un bastion.
  6. Une redirection de ports sur le réseau NAT (port de l’hôte vers la VM).
  7. Environ 43 minutes (0,1 % de 43 200 minutes).
  8. Le trafic sortant, les snapshots, les disques orphelins, les adresses IP publiques, une VM oubliée allumée.
  9. IaaS : contrôle total, portabilité, besoins particuliers possibles. PaaS : moins d’exploitation, sauvegardes et haute disponibilité incluses.
  10. En SSH avec une clé : la clé publique est injectée à la création, on utilise l’utilisateur de l’image et sa clé privée.
