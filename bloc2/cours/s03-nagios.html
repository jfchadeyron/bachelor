Nagios Core : hôtes, services, états

Nagios est l'ancêtre des outils de supervision libres : la plupart des outils actuels en reprennent les plugins et la logique des états. Un ordonnanceur qui lance des plugins, des objets décrits en fichiers texte, des états SOFT et HARD contre les fausses alertes, un agent pour voir l'intérieur des machines, des notifications.

1. Nagios en quelques mots

Nagios Core est libre (GPL) depuis 1999 ; Icinga, Naemon, Centreon et Checkmk en descendent. Debian 13 fournit Nagios Core 4.4 (paquet nagios4). Le principe : un ordonnanceur lance des plugins à intervalles réguliers, retient les états, prévient les bonnes personnes, et une interface web affiche le tout.

Nagios Core seul n’a ni base de données, ni graphiques, ni découverte automatique, ni configuration par l’interface : tout s’écrit dans des fichiers texte.

2. Les objets

Objet Rôle
host, hostgroup une machine ; un groupe de machines
service un contrôle sur un hôte
command la ligne de commande d’un plugin
contact, contactgroup qui prévenir, et comment
timeperiod des plages horaires (24x7, workhours)
ExempleFichier : /etc/nagios4/conf.d/exemple.cfgà lire, pas à taper
define command {
    command_name    hx-http-page
    command_line    $USER1$/check_http -I $HOSTADDRESS$ -u $ARG1$ -s $ARG2$
}

define host {
    use             hexalog-hote          ; hérite d'un modèle
    host_name       srv-lnx-01
    address         10.20.N.20
}

define service {
    use                     hexalog-service
    host_name               srv-lnx-01
    service_description     Intranet - accueil
    check_command           hx-http-page!/!Hexalog
}
  • Ce qui suit chaque ! devient $ARG1$, $ARG2$… ; $HOSTADDRESS$ est remplacé par l’adresse de l’hôte ; $USER1$ (le chemin des plugins) et les valeurs privées sont dans resource.cfg.
  • use fait hériter d’un modèle (register 0 : non supervisé, il porte les réglages communs).
  • Vos fichiers vont dans /etc/nagios4/conf.d/. Après chaque modification : vérifier (sudo nagios4 -v /etc/nagios4/nagios.cfg), puis recharger (sudo systemctl reload nagios4).

Deux pièges fréquents

  • Pas d’apostrophe ni de parenthèses dans un nom : Intranet - page d'accueil est refusé.
  • Pas deux commandes du même nom : check_http existe déjà chez Debian. D’où le préfixe hx-.

3. Les contrôles et les états

Objet États
Hôte UP, DOWN, UNREACHABLE (un équipement intermédiaire est en panne)
Service OK, WARNING, CRITICAL, UNKNOWN ; PENDING avant le premier contrôle

SOFT et HARD

Un seul échec peut être fugace : Nagios reteste avant d’alerter.

Directive Rôle Dans hexalog-service
check_interval intervalle quand tout va bien (min) 2
retry_interval intervalle des nouveaux essais 1
max_check_attempts échecs pour confirmer 3

Seul l’état HARD déclenche une notification. Délai maximal de détection ≈ check_interval + (max_check_attempts − 1) × retry_interval = 2 + 2 × 1 = 4 minutes (14 minutes avec les valeurs de Debian). C’est un compromis entre rapidité et fausses alertes, qui pèse directement sur le MTTD.

Moins de bruit : déclarer un commutateur comme parents des serveurs qui sont derrière le fait passer seul en DOWN, eux en UNREACHABLE, avec une seule alerte ; une servicedependency évite deux alertes pour une cause (MariaDB, puis l’intranet) ; un service qui change d’état sans arrêt est instable (flapping), et Nagios suspend ses notifications.

4. Voir l’intérieur des machines : NRPE et NCPA

Les plugins tournent sur le serveur Nagios : pour le disque ou la charge d’une autre machine, il faut un agent.

  • NRPE écoute sur 5666, n’accepte que les adresses de allowed_hosts, et n’exécute que des commandes prédéfinies (command[hx_disque_racine]=…). Avec dont_blame_nrpe=0, Nagios ne peut pas lui passer d’arguments : moins souple, beaucoup plus sûr.
  • Sous Windows, NCPA : une API HTTPS (5693) protégée par un jeton, interrogée par check_ncpa.py.

5. Notifications et interface

  • On rattache les services à un groupe de contacts (une équipe), pas à des personnes. notification_options dit pour quels états prévenir (w, c, u, r rétablissement…), notification_interval règle les relances.
  • Acquitter : « je m’en occupe » ; les relances s’arrêtent jusqu’au retour à OK.
  • Planifier un arrêt (downtime) : une maintenance annoncée à l’avance, sans alerte.
  • Dans le lab, Postfix remet les courriels localement, dans la boîte de sysadmin sur sup-lnx-01.

Dans l’interface : Tactical Overview (vue d’ensemble), Problems / Unhandled (l’écran de l’astreinte), Event Log (historique), Availability (rapports).

Le réglage par défaut de Debian

L’interface de Nagios est livrée sans authentification (use_authentication=0) : quiconque l’atteint lit toute la configuration et peut acquitter des alertes. Le TP l’active dès l’installation.

6. Forces et limites

Forces Limites
simple, robuste, léger configuration à la main, fastidieuse au-delà de quelques dizaines d’hôtes
des milliers de plugins pas de graphiques ni d’historique sans module
configuration texte, versionnable pas de découverte automatique, interface datée

Ces limites expliquent le succès de Centreon, Icinga, Checkmk, et de Zabbix, qui stocke ses mesures dans une base et se configure par l’interface web (séances 4 et 5).

7. À retenir

Points clés

  • Un ordonnanceur lance des plugins, retient des états, notifie ; configuration en fichiers texte.
  • Objets host, service, command, contact ; modèles (use, register 0) ; macros $HOSTADDRESS$, $ARGn$, $USERn$.
  • Toujours nagios4 -v avant systemctl reload nagios4.
  • SOFT puis HARD : délai de détection = check_interval + (max − 1) × retry_interval.
  • Parents → UNREACHABLE ; dépendances ; battement.
  • NRPE : 5666, allowed_hosts, commandes prédéfinies ; NCPA pour Windows.
  • Acquitter ≠ planifier un arrêt ; activer l’authentification de l’interface.

Quiz

  1. Qu’est-ce qui, dans Nagios, lance réellement les tests ?
  2. Dans check_command hx-tcp!389, que vaut $ARG1$ ?
  3. À quoi sert register 0 ?
  4. Pourquoi service_description Intranet (accueil) est-il refusé ?
  5. Un service a check_interval 5, retry_interval 1, max_check_attempts 4. Combien de temps au maximum entre le début d’une panne et la notification ?
  6. Qu’est-ce qui distingue un état SOFT d’un état HARD ? Lequel déclenche une notification ?
  7. Le commutateur d’un étage tombe. Que voit-on dans Nagios pour les serveurs situés derrière, si les parents sont déclarés ? Et s’ils ne le sont pas ?
  8. Pourquoi NRPE refuse-t-il, par défaut, que Nagios lui envoie les seuils d’un contrôle ?
  9. Quelle différence entre acquitter un problème et planifier un arrêt ?
  10. Quel risque présente l’interface de Nagios telle que Debian l’installe ?
Voir la correction
  1. L’ordonnanceur (le démon nagios4) lance les plugins ; ce sont eux qui testent.
  2. 389.
  3. À définir un modèle : l’objet n’est pas supervisé, il sert seulement à être hérité par use.
  4. Les parenthèses font partie des caractères interdits dans les noms d’objets.
  5. 5 + (4 − 1) × 1 = 8 minutes.
  6. SOFT : le problème n’est pas encore confirmé, Nagios reteste ; HARD : confirmé après max_check_attempts échecs. Seul l’état HARD déclenche la notification.
  7. Avec les parents : le commutateur DOWN, les serveurs UNREACHABLE, une seule alerte. Sans : tous les serveurs DOWN et une alerte par serveur.
  8. Pour que personne, même en se faisant passer pour Nagios, ne puisse faire exécuter des commandes arbitraires à l’agent (dont_blame_nrpe=0).
  9. Acquitter : un problème déjà là est pris en charge. Planifier un arrêt : on annonce à l’avance une maintenance pendant laquelle Nagios n’alertera pas.
  10. Aucune authentification : toute personne qui atteint la page (depuis une adresse privée) lit la configuration et peut agir sur les alertes.
