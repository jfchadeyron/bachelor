TP 10 : Sauvegarder Hexalog et prouver la restauration

Vous sauvegardez les VM d'Hexalog dans Proxmox Backup Server, vous mettez en place une sauvegarde applicative horaire de la base de l'intranet et une copie tirée, en lecture seule, sur une autre machine, vous supervisez le tout dans Zabbix. Puis vous restaurez trois fois : un fichier, une table, une VM entière, en chronométrant. Le rapport de test de restauration servira de base au PRA.

Durée3 h 30

Contexte

Hexalog n’a jamais restauré quoi que ce soit : « les sauvegardes, c’est Nicolas qui s’en occupe, ça marche ». L’assureur de l’entreprise demande désormais la preuve que les données peuvent être restaurées, et en combien de temps.

Organisation

Socle : parties A à F (F.1 à F.3 au minimum), G et I ; la partie D (copie tirée) sert à l’exercice de la séance 11. Facultatif : partie H (Windows Server).

La partie G se lance en arrière-plan dès la partie B : les sauvegardes des autres VM tournent pendant que vous continuez.

Ce que vous construisez

Partie A. Avant de commencer (10 min)

  1. Dans Proxmox, sélectionnez chaque VM → Snapshots : supprimez les snapshots devenus inutiles des séances précédentes (gardez le plus récent de chaque VM). Combien d’espace occupaient-ils, et où ?
  2. Vérifiez que le stockage pbs-etuN apparaît sous le nœud (icône de sauvegarde) et ouvrez-le : onglet Sauvegardes, vide pour l’instant.
  3. Notez dans votre journal la réponse à la question : si le disque du serveur Proxmox lâchait cette nuit, que resterait-il de vos snapshots ?

Partie B. Sauvegarder srv-lnx-01 dans Proxmox Backup Server (25 min)

B.1, La première sauvegarde

srv-lnx-01 → Sauvegarde → Sauvegarder maintenant (Backup now) :

Champ Valeur
Stockage pbs-etuN
Mode Snapshot (la VM continue de tourner)
Notes {{guestname}}, TP 10, première sauvegarde

Cliquez sur Sauvegarder et gardez ouverte la fenêtre de la tâche. Relevez dans le journal de la tâche :

  • les lignes fs-freeze et fs-thaw : l’agent invité fige les systèmes de fichiers (cours, partie 5) ;
  • la ligne dirty-bitmap status : created new pour une première sauvegarde ;
  • la quantité transférée et la durée totale (Finished Backup of VM … (hh:mm:ss)) ;
  • la part réutilisée (reused) : les blocs que le serveur avait déjà, par exemple ceux du modèle, sauvegardés par un camarade.

B.2, La deuxième, tout de suite après

Modifiez quelque chose sur srv-lnx-01 (sudo apt install -y tree), puis relancez une sauvegarde identique (notes : deuxième sauvegarde). Comparez avec la première : ligne dirty-bitmap, quantité lue et transférée, durée. Expliquez la différence dans votre journal.

B.3, Ce que contient le stockage

pbs-etuN → Sauvegardes : deux sauvegardes de la VM N20. Pour chacune : date, taille affichée, état de vérification, notes. La taille affichée est celle de la VM ; ce qui est réellement occupé sur le serveur est bien plus faible (déduplication). Lequel des deux chiffres sert à prévoir la durée d’une restauration ?

Partie C. L’activité de l’intranet et sa sauvegarde applicative (35 min)

C.1, Une activité simulée

Pour mesurer ce qu’une restauration fait perdre, l’intranet doit vivre : un petit programme saisit une expédition toutes les 5 minutes, avec son heure de création.

Machine : srv-lnx-01 (sysadmin)
curl -fsSLO https://jfchadeyron.github.io/bachelor/bloc2/fichiers/activite-intranet.sh
less activite-intranet.sh
sudo bash activite-intranet.sh

Résultat attendu : les trois expéditions les plus récentes, dont une EXP-AAMMJJ-hhmm qui vient d’être créée. sudo bash activite-intranet.sh etat affiche à tout moment les dernières saisies.

C.2, Le script de sauvegarde de la base

Machine : srv-lnx-01 (sysadmin)
sudo tee /usr/local/sbin/sauvegarde-intranet > /dev/null <<'EOF'
#!/bin/bash
# Sauvegarde cohérente de la base de l'intranet d'Hexalog (TP 10)
set -euo pipefail
DEST=/var/backups/intranet                  # dossier des sauvegardes
JOURS=2                                     # durée de conservation ici, en jours
ETAT=/var/lib/hexalog/sauvegarde-intranet.ok

mkdir -p "$DEST" "$(dirname "$ETAT")"
chmod 750 "$DEST"
if getent group copie > /dev/null ; then chgrp copie "$DEST" ; fi   # lecture par la copie (partie D)
FICHIER="$DEST/intranet-$(date +%Y%m%d-%H%M).sql.gz"

# --single-transaction : une image cohérente de la base, sans bloquer l'intranet
mariadb-dump --single-transaction --routines --triggers intranet | gzip > "$FICHIER.partiel"
gzip -t "$FICHIER.partiel"                  # l'archive est-elle lisible ?
mv "$FICHIER.partiel" "$FICHIER"

# rotation : les sauvegardes de plus de JOURS jours sont supprimées
find "$DEST" -maxdepth 1 -name 'intranet-*.sql.gz' -mtime +"$JOURS" -delete

touch "$ETAT"                               # date de la dernière réussite (supervisée par Zabbix)
echo "Sauvegarde réussie : $FICHIER ($(du -h "$FICHIER" | cut -f1))"
EOF
sudo chmod 750 /usr/local/sbin/sauvegarde-intranet
sudo /usr/local/sbin/sauvegarde-intranet
sudo ls -l /var/backups/intranet/
sudo sh -c 'zcat /var/backups/intranet/intranet-*.sql.gz | grep -c "^INSERT INTO"'

Lisez le script ligne par ligne et répondez dans votre journal : pourquoi écrire d’abord un fichier .partiel ? Que se passe-t-il si mariadb-dump échoue (pensez à set -euo pipefail) ? Le fichier témoin est-il mis à jour dans ce cas ?

Le dossier n’est lisible que par root : d’où le sudo sh -c '…', pour que le * soit développé avec les droits de root. L’export ne contient pas de CREATE DATABASE : on choisira la base de destination au moment de la restauration (partie F.2), ce qui évite d’écraser la production par erreur.

C.3, Toutes les heures

Machine : srv-lnx-01 (sysadmin)
sudo tee /etc/systemd/system/sauvegarde-intranet.service > /dev/null <<'EOF'
[Unit]
Description=Hexalog : sauvegarde de la base de l'intranet
After=mariadb.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/sauvegarde-intranet
EOF
sudo tee /etc/systemd/system/sauvegarde-intranet.timer > /dev/null <<'EOF'
[Unit]
Description=Hexalog : sauvegarde horaire de la base de l'intranet

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now sauvegarde-intranet.timer
systemctl list-timers 'sauvegarde-*' --no-pager

Persistent=true : si la VM était éteinte à l’heure prévue, la sauvegarde est faite au démarrage. Le résultat de chaque exécution est dans journalctl -u sauvegarde-intranet.

Partie D. Une copie tirée par sup-lnx-01, en lecture seule (30 min)

Les exports de la base sont sur srv-lnx-01 : si la VM est perdue ou chiffrée, ils le sont aussi. sup-lnx-01 vient donc en chercher une copie chaque heure, avec un compte qui ne peut que lire ce dossier (cours, partie 9).

D.1, Sur srv-lnx-01 : un compte limité à la lecture du dossier

Machine : srv-lnx-01 (sysadmin)
sudo apt install -y rsync
sudo useradd -m -s /bin/bash copie
sudo /usr/local/sbin/sauvegarde-intranet
sudo ls -ld /var/backups/intranet

Le dossier appartient désormais au groupe copie, en lecture seule (drwxr-x---).

D.2, Sur sup-lnx-01 : la clé de la copie

Machine : sup-lnx-01 (sysadmin)
sudo apt install -y rsync
sudo ssh-keygen -t ed25519 -N '' -C copie@sup-lnx-01 -f /root/.ssh/copie-srv-lnx-01
sudo cat /root/.ssh/copie-srv-lnx-01.pub

La clé n’a pas de phrase de passe, puisqu’aucun humain ne sera là pour la taper : c’est pour cela qu’on la limite strictement côté srv-lnx-01.

D.3, Sur srv-lnx-01 : n’autoriser que la lecture par rsync

Copiez la ligne ssh-ed25519 AAAA… copie@sup-lnx-01 affichée en D.2 à la place de CLE-PUBLIQUE :

Machine : srv-lnx-01 (sysadmin)
sudo mkdir -p /home/copie/.ssh
echo 'command="/usr/bin/rrsync -ro /var/backups/intranet",restrict CLE-PUBLIQUE' | sudo tee /home/copie/.ssh/authorized_keys
sudo chown -R copie:copie /home/copie/.ssh
sudo chmod 700 /home/copie/.ssh
sudo chmod 600 /home/copie/.ssh/authorized_keys
  • command="/usr/bin/rrsync -ro /var/backups/intranet" : quoi que demande la connexion, elle ne peut lancer que rsync, en lecture seule, dans ce dossier ;
  • restrict : pas de terminal, pas de redirection de ports, pas d’agent.

D.4, Sur sup-lnx-01 : la copie, chaque heure

Machine : sup-lnx-01 (sysadmin)
sudo tee /usr/local/sbin/copie-sauvegardes > /dev/null <<'EOF'
#!/bin/bash
# Tire une copie des sauvegardes de la base de l'intranet (TP 10)
set -euo pipefail
SOURCE=copie@10.20.N.20:                    # le dossier imposé par rrsync côté srv-lnx-01
DEST=/srv/copies/srv-lnx-01
mkdir -p "$DEST" /var/lib/hexalog
chmod 750 "$DEST" && chgrp sudo "$DEST"   # lisible par les administrateurs, pour restaurer
# pas de --delete : un fichier supprimé ou chiffré sur srv-lnx-01 reste intact ici
rsync -rt -e "ssh -i /root/.ssh/copie-srv-lnx-01 -o BatchMode=yes -o StrictHostKeyChecking=accept-new" "$SOURCE" "$DEST/"
find "$DEST" -maxdepth 1 -name 'intranet-*.sql.gz' -mtime +30 -delete     # 30 jours ici
touch /var/lib/hexalog/copie-srv-lnx-01.ok
echo "Copie à jour : $(ls "$DEST" | wc -l) sauvegardes dans $DEST"
EOF
sudo sed -i 's/10\.20\.N\./10.20.3./' /usr/local/sbin/copie-sauvegardes     # votre numéro
sudo chmod 750 /usr/local/sbin/copie-sauvegardes
sudo tee /etc/systemd/system/copie-sauvegardes.service > /dev/null <<'EOF'
[Unit]
Description=Hexalog : copie des sauvegardes de srv-lnx-01
After=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/copie-sauvegardes
EOF
sudo tee /etc/systemd/system/copie-sauvegardes.timer > /dev/null <<'EOF'
[Unit]
Description=Hexalog : copie horaire des sauvegardes de srv-lnx-01, 10 minutes après la sauvegarde

[Timer]
OnCalendar=*:10
Persistent=true

[Install]
WantedBy=timers.target
EOF
sudo systemctl daemon-reload
sudo systemctl start copie-sauvegardes.service
sudo systemctl enable --now copie-sauvegardes.timer
sudo ls -l /srv/copies/srv-lnx-01/

D.5, Prouver que la copie est en lecture seule

Machine : sup-lnx-01 (sysadmin)
sudo ssh -i /root/.ssh/copie-srv-lnx-01 copie@10.20.N.20 id
sudo rsync -e "ssh -i /root/.ssh/copie-srv-lnx-01" /etc/hostname copie@10.20.N.20:

Les deux sont refusées : pas de commande, pas d’écriture. Notez les messages. Si srv-lnx-01 était compromise, que pourrait faire l’attaquant contre les copies de sup-lnx-01 ? Et si c’était sup-lnx-01 ?

Partie E. Superviser les sauvegardes (15 min)

  1. Sur l’hôte srv-lnx-01 de Zabbix, créez l’élément Sauvegarde de la base : dernière réussite : type Agent Zabbix, clé vfs.file.time[/var/lib/hexalog/sauvegarde-intranet.ok], type d’information Numérique (non signé), unités unixtime, intervalle 1m.
  2. Et le déclencheur Sauvegarde de la base de l'intranet en retard sur {HOST.NAME}, sévérité Moyen :
Machine : expression du déclencheur
now()-last(/srv-lnx-01/vfs.file.time[/var/lib/hexalog/sauvegarde-intranet.ok])>7200
  1. Même chose sur l’hôte Zabbix server (sup-lnx-01) pour /var/lib/hexalog/copie-srv-lnx-01.ok : Copie des sauvegardes de srv-lnx-01 en retard.
  2. Testez sans attendre deux heures, en vieillissant le fichier témoin :
Machine : srv-lnx-01 (sysadmin)
sudo touch -d '-3 hours' /var/lib/hexalog/sauvegarde-intranet.ok

Le problème apparaît en une à deux minutes. Puis relancez une vraie sauvegarde (sudo systemctl start sauvegarde-intranet.service) : il se résout. Pourquoi le seuil est-il de deux heures pour une sauvegarde horaire ?

Partie F. Restaurer (50 min)

Pour chaque restauration, chronométrez : heure du constat, heure de la décision, heure de fin de la restauration, heure de la vérification. Ces durées vont dans le rapport (partie I).

F.1, Un fichier supprimé par erreur

Machine : srv-lnx-01 (sysadmin)
sudo rm /var/www/intranet/index.php
curl -s -o /dev/null -w "accueil : %{http_code}\n" http://localhost/

L’accueil de l’intranet ne répond plus (403). Restaurez seulement ce fichier depuis la sauvegarde de la partie B :

  1. pbs-etuN → Sauvegardes → la sauvegarde la plus récente de la VM N20 → Restauration de fichiers (File Restore). Proxmox lit la sauvegarde (cela prend une minute la première fois) : dépliez le disque, la partition, puis var/www/intranet/ ; sélectionnez index.php → Télécharger.
  2. Le fichier arrive sur votre PC. Renvoyez-le sur srv-lnx-01, en rebondissant par sup-lnx-01, puis remettez-le en place avec les bons droits :
Machine : PC
scp index.php srv-lnx-01:/tmp/
Machine : srv-lnx-01 (sysadmin)
sudo install -o root -g www-data -m 640 /tmp/index.php /var/www/intranet/index.php
curl -s -o /dev/null -w "accueil : %{http_code}\n" http://localhost/

F.2, Une table vidée par une mauvaise requête

Un collègue voulait « archiver les expéditions livrées » ; il les a supprimées :

Machine : srv-lnx-01 (sysadmin)
sudo mariadb intranet -e "DELETE FROM expeditions WHERE statut = 'livrée'"
sudo mariadb intranet -e "SELECT statut, COUNT(*) FROM expeditions GROUP BY statut"

Restaurer toute la base depuis le dernier export ferait perdre les expéditions saisies depuis (l’activité simulée continue). On restaure donc l’export dans une base à part, puis on ne réinjecte que les lignes perdues :

Machine : srv-lnx-01 (sysadmin)
DERNIER=$(sudo sh -c 'ls -1t /var/backups/intranet/intranet-*.sql.gz | head -n 1') ; echo "$DERNIER"
sudo mariadb -e "CREATE DATABASE intranet_restau"
sudo zcat "$DERNIER" | sudo mariadb intranet_restau
sudo mariadb -e "SELECT COUNT(*) AS livrees_dans_l_export FROM intranet_restau.expeditions WHERE statut = 'livrée'"
sudo mariadb -e "INSERT INTO intranet.expeditions
                 SELECT * FROM intranet_restau.expeditions r
                 WHERE r.statut = 'livrée' AND r.id NOT IN (SELECT id FROM intranet.expeditions)"
sudo mariadb intranet -e "SELECT statut, COUNT(*) FROM expeditions GROUP BY statut"
sudo mariadb -e "DROP DATABASE intranet_restau"

Vérifiez dans l’intranet que les expéditions livrées sont revenues et que les saisies récentes sont toujours là (sudo bash activite-intranet.sh etat). Qu’aurait-on perdu si la dernière expédition livrée avait été saisie après le dernier export ?

F.3, Une VM entière, en test

Vous restaurez srv-lnx-01 à côté de la production, sur le numéro de VM de test N99, sans la brancher au réseau (elle a la même adresse que l’original).

  1. pbs-etuN → Sauvegardes → la sauvegarde la plus récente de N20 → Restaurer : ID de VM N99, stockage celui de vos disques, Unique coché, Démarrer après la restauration décoché → Restaurer. Notez l’heure de début et de fin dans le journal de la tâche.
  2. Avant de la démarrer : VM N99 → Matériel → Périphérique réseau → Modifier → cochez Déconnecter → OK.
  3. Démarrez-la, ouvrez sa console, connectez-vous (sysadmin, mot de passe de lab) et vérifiez : hostname, ls /var/www/intranet, sudo mariadb intranet -e "SELECT COUNT(*), MAX(cree_le) FROM expeditions", ip -br a (la carte est sans lien). Les données correspondent-elles à l’heure de la sauvegarde ?
  4. Arrêtez-la, puis supprimez-la : Plus → Supprimer, en vérifiant deux fois qu’il s’agit bien de la VM N99 (elle porte le même nom que srv-lnx-01).

Combien de temps a pris la restauration elle-même ? Et l’ensemble, du constat à la vérification ? C’est la base du RTO réel de srv-lnx-01 (séance 11).

Partie G. Sauvegarder les autres VM (en arrière-plan)

Lancez une sauvegarde Snapshot vers pbs-etuN de sup-lnx-01, srv-lnx-02 et srv-win-01, l’une après l’autre (une seule à la fois par VM). Relevez pour chacune la durée et la quantité transférée : laquelle est la plus longue, et pourquoi ? Pour srv-win-01, le journal de la tâche indique-t-il fs-freeze ? (L’agent invité de Windows utilise le service de clichés instantanés, VSS.)

Une tâche planifiée sauvegarde aussi votre pool chaque soir vers pbs-etuN ; elle est réglée au niveau du centre de données (Centre de données → Sauvegarde), que votre compte ne voit pas : M. CHADEYRON la montre au vidéoprojecteur (heure, mode, sélection par pool, conservation). Qu’apporte-t-elle par rapport à vos sauvegardes manuelles ? Retrouvez ses sauvegardes dans pbs-etuN (notes et heure).

Partie H. Windows Server : l’état du système (facultatif, 25 min)

  1. Proxmox : srv-win-01 → Matériel → Ajouter → Disque dur : SCSI, 30 Gio, sur votre stockage.
  2. Dans Windows : diskmgmt.msc → initialiser le nouveau disque (GPT) → Nouveau volume simple → lettre E:, NTFS, nom Sauvegardes.
  3. Gestionnaire de serveur → Gérer → Ajouter des rôles et fonctionnalités → Fonctionnalités → Sauvegarde Windows Server → Installer.
  4. Outils → Sauvegarde Windows Server → Sauvegarde locale → Sauvegarde unique → Options différentes → Personnalisé → Ajouter des éléments → État du système → destination Lecteurs locaux → E: → Sauvegarde.
  5. Relevez la durée et la taille. Qu’est-ce qui est inclus dans l’état du système d’un contrôleur de domaine ? Que faudrait-il pour restaurer l’annuaire (mode de restauration des services d’annuaire, mot de passe DSRM du TP 1) ? Pourquoi une entreprise a-t-elle au moins deux contrôleurs de domaine ?

Partie I. Le rapport de test de restauration (10 min)

Remplissez le modèle « Rapport de test de restauration » de la page Modèles de livrables pour les trois restaurations de la partie F : ce qui a été restauré, depuis quelle sauvegarde (date), durée de chaque étape, données perdues, difficultés, améliorations. Ce rapport est une preuve pour l’assureur, et il alimentera le PRA.

Dépannage

Symptôme Piste
pbs-etuN absent de la liste des stockages droits sur le stockage ; prévenir M. CHADEYRON
Sauvegarde : guest-agent ne répond pas, pas de fs-freeze agent invité non démarré dans la VM (systemctl status qemu-guest-agent) ou option Agent QEMU désactivée dans les options de la VM
La deuxième sauvegarde n’est pas plus rapide la VM a été arrêtée ou redémarrée entre les deux : la carte des blocs modifiés est perdue
activite-intranet.sh : curl: (22) ou délai dépassé site du cours non joignable depuis la VM : téléchargez le fichier sur votre PC (ou prenez-le sur la clé de M. CHADEYRON) et envoyez-le avec scp activite-intranet.sh srv-lnx-01:
mariadb-dump : Access denied le script doit être lancé avec sudo (connexion de root par le socket)
rsync : Permission denied (publickey) ligne authorized_keys mal collée (une seule ligne, sans retour à la ligne), ou droits de /home/copie/.ssh
rsync : rrsync error ou Permission denied sur les fichiers le dossier n’appartient pas au groupe copie : relancer le script de sauvegarde après avoir créé le compte (D.1)
Élément vfs.file.time Non supporté fichier témoin absent (aucune sauvegarde encore réussie) ou chemin mal recopié
La restauration de fichiers reste sur « chargement » première ouverture : attendre une à deux minutes ; sinon prévenir M. CHADEYRON
Restauration de la VM N99 refusée (permission check failed) numéro de VM différent de N99 (seul celui-ci est prévu pour vos tests)
INSERT … SELECT : Column count doesn’t match l’export date d’avant l’installation de l’activité simulée (colonne cree_le absente) : prendre un export plus récent
