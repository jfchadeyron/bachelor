TP 5 : Alertes, scénario web et tableau de bord

Vous faites de Zabbix un vrai outil d'astreinte : alertes par courriel, scénario web qui teste l'intranet comme un utilisateur, seuils adaptés, hystérésis et dépendances pour réduire le bruit, période de maintenance, supervision SNMP, et un tableau de bord pour l'astreinte d'Hexalog. Chaque réglage est vérifié par une panne provoquée.

Durée3 h 30
Machines virtuellessup-lnx-01, srv-lnx-01, srv-win-01
Cours associéSéance 5 : Zabbix : déclencheurs, alertes, tableaux de bord

Contexte

La supervision Zabbix d’Hexalog collecte, mais elle ne prévient personne, et la liste des problèmes contient déjà des alertes sans intérêt. Avant de la confier à l’astreinte, vous la rendez fiable (on est prévenu des vraies pannes) et sobre (on n’est prévenu que des vraies pannes).

Organisation

Socle : toutes les parties, de A à H.

La messagerie locale de sup-lnx-01 a été installée au TP 3 (partie F.1). Sinon, faites-le d’abord.

Ce que vous construisez

Partie A. Être prévenu par courriel (30 min)

A.1, Le type de média

Alertes → Types de média (Alerts → Media types) → Courriel (Email) :

Champ Valeur
Serveur SMTP 127.0.0.1
Port du serveur SMTP 25
SMTP helo sup-lnx-01.hexalog.local
Courriel zabbix@sup-lnx-01.hexalog.local
Sécurité de la connexion, Authentification Aucune
Activé coché

Actualiser, puis le bouton Test sur la ligne Courriel : envoyez un message à sysadmin@localhost et lisez-le avec mail sur sup-lnx-01.

A.2, Le média de l’utilisateur Admin

Utilisateurs → Utilisateurs → Admin → onglet Média → Ajouter : type Courriel, envoyer à sysadmin@localhost, lorsque actif 1-7,00:00-24:00, utiliser si sévérité : Avertissement, Moyen, Haut, Désastre → Ajouter → Actualiser.

A.3, L’action

Alertes → Actions → Actions de déclencheur (Trigger actions) : ouvrez Report problems to Zabbix administrators. Lisez ses onglets Opérations (à qui, par quel média) et Opérations de récupération, puis activez-la (case Activé, ou clic sur Désactivé dans la liste).

A.4, Vérifier toute la chaîne

Machine : srv-lnx-01 (sysadmin)
date ; sudo systemctl stop nginx

Suivez Surveillance → Problèmes : Nginx: Process is not running (Haut), puis d’autres. Lisez le courriel sur sup-lnx-01, puis redémarrez nginx et attendez le message de résolution. Ouvrez Rapports → Journal des actions (Reports → Action log) : chaque message envoyé y figure, avec son état.

Combien de problèmes une seule cause a-t-elle ouverts ? Gardez la liste : la partie D en réduit le nombre.

Partie B. Tester l’intranet comme un utilisateur (30 min)

B.1, Le scénario web

Collecte de données → Hôtes → ligne srv-lnx-01 → Web → Créer un scénario web :

Onglet Champ Valeur
Scénario Nom Intranet
Intervalle d’actualisation 1m
Tentatives 2
Étapes Ajouter nom Accueil, URL http://10.20.N.20/, chaîne requise Hexalog, code d’état requis 200, expiration 10s
Ajouter nom Sante, URL http://10.20.N.20/sante.php, chaîne requise BASE-OK, code d’état requis 200, expiration 10s

Ajouter. Après deux minutes, Surveillance → Dernières données, filtre sur le nom Intranet : temps de réponse et code de chaque étape, et l’élément Failed step of scenario “Intranet” à 0.

B.2, Les déclencheurs du scénario

Sur srv-lnx-01 → Déclencheurs → Créer un déclencheur, deux fois :

Nom Sévérité Expression
Intranet : le parcours utilisateur échoue (étape {ITEM.LASTVALUE1}) Haut last(/srv-lnx-01/web.test.fail[Intranet])<>0
Intranet : temps de réponse supérieur à 1 s Avertissement avg(/srv-lnx-01/web.test.time[Intranet,Accueil,resp],5m)>1

Le premier n’a pas besoin d’expression de récupération : un parcours réussi suffit à rétablir. Dans l’onglet Tags des deux déclencheurs, ajoutez service = intranet.

B.3, Vérifier

Machine : srv-lnx-01 (sysadmin)
sudo systemctl stop mariadb

Le scénario échoue à l’étape 2 (la page s’affiche, mais BASE-OK est absent). Lisez l’élément Last error message of scenario “Intranet”. Puis sudo systemctl start mariadb.

Partie C. Adapter les seuils (30 min)

C.1, Un seuil propre à l’hôte, par macro

srv-lnx-01 a un petit disque (10 Go) : on veut être prévenu plus tôt. Hôte srv-lnx-01 → onglet Macros → Macros héritées et de l’hôte : repérez {$VFS.FS.PUSED.MAX.WARN} (80, venue du modèle). Redéfinissez sur l’hôte {$VFS.FS.PUSED.MAX.WARN} = 70 et {$VFS.FS.PUSED.MAX.CRIT} = 85 → Actualiser.

Provoquez le remplissage du disque, en calculant la taille pour atteindre environ 75 % :

Machine : srv-lnx-01 (sysadmin)
df -h /
TAILLE=$(df --output=size,used -B1 / | awk 'NR==2 {printf "%d", $1*0.75 - $2}')
echo "Fichier de $((TAILLE / 1024 / 1024)) Mo"
sudo fallocate -l "$TAILLE" /var/tmp/test-remplissage
df -h /

En une à deux minutes, Linux: FS [/]: Space is low apparaît (Avertissement). Supprimez le fichier (sudo rm /var/tmp/test-remplissage) et vérifiez la résolution.

C.2, Un déclencheur avec hystérésis

Sur srv-lnx-01, créez le déclencheur :

Champ Valeur
Nom Charge élevée et durable sur {HOST.NAME}
Sévérité Moyen
Expression min(/srv-lnx-01/system.cpu.load[all,avg1],3m)>1.5
Génération d’événement OK Expression de récupération
Expression de récupération max(/srv-lnx-01/system.cpu.load[all,avg1],3m)<0.8

Testez avec deux calculs inutiles qui occupent le processeur (srv-lnx-01 n’a qu’un cœur), puis arrêtez-les après l’apparition du problème :

Machine : srv-lnx-01 (sysadmin)
sudo systemd-run --unit=test-charge-1 sha256sum /dev/zero
sudo systemd-run --unit=test-charge-2 sha256sum /dev/zero
uptime
Machine : srv-lnx-01 (sysadmin)
sudo systemctl stop test-charge-1 test-charge-2

Relevez l’heure d’apparition et de résolution du problème, et la charge à ces deux moments. Pourquoi la résolution n’est-elle pas immédiate ?

Partie D. Une alerte par cause (30 min)

D.1, La dépendance

Ouvrez le déclencheur Intranet : le parcours utilisateur échoue… → onglet Dépendances → Ajouter → hôte srv-lnx-01 → MySQL: Service is down, puis ajoutez aussi Nginx: Process is not running et PHP-FPM: Service is down → Actualiser.

Arrêtez MariaDB : seul MySQL: Service is down doit notifier ; le problème de l’intranet n’apparaît pas tant que MariaDB est arrêtée. Redémarrez-la.

D.2, Le tri des alertes du modèle

Ouvrez Surveillance → Problèmes, cochez Afficher : Historique sur les dernières 24 heures. Pour chaque problème qui ne correspondait à aucune vraie panne (par exemple Number of installed packages has been changed), décidez : seuil à changer, sévérité, désactivation sur l’hôte, ou rien. Notez vos décisions et leur justification dans le journal de bord.

Pour désactiver un déclencheur venu d’un modèle sur un seul hôte : hôte → Déclencheurs → cliquez sur Activé dans sa ligne (il devient Désactivé). Le modèle n’est pas modifié.

Partie E. Une maintenance sans fausse alerte (20 min)

Vous devez redémarrer srv-lnx-01 pour appliquer des mises à jour. Collecte de données → Maintenance → Créer une période de maintenance :

Champ Valeur
Nom Mises à jour srv-lnx-01
Type de maintenance Avec collecte de données
Actif depuis, actif jusqu’à maintenant, dans 2 heures
Périodes Ajouter : Une fois uniquement, date et heure de début : dans 2 minutes, durée : 30 minutes
Hôtes srv-lnx-01

Une fois la période commencée (icône de clé dans Surveillance → Hôtes), redémarrez la VM : sudo reboot. Les problèmes apparaissent marqués comme supprimés, et aucun courriel ne part. Vérifiez-le dans Rapports → Journal des actions.

Partie F. srv-lnx-01 vu en SNMP (20 min)

On crée un second hôte pour la même machine, interrogé en SNMPv3 (avec l’utilisateur du TP 2) : il ne peut pas recevoir le modèle SNMP sur le même hôte que le modèle d’agent, leurs éléments portant les mêmes clés.

Créer un hôte : nom srv-lnx-01-snmp, nom visible SRV-LNX-01 (SNMP), modèle Linux by SNMP, groupe Hexalog/SNMP, interface SNMP :

Champ Valeur
Adresse IP, port 10.20.N.20, 161
Version SNMP SNMPv3
Nom de sécurité supervision
Niveau de sécurité authPriv
Protocole d’authentification, phrase secrète SHA256, Snmp-Auth-Hexalog
Protocole de confidentialité, phrase secrète AES128, Snmp-Chiff-Hexalog

Après quelques minutes, comparez dans Dernières données la charge et l’espace de / vus par l’agent et par SNMP. Pastille SNMP verte dans Surveillance → Hôtes.

Partie G. Le tableau de bord de l’astreinte (30 min)

Tableaux de bord → Créer un tableau de bord : nom Hexalog - astreinte. Ajoutez les widgets suivants (Ajouter un widget), puis Sauvegarder les modifications :

Widget Réglages
Problèmes par sévérité groupes d’hôtes Hexalog
Problèmes groupes Hexalog, sévérités Avertissement à Désastre, afficher les problèmes supprimés : non
Disponibilité de l’hôte groupes Hexalog, interface Agent
Graph (classique) source : élément simple ; srv-lnx-01, Response time for step “Accueil” of scenario “Intranet”
Valeur de l’élément srv-lnx-01, Failed step of scenario “Intranet” (0 = tout va bien)
Top des hôtes groupes Hexalog, colonne utilisation du processeur

Testez le tableau en arrêtant PHP-FPM sur srv-lnx-01 (sudo systemctl stop php8.4-fpm) : en combien de temps le voyez-vous ? Redémarrez-le.

Snapshots 05-zabbix-alertes de sup-lnx-01 et srv-lnx-01.

Partie H. Services et SLA (25 min)

  1. Services → Services → Créer un service : nom Intranet, Règle de statut par défaut, Tags de problème : service égal intranet. Les deux déclencheurs du scénario web (tag service:intranet) déterminent maintenant l’état du service.
  2. Services → SLA → créer Intranet heures ouvrées : SLO 99.5, période mensuelle, plage du lundi au vendredi de 7 h à 19 h, services avec le tag service:intranet (ajoutez ce tag au service).
  3. Provoquez une panne de quelques minutes, puis consultez Services → Rapport SLA : disponibilité calculée et budget d’erreur restant.

Vérifications

Questions

  1. Pourquoi a-t-on mis le seuil de l’espace disque dans une macro de l’hôte plutôt que de modifier le modèle Linux by Zabbix agent ?
  2. Quand MariaDB est arrêtée, que voit-on dans les dernières données du scénario web ? Pourquoi nginx répond-il quand même 200 à l’étape 1 ?
  3. Pendant la partie C.2, combien de temps s’est écoulé entre le début de la charge et le problème ? Entre l’arrêt de la charge et la résolution ? Expliquez avec les expressions.
  4. Une panne de MariaDB la nuit : qui est prévenu, par quel moyen ? Que faudrait-il ajouter pour qu’un responsable soit prévenu si personne ne réagit en 30 minutes ?
  5. Comparez avec Nagios la même panne (nginx arrêté) : délai de détection, nombre d’alertes, contenu du message.

Dépannage

Symptôme Piste
Le test du type de média échoue (Connection refused) Postfix absent ou arrêté sur sup-lnx-01 : systemctl status postfix
Pas de courriel lors d’un problème action désactivée ; média de l’utilisateur absent, ou sévérité non cochée ; Rapports → Journal des actions donne la raison
Le scénario web échoue à l’étape 1 avec Couldn't connect URL avec N non remplacé, ou nginx arrêté
Required pattern not found alors que la page s’affiche chaîne requise différente de la page (majuscules, accents)
Expression de déclencheur refusée (incorrect item key) clé recopiée avec une faute ; la choisir avec le bouton Ajouter du constructeur d’expression
Pas d’élément vfs.fs.dependent.size[/,pused] la découverte des systèmes de fichiers n’a pas encore tourné : Exécuter maintenant sur la règle de découverte
Le problème de l’intranet apparaît malgré la dépendance le déclencheur dont il dépend n’était pas encore en problème (MariaDB arrêtée depuis moins d’une minute) : les dépendances jouent sur l’état au moment de l’évaluation
Hôte SNMP : Timeout while connecting snmpd arrêté, ou paramètres v3 différents de ceux du TP 2 (SHA-256 côté snmpd = SHA256 dans Zabbix ; AES = AES128)
Des problèmes restent affichés pendant la maintenance normal : ils sont supprimés (icône), sans notification ; filtre Afficher les problèmes supprimés
