Vous découvrez l'interface web de Proxmox, vous créez vos trois premières machines virtuelles avec son assistant, vous installez Windows Server 2025 et deux Debian 13 à partir des images ISO, vous accédez à vos serveurs depuis votre PC par SSH avec une clé neuve, vous installez l'intranet d'Hexalog et vous recréez le domaine hexalog.local. Tout est neuf : rien ne vient du lab VirtualBox du BLOC 1.

Contexte

Hexalog a acheté un serveur de virtualisation Proxmox VE. Ses serveurs y sont réinstallés à neuf : on ne récupère ni les machines du BLOC 1 (elles tournaient dans VirtualBox, sur votre PC), ni leurs clés SSH. Vous reconstruisez le cœur du système d’information : le contrôleur de domaine, le serveur qui porte l’intranet de suivi des expéditions, et le futur serveur de supervision, qui sera aussi votre porte d’entrée pour l’administration.

Organisation

Socle (indispensable pour la séance 2) : parties A à G, et la partie H jusqu’à la création du domaine (H.2). Les parties H.3 à J peuvent être terminées au début de la séance 2. La partie K est facultative.

Notez dès maintenant dans votre journal de bord : votre numéro N, l’adresse PROXMOX, l’adresse DNS-SECOURS, le nom du stockage des disques et le mot de passe de lab, donnés par M. CHADEYRON.

Ce que vous construisez aujourd’hui

L’installation de Windows est longue mais se déroule seule : on la lance en premier, et l’on installe les deux Debian pendant ce temps.

Partie A. Découvrir l’interface de Proxmox (15 min)

B.2, Pourquoi un deuxième CD de pilotes ?

Le disque et la carte réseau de la VM sont VirtIO : des périphériques « paravirtualisés », conçus pour la virtualisation, bien plus rapides que l’imitation d’un vrai disque. Linux les connaît d’origine ; Windows non. Sans son pilote, l’installeur de Windows ne voit aucun disque.

Pourquoi laisser le mot de passe de root vide ?

Le compte root est alors désactivé, et sysadmin reçoit le droit d’utiliser sudo. Personne ne se connecte directement en root : chaque action d’administration est faite par une personne identifiée, avec son propre mot de passe, et laisse une trace dans les journaux (sudo y écrit qui a fait quoi). C’est le principe du moindre privilège, vu au BLOC 1.

Partie D. Terminer l’installation de Windows (25 min)

D.1, Le mot de passe de l’Administrateur

Revenez à la Console de srv-win-01. À l’écran Paramètres personnalisés, saisissez deux fois le mot de passe de lab pour le compte Administrateur, puis Terminer.

Pour l’écran de connexion, la combinaison Ctrl+Alt+Suppr de votre clavier serait interceptée par votre PC : utilisez le bouton Ctrl-Alt-Suppr du panneau qui s’ouvre à gauche de la console (petite flèche).

D.2, Les pilotes VirtIO et l’agent invité

Windows n’a pas encore de réseau : il lui manque le pilote de sa carte VirtIO.

  1. Ouvrez l’Explorateur de fichiers → Ce PC → le lecteur virtio-win.
  2. Double-cliquez sur virtio-win-guest-tools et suivez l’assistant (Suivant, accepter, Installer). Il installe tous les pilotes VirtIO et l’agent invité QEMU.
  3. Proxmox : srv-win-01 → Matériel → retirez les deux médias (Lecteur CD/DVD → Modifier → N’utiliser aucun média, pour chacun).
  4. Résumé de la VM : au bout d’une minute, la rubrique Adresses IP affiche une adresse : l’agent fonctionne.

Partie F. Accéder aux VM depuis votre PC, avec une clé neuve (30 min)

Votre PC n’est pas sur le réseau 10.20.N.0/24 : il passe par le serveur Proxmox, qui redirige le port 1N022 vers sup-lnx-01. Pour aller plus loin, jusqu’à srv-lnx-01, on rebondit par sup-lnx-01.

F.1, Une paire de clés propre au BLOC 2

On ne réutilise pas les clés du BLOC 1 : elles appartiennent à un autre lab. Une clé, un usage : si l’une est compromise, on la révoque sans toucher aux autres. Créez une paire avec une phrase de passe :

Machine : PC (Windows, PowerShell)
mkdir $env:USERPROFILE\.ssh -Force
ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\id_bloc2 -C "bloc2"

Sous Linux : mkdir -p ~/.ssh && ssh-keygen -t ed25519 -f ~/.ssh/id_bloc2 -C bloc2.

Deux fichiers sont créés : id_bloc2 (la clé privée, qui ne quitte jamais votre PC) et id_bloc2.pub (la clé publique, que l’on dépose sur les serveurs).

F.2, Le fichier de configuration SSH

Créez le fichier config du dossier .ssh de votre PC (sous Windows C:\Users\<vous>\.ssh\config, sans extension : le Bloc-notes ajoute volontiers .txt), avec le bloc de la page du lab, en remplaçant PROXMOX et N.

F.3, Première connexion, par mot de passe

Machine : PC
ssh sup-lnx-01

Votre PC affiche l’empreinte de la clé d’hôte du serveur et demande s’il faut lui faire confiance. Avant de répondre yes, comparez-la avec celle que donne la VM elle-même, dans la console Proxmox de sup-lnx-01 :

Machine : sup-lnx-01 (console Proxmox) (sysadmin)
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Les deux doivent être identiques. Répondez yes, saisissez le mot de passe de sysadmin, puis exit.

F.4, Déposer la clé publique sur les deux serveurs

Machine : PC (Windows, PowerShell)
Get-Content $env:USERPROFILE\.ssh\id_bloc2.pub | ssh sup-lnx-01 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
Get-Content $env:USERPROFILE\.ssh\id_bloc2.pub | ssh srv-lnx-01 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

Sous Linux, plus simplement : ssh-copy-id -i ~/.ssh/id_bloc2.pub sup-lnx-01, puis la même chose pour srv-lnx-01.

La première commande demande le mot de passe de sysadmin. Pour la seconde, le premier saut (sup-lnx-01) se fait déjà par clé (phrase de passe), le second demande le mot de passe de srv-lnx-01 ; validez aussi son empreinte (10.20.N.20, à comparer avec sa console).

F.5, Vérifier

Machine : PC
ssh sup-lnx-01 hostname
ssh srv-lnx-01 hostname

Résultat attendu : sup-lnx-01, puis srv-lnx-01, sans mot de passe (seulement la phrase de passe de la clé). Ouvrez une session sur chacun et regardez vos droits :

Machine : srv-lnx-01 (sysadmin)
id
sudo -l

sysadmin est membre du groupe sudo et peut tout faire en administrateur, après avoir saisi son mot de passe.

F.6, Interdire les mots de passe en SSH

Maintenant que la clé fonctionne, on ferme la porte aux attaques par mot de passe. Sur sup-lnx-01, puis sur srv-lnx-01 :

Machine : sup-lnx-01 puis srv-lnx-01 (sysadmin)
sudo tee /etc/ssh/sshd_config.d/10-hexalog.conf > /dev/null <<'EOF'
# Hexalog : connexion SSH par clé uniquement
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
sudo sshd -t && sudo systemctl reload ssh

Sans fermer votre session, testez depuis une nouvelle fenêtre de votre PC :

Machine : PC
ssh sup-lnx-01 hostname
ssh -o PubkeyAuthentication=no sup-lnx-01

La première fonctionne ; la seconde, qui refuse d’utiliser la clé, est rejetée (Permission denied (publickey)). En cas d’erreur, la console Proxmox reste toujours disponible pour corriger.

Partie G. Installer l’intranet sur srv-lnx-01 (15 min)

L’intranet est une petite application PHP de suivi des expéditions, avec sa base MariaDB. Le script d’installation est sur le site du cours : lisez-le avant de l’exécuter (c’est une bonne habitude avant tout sudo bash).

Machine : srv-lnx-01 (sysadmin)
curl -fsSLO https://jfchadeyron.github.io/bachelor/bloc2/fichiers/installer-intranet.sh
less installer-intranet.sh
sudo bash installer-intranet.sh

Si curl répond par une erreur, téléchargez le fichier depuis votre PC, envoyez-le avec scp installer-intranet.sh srv-lnx-01: et lancez les deux dernières commandes.

Le script installe nginx, PHP-FPM et MariaDB, crée la base intranet et son compte, l’application dans /var/www/intranet, et une page de santé /sante.php qui répond BASE-OK si l’application lit la base, BASE-KO (avec le code HTTP 500) sinon. Il prépare aussi deux pages d’état lisibles seulement depuis la machine elle-même, qui serviront à Zabbix (/basic_status pour nginx, /status pour PHP-FPM).

Vérifiez :

Machine : sup-lnx-01 (sysadmin)
curl -s http://10.20.N.20/sante.php
curl -s -o /dev/null -w "code %{http_code} en %{time_total} s\n" http://10.20.N.20/
curl -s -o /dev/null -w "basic_status depuis sup-lnx-01 : code %{http_code}\n" http://10.20.N.20/basic_status

Résultat attendu : BASE-OK expeditions=8, code 200, puis code 403 pour la page d’état (réservée à la machine elle-même). Ouvrez enfin l’intranet depuis votre PC, comme un utilisateur : http://PROXMOX:1N020/.

Partie H. Le domaine hexalog.local sur srv-win-01 (45 min)

H.1, Le rôle AD DS

Ouvrez une session Administrateur sur srv-win-01 (console Proxmox). Gestionnaire de serveur → Gérer → Ajouter des rôles et fonctionnalités → Suivant jusqu’aux rôles → Services AD DS → Ajouter des fonctionnalités → Suivant → Installer.

H.2, Promouvoir le serveur en contrôleur de domaine

Drapeau jaune en haut du Gestionnaire de serveur → Promouvoir ce serveur en contrôleur de domaine :

  • Ajouter une nouvelle forêt, nom de domaine racine hexalog.local ;
  • mot de passe du mode de restauration des services d’annuaire (DSRM) : le mot de passe de lab ;
  • nom NetBIOS proposé : HEXALOG ;
  • Suivant jusqu’à Installer. Le serveur redémarre (dix minutes environ). Ouvrez ensuite une session HEXALOG\Administrateur.

H.3, Le DNS du domaine

Outils → DNS :

  1. Clic droit sur SRV-WIN-01 → Propriétés → onglet Redirecteurs → Modifier → DNS-SECOURS. Le contrôleur pourra ainsi résoudre les noms d’Internet pour les autres VM.
  2. Zones de recherche directes → hexalog.local → clic droit → Nouvel hôte (A ou AAAA) : srv-lnx-01 → 10.20.N.20 ; srv-lnx-02 → 10.20.N.21 ; sup-lnx-01 → 10.20.N.40 ; sup-win-01 → 10.20.N.41.
  3. Clic droit → Nouvel alias (CNAME) : intranet → srv-lnx-01.hexalog.local ; glpi → srv-lnx-02.hexalog.local.

H.4, Autoriser le ping

Par défaut, Windows Server ne répond pas au ping ; pour la supervision, il semblerait éteint. Win + R → wf.msc → Règles de trafic entrant → clic droit sur Partage de fichiers et d’imprimantes (Demande d’écho - Trafic entrant ICMPv4), profil Domaine → Activer la règle.

Partie I. Le DNS des VM Linux (10 min)

Les deux Debian utilisent encore le DNS de secours, qui ne connaît pas hexalog.local. Sur sup-lnx-01 puis sur srv-lnx-01, remplacez le contenu de /etc/resolv.conf :

Machine : sup-lnx-01 puis srv-lnx-01 (sysadmin)
sudo nano /etc/resolv.conf
Fichier : /etc/resolv.conf
search hexalog.local
nameserver 10.20.N.10
nameserver DNS-SECOURS
options timeout:1

Le contrôleur de domaine est interrogé en premier ; s’il ne répond pas dans la seconde, le DNS de secours prend le relais (pour Internet seulement). Vérifiez :

Machine : sup-lnx-01 (sysadmin)
ping -c 2 10.20.N.10
getent hosts srv-lnx-01.hexalog.local
getent hosts intranet.hexalog.local
getent hosts deb.debian.org

Résultat attendu : le ping répond ; intranet.hexalog.local est donné comme un alias de srv-lnx-01.hexalog.local (10.20.N.20) ; le nom d’Internet est résolu.

Partie J. Snapshots (5 min)

Pour chacune des trois VM : Snapshots → Prendre un snapshot → nom 01-lab-initial, une description courte. Pour srv-win-01, ne cochez pas Inclure la RAM (le snapshot serait beaucoup plus gros).

Partie K. Superviser « à la main » (facultatif, 20 min)

Avant d’installer des outils, essayez de savoir si l’intranet va bien avec ce que vous connaissez déjà.

Machine : sup-lnx-01 (sysadmin)
ping -c 3 10.20.N.20
curl -s -o /dev/null -w "code %{http_code} en %{time_total} s\n" http://10.20.N.20/
curl -s http://10.20.N.20/sante.php
Machine : srv-lnx-01 (sysadmin)
uptime
df -h /
free -h
systemctl is-active nginx php8.4-fpm mariadb

Écrivez un petit script ~/verif-intranet.sh qui enchaîne les trois commandes de sup-lnx-01 et affiche « INTRANET OK » ou « INTRANET EN PANNE ». Puis complétez dans votre journal de bord : que manque-t-il à ce script pour être un outil de supervision ? (historique, seuils, alertes, nombre de machines, tableaux de bord, fiabilité du script lui-même). Les séances 3 à 6 répondent à chacun de ces manques.
