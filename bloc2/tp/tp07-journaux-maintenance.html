TP 7 : Centraliser les journaux et planifier la maintenance

Vous faites de sup-lnx-01 le serveur de journaux d'Hexalog, vous y envoyez les journaux de srv-lnx-01 de façon fiable, vous mettez toutes les machines à la même heure, puis Zabbix détecte les connexions refusées sous Linux et sous Windows. Dans un second temps, vous appliquez la politique de mises à jour d'Hexalog, vous supervisez les mises à jour en attente, et vous conduisez un vrai changement de bout en bout : demande, snapshot, maintenance, intervention, vérification, clôture.

Contexte

Lors d’un audit, deux constats ont été faits chez Hexalog : « les journaux restent sur chaque serveur, personne ne les lit » et « les mises à jour s’installent toutes seules, sans que personne ne sache quand ni lesquelles ». Vous corrigez les deux.

Organisation

Socle : parties A à F (D.1 et D.2 au minimum), et H. Facultatif : G (plan de maintenance, sinon à la maison), « Pour aller plus loin ».

Dans les fichiers de configuration, remplacez 10.20.N. par votre numéro (commande sed donnée à chaque fois, avec 3 à remplacer).

Ce que vous construisez

Partie A. Le serveur de journaux sur sup-lnx-01 (25 min)

A.1, Installer rsyslog

Machine : sup-lnx-01 (sysadmin)
sudo apt install -y rsyslog
ls -l /var/log/syslog /var/log/auth.log
sudo tail -n 3 /var/log/auth.log

Les fichiers texte habituels apparaissent : rsyslog reçoit désormais une copie de tout ce que journald enregistre. Ils appartiennent au groupe adm.

A.2, Recevoir les journaux des autres machines

Le serveur écoute en TCP sur le port 514, n’accepte que les machines du lab, et range les messages dans un dossier par machine, avec un fichier pour l’authentification et un pour le reste :

Machine : sup-lnx-01 (sysadmin)
sudo tee /etc/rsyslog.d/10-reception-hexalog.conf > /dev/null <<'EOF'
# Hexalog : réception des journaux des serveurs (TCP 514), un dossier par machine
module(load="imtcp")
$AllowedSender TCP, 127.0.0.1, 10.20.N.0/24

# secpath-replace : le nom de machine ne peut pas contenir de « / »
template(name="hx-auth" type="string"
         string="/var/log/hexalog/%HOSTNAME:::secpath-replace%/auth.log")
template(name="hx-syslog" type="string"
         string="/var/log/hexalog/%HOSTNAME:::secpath-replace%/syslog.log")

ruleset(name="hexalog-distants") {
    if prifilt("auth,authpriv.*") then {
        action(type="omfile" dynaFile="hx-auth" dirCreateMode="0750" dirGroup="adm"
               fileCreateMode="0640" fileGroup="adm")
    } else {
        action(type="omfile" dynaFile="hx-syslog" dirCreateMode="0750" dirGroup="adm"
               fileCreateMode="0640" fileGroup="adm")
    }
    stop
}

input(type="imtcp" port="514" ruleset="hexalog-distants")
EOF
sudo sed -i 's/10\.20\.N\./10.20.3./' /etc/rsyslog.d/10-reception-hexalog.conf     # votre numéro
sudo rsyslogd -N1
sudo systemctl restart rsyslog
sudo ss -tlnp | grep ':514'

Résultat attendu : End of config validation run, puis rsyslog en écoute sur 0.0.0.0:514. Le mot-clé ruleset isole les messages reçus du réseau : ils ne se mélangent pas aux journaux de sup-lnx-01 elle-même.

A.3, La rotation

Machine : sup-lnx-01 (sysadmin)
sudo tee /etc/logrotate.d/hexalog > /dev/null <<'EOF'
# Journaux reçus des serveurs d'Hexalog : rotation chaque semaine, 26 semaines gardées (6 mois)
/var/log/hexalog/*/*.log {
    weekly
    rotate 26
    compress
    delaycompress
    missingok
    notifempty
    sharedscripts
    postrotate
        /usr/lib/rsyslog/rsyslog-rotate
    endscript
}
EOF
sudo logrotate --debug /etc/logrotate.d/hexalog 2>&1 | tail -n 5

--debug simule sans rien faire. La commande rsyslog-rotate demande à rsyslog de rouvrir ses fichiers après la rotation. Pourquoi 26 semaines ? Notez la justification (cours, partie 4) dans votre journal de bord.

Partie B. Envoyer les journaux de srv-lnx-01 (30 min)

B.1, Le client

Machine : srv-lnx-01 (sysadmin)
sudo apt install -y rsyslog
sudo tee /etc/rsyslog.d/90-vers-sup-lnx-01.conf > /dev/null <<'EOF'
# Hexalog : copie de tous les journaux vers le serveur central, en TCP,
# avec une file d'attente qui garde les messages si le serveur est injoignable
action(type="omfwd" target="10.20.N.40" port="514" protocol="tcp"
       queue.type="LinkedList" queue.filename="vers-sup-lnx-01"
       queue.maxDiskSpace="100m" queue.saveOnShutdown="on"
       action.resumeRetryCount="-1")
EOF
sudo sed -i 's/10\.20\.N\./10.20.3./' /etc/rsyslog.d/90-vers-sup-lnx-01.conf     # votre numéro
sudo rsyslogd -N1
sudo systemctl restart rsyslog
logger -p auth.notice "TP7 : test d'envoi depuis $(hostname)"
Machine : sup-lnx-01 (sysadmin)
sudo ls -l /var/log/hexalog/
sudo tail -n 3 /var/log/hexalog/srv-lnx-01/auth.log
sudo tail -n 3 /var/log/hexalog/srv-lnx-01/syslog.log

Résultat attendu : un dossier srv-lnx-01, et votre message de test dans auth.log, précédé de la date au format ISO 8601, du nom de la machine et du nom du programme (sysadmin, le nom de l’utilisateur qui a lancé logger).

B.2, Que se passe-t-il si le serveur tombe ?

  1. Arrêtez la réception : sudo systemctl stop rsyslog sur sup-lnx-01.
  2. Sur srv-lnx-01, envoyez trois messages numérotés : for i in 1 2 3 ; do logger "TP7 : message $i pendant la coupure" ; done.
  3. Vérifiez qu’ils sont bien en local sur srv-lnx-01 (sudo tail -n 3 /var/log/syslog) et absents sur sup-lnx-01.
  4. Redémarrez la réception sur sup-lnx-01 (sudo systemctl start rsyslog), attendez une minute, puis cherchez les trois messages : sudo grep "pendant la coupure" /var/log/hexalog/srv-lnx-01/syslog.log.

Ils arrivent : le client les a gardés dans sa file d’attente et réessaie régulièrement. Avec UDP, ils seraient perdus. Notez combien de temps ils ont mis à arriver.

B.3, Suivre une connexion de bout en bout

Depuis votre PC, ouvrez une session sur srv-lnx-01 (ssh srv-lnx-01), lancez sudo -l, déconnectez-vous. Puis retrouvez la connexion sur sup-lnx-01 seulement : dans /var/log/auth.log (le passage par le point d’entrée) et dans /var/log/hexalog/srv-lnx-01/auth.log (l’arrivée sur srv-lnx-01 et la commande sudo). Construisez la chronologie dans votre journal de bord : heure, machine, ligne.

Partie C. Toutes les machines à la même heure (15 min)

Le serveur Proxmox (10.20.N.1, la passerelle de votre réseau) sert d’horloge de référence au lab.

Machines : sup-lnx-01 et srv-lnx-01 (sysadmin)
sudo apt install -y systemd-timesyncd
timedatectl
sudo mkdir -p /etc/systemd/timesyncd.conf.d
printf '[Time]\nNTP=10.20.N.1\n' | sudo tee /etc/systemd/timesyncd.conf.d/hexalog.conf
sudo sed -i 's/10\.20\.N\./10.20.3./' /etc/systemd/timesyncd.conf.d/hexalog.conf     # votre numéro
sudo systemctl restart systemd-timesyncd
sleep 5 ; timedatectl timesync-status

Résultat attendu : Server: 10.20.N.1, un décalage (Offset) de quelques millisecondes, et dans timedatectl : Time zone: Europe/Paris, System clock synchronized: yes. Si le fuseau est UTC, corrigez-le : sudo timedatectl set-timezone Europe/Paris. Si Packet count reste à 0, le serveur ne répond pas : prévenez M. CHADEYRON.

Sur srv-win-01, dans une invite de commandes : w32tm /query /status. Quelle est la source de l’heure du contrôleur de domaine ? Est-ce satisfaisant pour un domaine dont tous les membres se règlent sur lui ? (Voir « Pour aller plus loin ».)

Partie D. Détecter dans les journaux avec Zabbix (35 min)

D.1, Les connexions SSH refusées sur srv-lnx-01

  1. L’agent doit pouvoir lire /var/log/auth.log :
Machine : srv-lnx-01 (sysadmin)
sudo usermod -aG adm zabbix
sudo systemctl restart zabbix-agent2
sudo -u zabbix head -n 1 /var/log/auth.log
  1. Dans Zabbix : Collecte de données → Hôtes → srv-lnx-01 → Éléments → Créer un élément :
Champ Valeur
Nom SSH : connexions refusées
Type Agent Zabbix (actif)
Clé log[/var/log/auth.log,"Invalid user|Failed password|authenticating user",,,skip]
Type d’information Journal
Intervalle d’actualisation 1m
  1. Déclencheurs → Créer un déclencheur : nom Tentatives de connexion SSH en série sur {HOST.NAME}, sévérité Moyen, expression (construite avec le bouton Ajouter : élément ci-dessus, fonction count(), période 5m, résultat >= 5) :
Machine : expression du déclencheur
count(/srv-lnx-01/log[/var/log/auth.log,"Invalid user|Failed password|authenticating user",,,skip],5m)>=5

Cochez Permettre la fermeture manuelle, ajoutez le tag securite = ssh.

  1. Simulez quelqu’un qui cherche un compte, depuis sup-lnx-01 (qui n’a pas de clé : chaque essai est refusé) :
Machine : sup-lnx-01 (sysadmin)
for i in 1 2 3 4 5 6 ; do
  ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new intrus$i@10.20.N.20 true
done

Après une à deux minutes : Surveillance → Dernières données (l’élément montre les lignes trouvées, Invalid user intrus1 from 10.20.N.40…), puis Problèmes. Le problème se résout seul cinq minutes après le dernier refus. Vérifiez aussi que les mêmes lignes sont dans la copie centrale : sudo grep -c "Invalid user intrus" /var/log/hexalog/srv-lnx-01/auth.log.

  2. Dans Zabbix, sur l’hôte srv-win-01, créez l’élément :

  2. Simulez des essais de mot de passe sur le partage de fichiers du contrôleur de domaine :

Chaque essai répond NT_STATUS_LOGON_FAILURE. Vérifiez dans l’Observateur d’événements de srv-win-01 (journal Sécurité, Filtrer le journal actuel, ID 4625) : type d’ouverture de session, compte, adresse source. Puis dans Zabbix : dernières données et problème.

Partie E. La politique de mises à jour (30 min)

E.1, Les mises à jour automatiques de Debian

L’installateur de Debian met normalement en place l’outil des mises à jour automatiques, unattended-upgrades. La première commande le vérifie (elle ne fait rien s’il est déjà installé) ; les suivantes montrent ce qu’il fait par défaut :

Machine : srv-lnx-01 (sysadmin)
sudo apt install -y unattended-upgrades
cat /etc/apt/apt.conf.d/20auto-upgrades
grep -v '^\s*//' /etc/apt/apt.conf.d/50unattended-upgrades | grep -v '^\s*$' | head -n 12
systemctl list-timers 'apt-daily*' --no-pager
apt list --upgradable
ls /run/reboot-required 2>/dev/null || echo "pas de redémarrage demandé"

Répondez dans votre journal : les mises à jour automatiques sont-elles actives ? À quelle heure tournent-elles (les deux minuteurs apt-daily) ? Quelles origines sont autorisées par défaut (cherchez label=Debian et label=Debian-Security) ? Leur journal sera dans /var/log/unattended-upgrades/.

E.2, La politique d’Hexalog : sécurité automatique, le reste en maintenance

Machine : srv-lnx-01 (sysadmin)
sudo tee /etc/apt/apt.conf.d/52hexalog-unattended > /dev/null <<'EOF'
// Hexalog : seules les mises à jour de sécurité sont installées automatiquement ;
// les autres attendent la maintenance mensuelle (demande de changement).
#clear Unattended-Upgrade::Origins-Pattern;
Unattended-Upgrade::Origins-Pattern {
        "origin=Debian,codename=${distro_codename}-security,label=Debian-Security";
};
Unattended-Upgrade::Automatic-Reboot "false";
EOF
apt-config dump | grep -A2 'Origins-Pattern'
sudo unattended-upgrade --dry-run --debug 2>&1 | grep -E 'Allowed origins|Packages that will be upgraded|No packages found'

La ligne #clear vide la liste définie par Debian avant d’en donner une nouvelle : sans elle, les deux listes s’ajouteraient. Résultat attendu : Allowed origins are: origin=Debian,codename=trixie-security,label=Debian-Security. On ne modifie pas 50unattended-upgrades, fourni par le paquet.

E.3, Superviser les mises à jour en attente

  1. Ajoutez trois clés à l’agent de srv-lnx-01 (cours, partie 6) :
Machine : srv-lnx-01 (sysadmin)
sudo tee /etc/zabbix/zabbix_agent2.d/hexalog-maj.conf > /dev/null <<'EOF'
# Hexalog : mises à jour en attente et redémarrage nécessaire
UserParameter=hexalog.maj.attente,apt-get -s -o Debug::NoLocking=true upgrade | grep -c '^Inst' || true
UserParameter=hexalog.maj.securite,apt-get -s -o Debug::NoLocking=true upgrade | grep '^Inst' | grep -c -- '-security' || true
UserParameter=hexalog.redemarrage,test -f /run/reboot-required && echo 1 || echo 0
EOF
for k in hexalog.maj.attente hexalog.maj.securite hexalog.redemarrage ; do
  zabbix_agent2 -t $k -c /etc/zabbix/zabbix_agent2.conf
done
sudo systemctl restart zabbix-agent2
Machine : sup-lnx-01 (sysadmin)
zabbix_get -s 10.20.N.20 -k hexalog.maj.attente
  1. Dans Zabbix, sur srv-lnx-01, créez trois éléments de type Agent Zabbix, type d’information Numérique (non signé), intervalle 30m, délai d’expiration 15s : Mises à jour en attente (hexalog.maj.attente), Mises à jour de sécurité en attente (hexalog.maj.securite), Redémarrage nécessaire (hexalog.redemarrage).
  2. Deux déclencheurs :
Nom Sévérité Expression
Correctifs de sécurité en attente depuis plus de 24 h sur {HOST.NAME} Avertissement min(/srv-lnx-01/hexalog.maj.securite,24h)>0
Redémarrage nécessaire sur {HOST.NAME} Information last(/srv-lnx-01/hexalog.redemarrage)=1

Pourquoi le premier attend-il 24 heures ?

Partie F. Un changement de bout en bout (40 min)

La maintenance mensuelle de srv-lnx-01 est due : installer les mises à jour qui ne sont pas de sécurité, et redémarrer si nécessaire.

F.1, La demande de changement

Remplissez le modèle « Demande de changement » de la page Modèles de livrables : objet, justification, machines et services touchés, impact pendant l’intervention (l’intranet est-il interrompu ? combien de temps ?), risque, plan de test, plan de retour arrière, fenêtre, personnes prévenues. Faites-la relire par votre voisin, qui joue le rôle du responsable : il la valide ou demande des compléments.

F.2, Préparer

  1. Snapshot 07-avant-maj de srv-lnx-01 dans Proxmox (c’est votre retour arrière).
  2. Zabbix : période de maintenance avec collecte de données sur srv-lnx-01, qui commence maintenant, pour 30 minutes (comme au TP 5, partie E).
  3. Nagios : il supervise aussi srv-lnx-01 : page de l’hôte → Schedule downtime for this host and all services, 30 minutes.

Deux outils de supervision, deux maintenances à déclarer : notez-le comme un inconvénient d’avoir plusieurs outils.

F.3, Réaliser

Machine : srv-lnx-01 (sysadmin)
date
sudo apt update
apt list --upgradable
sudo apt full-upgrade -y
ls /run/reboot-required 2>/dev/null && cat /run/reboot-required.pkgs

Si /run/reboot-required existe (nouveau noyau, bibliothèque système), redémarrez : sudo reboot. Le redémarrage relance aussi les services qui utilisaient encore les anciennes versions des bibliothèques. Notez l’heure de début et de fin de l’interruption.

F.4, Vérifier

  • curl -s http://10.20.N.20/sante.php depuis sup-lnx-01 : BASE-OK ;
  • Zabbix : scénario web Intranet en succès, pastille ZBX verte, problèmes éventuels marqués comme supprimés, aucune notification dans Rapports → Journal des actions ;
  • Nagios : services de srv-lnx-01 OK, Event Log sans notification pendant le downtime ;
  • zabbix_get -s 10.20.N.20 -k hexalog.maj.attente : 0.

F.5, Clôturer

  1. Complétez la demande de changement : réalisé le, par, résultat, durée réelle de l’interruption, écarts.
  2. Ajoutez la ligne correspondante dans votre journal des modifications (modèle sur la page Modèles de livrables).
  3. Une fois le changement validé, supprimez le snapshot 07-avant-maj. Pourquoi ne pas le garder « au cas où » ?

Partie G. Le plan de maintenance d’Hexalog (facultatif, 15 min, sinon à la maison)

Complétez le modèle « Plan de maintenance préventive » de la page Modèles de livrables pour les machines du lab : au moins dix tâches, avec la fréquence, le responsable, l’outil et la preuve. Ce plan fait partie du dossier de MCO (séance 12).

Partie H. Anticiper la saturation (20 min)

  1. Sur srv-lnx-01, créez un déclencheur / sera plein dans moins de 2 h sur {HOST.NAME}, sévérité Avertissement : timeleft(/srv-lnx-01/vfs.fs.dependent.size[/,pused],10m,100)<2h.
  2. Simulez un fichier qui grossit de 100 Mo par minute (une exportation qui s’emballe) :
Machine : srv-lnx-01 (sysadmin)
sudo systemd-run --unit=export-emballe bash -c 'for i in $(seq 1 40) ; do fallocate -l 50M /var/tmp/export-$i.tmp ; sleep 30 ; done'
df -h /
  1. Observez le graphique de l’espace utilisé et l’apparition du problème avant que le disque soit plein. Puis arrêtez et nettoyez : sudo systemctl stop export-emballe ; sudo rm -f /var/tmp/export-*.tmp.

Dépannage

Symptôme Piste
rsyslogd -N1 : erreur de syntaxe guillemets ou accolades oubliés en recopiant ; relancer -N1 après chaque correction
Rien n’arrive dans /var/log/hexalog sur sup-lnx-01 : ss -tlnp | grep 514 ; adresse de $AllowedSender (N remplacé ?) ; sur srv-lnx-01 : adresse target, sudo journalctl -u rsyslog
journalctl -u rsyslog (sup-lnx-01) : disallowed sender l’adresse de l’émetteur n’est pas dans $AllowedSender
Les messages de la coupure n’arrivent pas attendre une à deux minutes (le client réessaie à intervalles croissants) ; action.resumeRetryCount="-1" présent ?
timedatectl timesync-status : Packet count: 0 le serveur NTP ne répond pas : N, passerelle ; prévenir M. CHADEYRON
Élément log[] Non supporté : Cannot open file le compte zabbix n’est pas dans adm, ou l’agent n’a pas été redémarré
Élément log[] ou eventlog[] sans valeur, pas d’erreur contrôle actif : ServerActive= et Hostname= de l’agent (TP 4) ; le nom doit être identique à celui de l’hôte dans Zabbix ; les lignes antérieures à la création sont ignorées (skip)
Pas d’événement 4625 stratégie d’audit non appliquée : gpupdate /force, vérifier qu’il s’agit bien de la Default Domain Controllers Policy
smbclient : Connection refused srv-win-01 éteint, ou mauvaise adresse
apt-config dump montre encore label=Debian ligne #clear absente ou mal orthographiée
Élément hexalog.maj.attente : Timeout while executing a shell script délai d’expiration de l’élément trop court : 15s
