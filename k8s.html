Module 00

Construire son lab Proxmox

Avant tout, il faut un vrai cluster. Nous allons créer 3 machines virtuelles Proxmox : un master et deux workers. C'est la configuration minimale pour reproduire un environnement de production réaliste.

Architecture du lab

─── ARCHITECTURE DU LAB Proxmox ───
  Proxmox
  ├─
  │
  ├─ VM1 : k8s-master   → 172.16.25.60  (4 vCPU / 4 Go RAM)
  │        rôle : Control Plane
  │        composants : API Server, Scheduler, etcd, Controller
  │
  ├─ VM2 : k8s-worker1  → 172.16.25.61  (2 vCPU / 2 Go RAM)
  │        rôle : Worker Node

  └─ VM3 : k8s-worker2  → 172.16.25.62  (2 vCPU / 2 Go RAM)

  kubectl → 172.16.25.60:6443 (API Server)

⚙️ TP 0.2 — Installer Kubernetes sur les 3 VMs
Proxmox Intermédiaire ⏱ 45 min
Objectif Installer containerd, kubeadm, kubelet et kubectl sur les 3 VMs, puis bootstrapper le cluster.

Script d'installation — À exécuter sur les 3 machines

Crée ce script sur chaque VM et exécute-le. C'est plus rapide que de taper chaque commande.

bash — install-k8s-base.sh (à lancer sur les 3 VMs)
#!/bin/bash
# =========================================================
# Script d'installation Kubernetes pour Ubuntu Server 24.04
# Exécuter avec : sudo bash install-k8s-base.sh
# =========================================================


echo "=== 1/3 Installation containerd ==="
apt-get update -qq
apt-get install -y -qq ca-certificates curl gnupg
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  tee /etc/apt/sources.list.d/docker.list
apt-get update -qq
apt-get install -y -qq containerd.io
mkdir -p /etc/containerd
containerd config default | tee /etc/containerd/config.toml
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
systemctl restart containerd
systemctl enable containerd

echo "=== 2/3 Installation kubeadm + kubelet + kubectl ==="
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.29/deb/Release.key | \
  gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] \
  https://pkgs.k8s.io/core:/stable:/v1.29/deb/ /' | \
  tee /etc/apt/sources.list.d/kubernetes.list
apt-get update -qq
apt-get install -y -qq kubelet kubeadm kubectl
apt-mark hold kubelet kubeadm kubectl

echo "=== 3/3 Activation kubelet ==="
systemctl enable kubelet

echo "✅ Installation terminée ! Prêt pour kubeadm init/join"
bash — Exécution sur les 3 VMs
# Sur ton PC, copier le script sur les 3 VMs et l'exécuter
$ for ip in 172.16.25.60 172.16.25.61 172.16.25.62; do
    scp install-k8s-base.sh k8sadmin@$ip:~/ # Copier le script
    ssh k8sadmin@$ip "sudo bash ~/install-k8s-base.sh"
    echo "✅ $ip installé"
  done

Module 02

StatefulSets — Applications avec état

Un StatefulSet est comme un Deployment, mais pour les applications qui ont besoin d'une identité stable et persistante : bases de données, systèmes de messagerie, Elasticsearch.

Deployment vs StatefulSet

CritèreDeploymentStatefulSet
Noms des Pods app-7d9f-xk2p1 (aléatoire) mysql-0, mysql-1 (ordonné, stable)
Ordre de démarrage Simultané, aléatoire Séquentiel : 0, puis 1, puis 2...
Stockage Partagé entre tous les Pods Volume dédié par Pod (PVC unique)
Réseau IP aléatoire à chaque redémarrage Headless Service + DNS stable : mysql-0.mysql-svc
Usage Applis sans état (Nginx, API REST) MySQL, PostgreSQL, Kafka, Elasticsearch
🌐
DNS stable avec StatefulSet Chaque Pod d'un StatefulSet a un nom DNS prévisible : pod-name.service-name.namespace.svc.cluster.local
Ex: mysql-0.mysql-headless.default.svc.cluster.local
🗄️ TP 2.1 — MySQL en StatefulSet avec volume dédié par réplica
Intermédiaire ⏱ 40 min
Objectif Déployer MySQL avec un StatefulSet. Vérifier que chaque pod a son propre volume persistant, et que le DNS interne permet de les adresser individuellement.

Étape 1 — Créer le fichier mysql-statefulset.yaml

yaml — mysql-statefulset.yaml
# ─── Headless Service (pas d'IP fixe, pour le DNS uniquement) ───
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
spec:
  clusterIP: None            # "None" = Headless Service
  selector:
    app: mysql
  ports:
    - port: 3306
      targetPort: 3306
---
# ─── Service ClusterIP pour les clients ───
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  selector:
    app: mysql
  ports:
    - port: 3306
---
# ─── StatefulSet MySQL ───
apiVersion: apps/v1
kind: StatefulSet          # Type StatefulSet, pas Deployment
metadata:
  name: mysql
spec:
  serviceName: "mysql-headless"  # Lié au Headless Service
  replicas: 2
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          env:
            - name: MYSQL_ROOT_PASSWORD
              value: "TP_K8s_2024"
          ports:
            - containerPort: 3306
              name: mysql
          volumeMounts:
            - name: mysql-data
              mountPath: /var/lib/mysql
  volumeClaimTemplates:          # Template PVC : 1 PVC créé par Pod !
    - metadata:
        name: mysql-data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 500Mi

Étape 2 — Déployer et observer

Module 03

DaemonSets — Un Pod par Node

Un DaemonSet garantit qu'un Pod tourne sur chaque Node du cluster. Quand un nouveau Node rejoint le cluster, le DaemonSet y déploie automatiquement son Pod. Idéal pour les agents de monitoring, de logs ou de sécurité.

📊

Monitoring

Node Exporter (Prometheus), Datadog Agent, New Relic

📝

Logging

Fluentd, Filebeat, Fluent Bit — collecte les logs de chaque node

🔒

Sécurité

Falco (détection intrusion), scanners de vulnérabilités

🌐

Réseau

CNI plugins (Flannel, Calico), kube-proxy lui-même est un DaemonSet

📝 TP 3.1 — Collecteur de logs avec DaemonSet
Intermédiaire ⏱ 25 min
Objectif Déployer un agent Fluent Bit en DaemonSet pour collecter les logs de chaque node du cluster. Vérifier qu'il tourne bien sur les 2 workers ET le master.
yaml — daemonset-fluentbit.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
  namespace: kube-system    # Les agents tournent dans kube-system
spec:
  selector:
    matchLabels:
      name: log-collector
  template:
    metadata:
      labels:
        name: log-collector
    spec:
      tolerations:             # Permettre de tourner sur le master
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
      containers:
        - name: fluent-bit
          image: fluent/fluent-bit:2.2
          resources:
            limits:   { memory: "100Mi", cpu: "100m" }
            requests: { memory: "50Mi",  cpu: "50m"  }
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
            - name: varlibdockercontainers
              mountPath: /var/lib/docker/containers
              readOnly: true
      volumes:
        - name: varlog
          hostPath:
            path: /var/log         # Monter le dossier RÉEL du node
        - name: varlibdockercontainers
          hostPath:
            path: /var/lib/docker/containers
bash
$ kubectl apply -f daemonset-fluentbit.yaml

# Vérifier : 1 pod par node (3 nodes = 3 pods)
$ kubectl get pods -n kube-system -l name=log-collector -o wide
# NAME                 READY  STATUS   NODE
# log-collector-abc1   1/1    Running  k8s-master
# log-collector-def2   1/1    Running  k8s-worker1
# log-collector-ghi3   1/1    Running  k8s-worker2

# Ajouter un nouveau node → un nouveau pod apparaît automatiquement !
# Tester : noter les pods, puis relancer un worker et réobserver

# Voir les tolérances (pourquoi le pod tourne sur le master)
$ kubectl get pods -n kube-system log-collector-abc1 -o yaml | grep -A5 tolerations
📌
Pourquoi les Tolerations ? Par défaut, le master a une taint (contamination) NoSchedule qui empêche les Pods normaux d'y tourner. Les Tolerations permettent d'ignorer cette restriction. Utile pour les agents système qui doivent tourner partout.
Module 04

Jobs & CronJobs — Tâches programmées

Un Job lance un Pod qui doit s'exécuter et se terminer avec succès. Un CronJob lance des Jobs selon un planning (comme cron sous Linux). Parfaits pour les sauvegardes, les rapports, le nettoyage de données.

TypeComportementCas d'usage
JobLance 1 ou N Pods, attend qu'ils terminent avec succèsMigration de BDD, envoi de mails en masse, traitement batch
CronJobCrée un Job selon un planning CRONSauvegardes nocturnes, rapports hebdo, nettoyage
⏰ TP 4.1 — Backup automatique avec CronJob
Facile ⏱ 30 min
Objectif Créer un Job de simulation de sauvegarde, puis un CronJob qui l'exécute toutes les minutes (pour les tests). Observer la gestion de l'historique des Jobs.

Étape 1 — Job simple (exécution unique)

yaml — job-backup.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-backup-manuel
spec:
  completions: 1          # Nombre d'exécutions à succès requises
  parallelism: 1          # Pods parallèles maximum
  backoffLimit: 3         # Nombre de tentatives en cas d'échec
  activeDeadlineSeconds: 120  # Timeout global en secondes
  template:
    spec:
      restartPolicy: OnFailure  # Never ou OnFailure (jamais Always pour un Job)
      containers:
        - name: backup
          image: ubuntu:22.04
          command:
            - /bin/bash
            - -c
            - |
              echo "=== Démarrage sauvegarde $(date) ==="
              echo "Simulation : compresse la base de données..."
              sleep 10
              echo "Simulation : upload vers /backups/dump-$(date +%Y%m%d).sql"
              echo "=== Sauvegarde terminée avec succès ! ==="
bash
$ kubectl apply -f job-backup.yaml

# Suivre le job
$ kubectl get jobs -w
# NAME               COMPLETIONS   DURATION   AGE
# db-backup-manuel   0/1           5s         5s
# db-backup-manuel   1/1           15s        15s  ← complété

# Voir les logs du Job (le pod s'appelle comme le job avec un suffix)
$ kubectl logs -l job-name=db-backup-manuel
# === Démarrage sauvegarde Thu Jan 18 10:30:00 UTC 2024 ===
# Simulation : compresse la base de données...
# === Sauvegarde terminée avec succès ! ===

Étape 2 — CronJob (exécution planifiée)

yaml — cronjob-backup.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-nuit
spec:
  schedule: "*/2 * * * *"        # Toutes les 2 min (pour tester)
    # Format : minute heure jour-du-mois mois jour-de-semaine
    # Exemples :
    # "0 2 * * *"     = tous les jours à 2h00
    # "0 2 * * 0"     = tous les dimanches à 2h00
    # "*/5 * * * *"   = toutes les 5 minutes
  successfulJobsHistoryLimit: 3  # Garder les 3 derniers jobs réussis
  failedJobsHistoryLimit: 1      # Garder le dernier job échoué
  concurrencyPolicy: Forbid     # Ne pas lancer si le précédent tourne encore
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: ubuntu:22.04
              command:
                - /bin/bash
                - -c
                - "echo Backup $(date) terminé >> /tmp/backup.log && cat /tmp/backup.log"
bash
$ kubectl apply -f cronjob-backup.yaml

# Lister les CronJobs
$ kubectl get cronjobs
# NAME           SCHEDULE      SUSPEND  ACTIVE  LAST SCHEDULE
# backup-nuit    */2 * * * *   False    0       <none>

# Attendre 2-3 minutes et observer les Jobs créés automatiquement
$ kubectl get jobs
# NAME                    COMPLETIONS
# backup-nuit-28435220    1/1
# backup-nuit-28435222    1/1
# backup-nuit-28435224    1/1  ← max 3 gardés

# Forcer l'exécution immédiate (sans attendre le prochain cron)
$ kubectl create job backup-force --from=cronjob/backup-nuit

# Suspendre le CronJob (pause)
$ kubectl patch cronjob backup-nuit -p '{"spec":{"suspend":true}}'
Module 05

Horizontal Pod Autoscaler (HPA)

Le HPA observe les métriques de tes Pods (CPU, RAM, métriques custom) et ajuste automatiquement le nombre de réplicas pour absorber la charge. Quand la charge diminue, il réduit le nombre de Pods pour économiser les ressources.

─── FONCTIONNEMENT DU HPA ───
   Charge faible                    Pic de trafic
   CPU : 10%                        CPU : 85%
   replicas : 2                     replicas : 2
        │                                │
        │          HPA surveille         │
        ▼                                ▼
   [Pod 1][Pod 2]             [Pod 1][Pod 2]
                                        │
                              HPA : CPU > 70% → scale up !
                                        │
                                        ▼
                         [Pod 1][Pod 2][Pod 3][Pod 4][Pod 5]

   Plus tard, charge baisse...
   HPA : CPU < 50% pendant 5min → scale down
        ▼
   [Pod 1][Pod 2][Pod 3]
⚠️
Prérequis : metrics-server Le HPA a besoin du metrics-server pour lire le CPU/RAM des Pods. Sans lui, kubectl top pods ne fonctionne pas et le HPA reste inactif.
📈 TP 5.1 — Stress test et HPA en action

yaml — hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache         # Le Deployment à scaler
  minReplicas: 1             # Jamais en dessous de 1
  maxReplicas: 8             # Jamais au-dessus de 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50  # Scaler si CPU > 50% de la request

Étape 4 — Générer de la charge et observer

Ouvre deux terminaux simultanément :

bash — Terminal 1 : Observer le HPA
$ kubectl apply -f hpa-demo.yaml
$ kubectl apply -f hpa.yaml

# Surveiller le HPA (rafraîchit toutes les 5s)
$ watch kubectl get hpa php-apache-hpa
# NAME             REFERENCE         TARGETS   MINPODS  MAXPODS  REPLICAS
# php-apache-hpa   Deployment/php    0%/50%    1        8        1
bash — Terminal 2 : Générer la charge
# Lancer une boucle infinie de requêtes HTTP
$ kubectl run -it load-gen --image=busybox --rm -- \
    /bin/sh -c "while true; do wget -q -O- http://php-apache; done"

# Dans le terminal 1, tu verras :
# TARGETS : 0%/50% → 75%/50% → 125%/50%
# REPLICAS : 1 → 2 → 4 → 6 (scaling UP automatique !)

# Arrêter la charge (Ctrl+C dans le terminal 2)
# Après quelques minutes :
# REPLICAS : 6 → 3 → 1 (scaling DOWN automatique !)
📊
Comprendre le calcul du HPA
Formule : replicas_désiré = ceil(replicas_actuel × (CPU_actuel / CPU_cible))
Exemple : 2 pods, CPU à 150%, cible 50% → ceil(2 × 150/50) = 6 pods
Module 06

Health Checks — Liveness, Readiness & Startup Probes

Les Probes sont des mécanismes de vérification de santé que Kubernetes effectue régulièrement. Elles permettent à K8s de savoir si ton application est vivante, prête à recevoir du trafic, et si elle a correctement démarré.

ProbeQuestion poséeAction si échec
livenessProbe L'application est-elle encore vivante ? Redémarre le conteneur (CrashLoopBackOff)
readinessProbe L'application est-elle prête à recevoir du trafic ? Retire le Pod du Service (plus de trafic vers lui)
startupProbe L'application a-t-elle fini son démarrage ? Désactive les autres probes tant que pas prête
❤️ TP 6.1 — Implémenter les 3 types de Probes
Intermédiaire ⏱ 35 min
Objectif Déployer une application avec les 3 types de probes configurées. Simuler une panne et observer comment Kubernetes réagit différemment selon la probe qui échoue.
yaml — app-with-probes.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-probes
spec:
  replicas: 2
  selector:
    matchLabels: { app: app-probes }
  template:
    metadata:
      labels: { app: app-probes }
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports: [{ containerPort: 80 }]

          # ── Startup Probe : délai de démarrage ──
          startupProbe:
            httpGet:
              path: /
              port: 80
            failureThreshold: 30    # 30 essais max (30 × 10s = 5min de délai)
            periodSeconds: 10

          # ── Liveness Probe : est-il encore vivant ? ──
          livenessProbe:
            httpGet:
              path: /         # Vérification HTTP GET sur /
              port: 80
            initialDelaySeconds: 15  # Attendre 15s avant de commencer
            periodSeconds: 10        # Vérifier toutes les 10s
            failureThreshold: 3       # Redémarrer après 3 échecs consécutifs
            timeoutSeconds: 5        # Timeout de 5s par sonde

          # ── Readiness Probe : est-il prêt pour le trafic ? ──
          readinessProbe:
            httpGet:
              path: /ready      # Endpoint dédié (ici 404 = pas prêt)
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3

Simuler des pannes pour observer les comportements

bash — Scénario 1 : Liveness Probe échoue
$ kubectl apply -f app-with-probes.yaml

# Obtenir le nom d'un pod
$ kubectl get pods
# app-probes-7dc9f-xxxxx

# Entrer dans le pod et supprimer le fichier index.html
# → La liveness probe va échouer → Kubernetes redémarre le conteneur
$ kubectl exec -it app-probes-7dc9f-xxxxx -- rm /usr/share/nginx/html/index.html

# Observer les RESTARTs augmenter
$ kubectl get pods -w
# NAME                  READY  RESTARTS
# app-probes-7dc9f-xxx  1/1    0
# app-probes-7dc9f-xxx  0/1    0   ← probe échoue
# app-probes-7dc9f-xxx  1/1    1   ← redémarré !
bash — Scénario 2 : Readiness Probe échoue
# Voir l'état READY (0/1 = pas de trafic mais pod vivant)
$ kubectl describe pod app-probes-7dc9f-xxxxx | grep -A10 Conditions
# Ready       False  → Pod retiré des endpoints du Service
# Initialized True

# Vérifier les endpoints du Service
$ kubectl get endpoints
# NAME         ENDPOINTS
# app-probes   10.244.1.5:80  ← seulement le pod prêt apparaît

NetworkPolicies — Firewall entre Pods

Par défaut, dans un cluster Kubernetes, tous les Pods peuvent communiquer avec tous les Pods, quel que soit le namespace. Les NetworkPolicies ajoutent des règles de filtrage réseau, comme un firewall iptables entre tes microservices.

⚠️
Prérequis : CNI compatible NetworkPolicy Flannel (utilisé dans ce cours) ne supporte pas les NetworkPolicies nativement. Pour ce TP, installe Calico (à la place de Flannel) ou ajoute le plugin Canal.

Remplacer Flannel par Calico :
kubectl delete -f kube-flannel.yml
kubectl apply -f https://docs.projectcalico.org/manifests/calico.yaml

# Politique : la DB n'accepte que le trafic du backend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-only-from-backend
  namespace: database
spec:
  podSelector:                   # S'applique aux pods avec app=db
    matchLabels: { app: db }
  policyTypes: [Ingress]         # Règle sur le trafic entrant
  ingress:
    - from:
        - namespaceSelector:      # Seulement depuis le namespace backend
            matchLabels:
              tier: backend
          podSelector:            # ET seulement les pods app=backend
            matchLabels:
              app: backend

Module 10

Helm — Le gestionnaire de paquets Kubernetes

Helm est à Kubernetes ce qu'APT est à Ubuntu. Il permet de packager, distribuer et installer des applications Kubernetes complexes en une seule commande. Un Chart Helm est un ensemble de fichiers YAML avec des variables, des conditions et des boucles.

📦

Chart

Package Helm. Contient tous les YAML de l'application + un fichier de valeurs.

🚀

Release

Une instance installée d'un Chart. Tu peux installer le même Chart plusieurs fois (prod, staging).

🗂️

Repository

Dépôt de Charts. Comme Docker Hub pour les images. ArtifactHub.io est le principal.

⚙️

Values

Variables de configuration du Chart. Tu les surcharges pour personnaliser le déploiement.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-app   # Nom de la release Helm
  labels:
    app: {{ .Release.Name }}
    chart: {{ .Chart.Name }}-{{ .Chart.Version }}
spec:
  replicas: {{ .Values.replicaCount }}    # Valeur depuis values.yaml
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: {{ .Values.service.port }}
          env:
          {{- range $key, $value := .Values.env }}
            - name: {{ $key }}
              value: {{ $value | quote }}
          {{- end }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
          {{- if .Values.autoscaling.enabled }}
          # HPA géré séparément si activé
          {{- end }}

RBAC — Contrôle d'accès basé sur les rôles

RBAC (Role-Based Access Control) permet de définir précisément qui peut faire quoi sur quelles ressources du cluster. Indispensable pour les équipes multi-développeurs et la sécurité en production.

ObjetPortéeRôle
RoleNamespace spécifiqueDéfinit des permissions dans un namespace
ClusterRoleCluster entierPermissions sur toutes les ressources ou non-namespacées (Nodes)
RoleBindingNamespace spécifiqueAssigne un Role à un utilisateur/groupe
ClusterRoleBindingCluster entierAssigne un ClusterRole globalement
🛡️ TP 13.1 — Créer un utilisateur avec permissions limitées
Avancé ⏱ 50 min
Objectif Créer un utilisateur alice qui peut lire et créer des Pods dans le namespace staging, mais ne peut rien supprimer et n'a aucun accès aux autres namespaces.

Étape 1 — Créer le certificat utilisateur

bash
# Générer une clé privée pour Alice
$ openssl genrsa -out alice.key 2048

# Créer une demande de signature de certificat (CSR)
$ openssl req -new -key alice.key \
    -out alice.csr \
    -subj "/CN=alice/O=developers"
# CN = Common Name (nom utilisateur dans K8s)
# O = Organisation (groupe dans K8s)

# Encoder le CSR en base64
$ CSR=$(cat alice.csr | base64 | tr -d '\n')

Étape 2 — Soumettre le CSR à Kubernetes

yaml — alice-csr.yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: alice-csr
spec:
  request: LS0tLS1CRUdJTi...   # Remplacer par la valeur de $CSR
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400   # 24 heures
  usages:
    - client auth
bash
# Injecter le CSR dans le YAML et appliquer
$ cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: alice-csr
spec:
  request: $CSR
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages: [client auth]
EOF

# Approuver le CSR (en tant qu'admin)
$ kubectl certificate approve alice-csr

# Récupérer le certificat signé
$ kubectl get csr alice-csr -o jsonpath='{.status.certificate}' | base64 -d > alice.crt

Étape 3 — Créer le Role et le RoleBinding

yaml — alice-rbac.yaml
# Namespace staging pour Alice
apiVersion: v1
kind: Namespace
metadata:
  name: staging
---
# Role : permissions dans staging seulement
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: staging
  name: pod-manager
rules:
  - apiGroups: [""]                  # "" = core API group
    resources: ["pods", "pods/log"]  # Ressources autorisées
    verbs: ["get", "list", "watch", "create"]  # PAS delete !
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list"]            # Lecture seule sur les deployments
---
# RoleBinding : assigne le Role à Alice
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: staging
  name: alice-pod-manager
subjects:
  - kind: User
    name: alice              # Correspond au CN du certificat
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-manager
  apiGroup: rbac.authorization.k8s.io

Étape 4 — Configurer kubectl pour Alice

bash
$ kubectl apply -f alice-rbac.yaml

# Ajouter les credentials d'Alice dans kubectl
$ kubectl config set-credentials alice \
    --client-certificate=alice.crt \
    --client-key=alice.key

# Créer un contexte pour Alice
$ kubectl config set-context alice-staging \
    --cluster=kubernetes \
    --namespace=staging \
    --user=alice

# Changer de contexte → utiliser les droits d'Alice
$ kubectl config use-context alice-staging

# Tester les permissions
$ kubectl get pods              # ✅ Autorisé
$ kubectl get pods -n default   # ❌ Forbidden (mauvais namespace)
$ kubectl delete pod mon-pod    # ❌ Forbidden (pas le droit delete)
$ kubectl run test --image=nginx # ✅ Autorisé (create)

# Revenir au contexte admin
$ kubectl config use-context kubernetes-admin@kubernetes

# Vérifier les droits d'Alice (depuis le compte admin)
$ kubectl auth can-i delete pods --namespace=staging --as=alice
# no
$ kubectl auth can-i create pods --namespace=staging --as=alice
# yes

Projet Final 01

Application de Vote — Architecture complète

Ce projet final te fait déployer l'application de vote officielle de Docker (utilisée dans leurs formations). Elle comprend 5 composants : frontend (Python), file de message (Redis), worker (.NET), base de données (PostgreSQL), et interface de résultats (Node.js).

─── ARCHITECTURE : VOTING APP ───
  Navigateur
  ├──── http://worker1:30000 ────→ [vote-app]     (Python Flask)
  │                                     │
  │                               enqueue votes
  │                                     ↓
  │                               [redis]         (Cache)
  │                                     │
  │                               worker consumes
  │                                     ↓
  │                               [worker]        (.NET)
  │                                     │
  │                               write results
  │                                     ↓
  └──── http://worker1:30001 ────→ [result-app]   (Node.js)
                                        │
                                  reads from
                                        ↓
                                  [postgresql]    (DB)
🗳️ Déployer la Voting App complète
Avancé ⏱ 90 min
Objectif Déployer les 5 services en autonomie. Utiliser des Secrets pour les credentials PostgreSQL, un PVC pour la persistence, et tester le scaling du composant vote-app sous charge.
bash — Créer la structure des fichiers
$ mkdir -p voting-app && cd voting-app
# Tu vas créer ces 6 fichiers :
# 1-namespace.yaml
# 2-secrets.yaml
# 3-redis.yaml
# 4-postgres.yaml
# 5-vote-worker.yaml
# 6-result.yaml
yaml — 1-namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: vote
yaml — 2-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: postgres-secret
  namespace: vote
stringData:
  POSTGRES_USER: "postgres"
  POSTGRES_PASSWORD: "vote_secret_2024"
  POSTGRES_DB: "votes"
yaml — 3-redis.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: vote
spec:
  replicas: 1
  selector:
    matchLabels: { app: redis }
  template:
    metadata:
      labels: { app: redis }
    spec:
      containers:
        - name: redis
          image: redis:alpine
          ports: [{ containerPort: 6379, name: redis }]
---
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: vote
spec:
  selector: { app: redis }
  ports: [{ port: 6379, targetPort: 6379 }]
yaml — 4-postgres.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
  namespace: vote
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 500Mi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
  namespace: vote
spec:
  replicas: 1
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
        - name: postgres
          image: postgres:15-alpine
          envFrom:
            - secretRef: { name: postgres-secret }
          ports: [{ containerPort: 5432 }]
          volumeMounts:
            - name: pgdata
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: pgdata
          persistentVolumeClaim:
            claimName: postgres-pvc
---
apiVersion: v1
kind: Service
metadata:
  name: db
  namespace: vote
spec:
  selector: { app: postgres }
  ports: [{ port: 5432, targetPort: 5432 }]
yaml — 5-vote-worker.yaml
# ─── Application de vote (frontend) ───
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vote
  namespace: vote
spec:
  replicas: 2
  selector:
    matchLabels: { app: vote }
  template:
    metadata:
      labels: { app: vote }
    spec:
      containers:
        - name: vote
          image: dockersamples/examplevotingapp_vote
          ports: [{ containerPort: 80 }]
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
---
apiVersion: v1
kind: Service
metadata:
  name: vote
  namespace: vote
spec:
  selector: { app: vote }
  type: NodePort
  ports: [{ port: 80, targetPort: 80, nodePort: 30000 }]
---
# ─── Worker (consomme Redis → écrit dans Postgres) ───
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
  namespace: vote
spec:
  replicas: 1
  selector:
    matchLabels: { app: worker }
  template:
    metadata:
      labels: { app: worker }
    spec:
      containers:
        - name: worker
          image: dockersamples/examplevotingapp_worker

bash — Déploiement et test
# Déployer tout dans l'ordre
$ kubectl apply -f ./voting-app/

# Suivre le démarrage
$ kubectl get pods -n vote -w

# Une fois tous en Running :
# Interface de vote  : http://172.16.25.61:30000
# Interface résultats: http://172.16.25.61:30001

# Scaler le vote-app à 5 réplicas
$ kubectl scale deployment vote -n vote --replicas=5

# Tester le self-healing : supprimer redis
$ kubectl delete pod -l app=redis -n vote
# Le worker redemarre, redis est recréé par le Deployment

# Vérifier que les votes persistent après redémarrage postgres
$ kubectl delete pod -l app=postgres -n vote
# Les résultats sur l'interface doivent être préservés (PVC)
Projet Final 03

Stack complète de production monitorée

Ce projet de fin de cours te fait assembler tout ce que tu as appris en une seule architecture : une application web, sa base de données, le monitoring, la sécurité RBAC et le scaling automatique.

─── ARCHITECTURE PROJET FINAL ───
  namespace: app-prod
  ┌────────────────────────────────────────────────────────────┐
  │  Ingress (HTTPS)                                           │
  │      ├── / → frontend-service (Nginx, 3 replicas + HPA)   │
  │      └── /api → api-service (Node.js, 2 replicas + HPA)   │
  │                      │                                     │
  │              mysql-service (StatefulSet, PVC)              │
  └────────────────────────────────────────────────────────────┘

  namespace: monitoring
  ┌────────────────────────────────────────────────────────────┐
  │  Prometheus (collecte métriques) + Grafana (dashboard)     │
  │  AlertManager (alertes si pods crashent)                   │
  └────────────────────────────────────────────────────────────┘

  namespace: kube-system
  ┌────────────────────────────────────────────────────────────┐
  │  Fluent Bit DaemonSet (collecte logs tous les nodes)       │
  │  Metrics-server (CPU/RAM pour HPA)                         │
  └────────────────────────────────────────────────────────────┘

  RBAC :
  - admin@prod    → tous droits sur app-prod
  - dev@equipe    → lecture seule sur app-prod
  - aucun accès   → namespace monitoring

Cheat Sheet Avancée

Helm

bash
helm repo add <name> <url>          # Ajouter un dépôt
helm search repo <keyword>          # Chercher un chart
helm install <release> <chart>      # Installer
helm install <release> <chart> -f vals.yaml  # Avec valeurs custom
helm upgrade <release> <chart>      # Mettre à jour
helm rollback <release> <revision>  # Revenir en arrière
helm uninstall <release>            # Désinstaller
helm list -A                        # Toutes les releases
helm show values <chart>            # Voir les valeurs par défaut
helm template <release> <chart>     # Voir le YAML généré
helm lint <chart-dir>               # Vérifier un chart

StatefulSets, DaemonSets, Jobs

bash
kubectl get statefulsets               # Lister StatefulSets
kubectl get daemonsets -A              # Lister DaemonSets (tous NS)
kubectl get jobs                       # Lister Jobs
kubectl get cronjobs                   # Lister CronJobs
kubectl create job test --from=cronjob/<name>  # Forcer CronJob
kubectl patch cronjob <name> -p '{"spec":{"suspend":true}}'  # Suspendre

Scaling & Autoscaling

bash
kubectl scale deploy <name> --replicas=N   # Scaling manuel
kubectl get hpa                            # Voir les HPA
kubectl describe hpa <name>               # Détails et événements HPA
kubectl top pods                           # CPU/RAM des pods
kubectl top nodes                          # CPU/RAM des nodes

RBAC

bash
kubectl get roles,rolebindings -A          # Tous les rôles
kubectl auth can-i <verb> <resource>      # Tester ses droits
kubectl auth can-i get pods --as=alice     # Tester les droits d'un user
kubectl auth can-i --list                  # Lister toutes ses permissions

Debugging avancé

bash
kubectl get events --sort-by=.lastTimestamp -A  # Événements récents
kubectl debug pod/<name> -it --image=busybox    # Debug sidecar
kubectl describe node <name> | grep -A5 Events  # Problèmes node
kubectl get pods --field-selector status.phase=Failed  # Pods en échec
kubectl logs <pod> --previous                  # Logs avant crash
kubectl cp <pod>:/path/file ./local-file        # Copier depuis un pod
kubectl cp ./local-file <pod>:/path/file        # Copier vers un pod
