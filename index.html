Chapitre 01

Pourquoi Kubernetes ? Docker ne suffit-il pas ?

Tu connais Docker : tu crées une image, tu lances un conteneur, et ton application tourne. Mais que se passe-t-il quand tu as 50 conteneurs sur 10 machines ? Quand un conteneur plante à 3h du matin ? Quand tu dois mettre à jour ton application sans interruption de service ? C'est là qu'intervient Kubernetes.

💡
Analogie simple Docker, c'est un camion de livraison. Kubernetes, c'est la compagnie de transport qui gère toute la flotte : qui conduit quoi, sur quel itinéraire, comment se dérouter si un camion tombe en panne.

Ce que Docker fait bien

Docker excelle à :

  • Créer et empaqueter des images de conteneurs
  • Lancer un ou quelques conteneurs sur une seule machine
  • Développement local et tests
  • Docker Compose pour des environnements multi-conteneurs simples

Les limites de Docker seul en production

Problème Avec Docker seul Avec Kubernetes
Un conteneur plante Il reste mort jusqu'à intervention manuelle Kubernetes le redémarre automatiquement
Beaucoup de trafic Tu dois créer des conteneurs manuellement Auto-scaling : K8s crée des copies automatiquement
Mise à jour de l'app Temps d'arrêt inévitable Rolling update : zéro downtime
Répartition de charge Nécessite un outil externe Load balancing intégré
Plusieurs serveurs Gestion manuelle et complexe Kubernetes gère un cluster multi-serveurs

Kubernetes en une phrase

Kubernetes (souvent abrégé K8s, car il y a 8 lettres entre le K et le s) est un orchestrateur de conteneurs open source créé par Google en 2014, aujourd'hui maintenu par la Cloud Native Computing Foundation (CNCF). Il automatise le déploiement, la mise à l'échelle et la gestion des applications conteneurisées.

🎯
Bonne nouvelle pour toi Kubernetes utilise les mêmes images Docker que tu connais déjà. Rien à réapprendre de ce côté-là. Ce sont uniquement les concepts d'orchestration qui sont nouveaux.
Chapitre 02

Les composants du Control Plane

🧠

API Server

Le point d'entrée de tout. Chaque commande kubectl passe par lui. C'est le cerveau qui reçoit et valide toutes les requêtes du cluster.

📋

Scheduler

Décide sur quel worker un nouveau Pod va être lancé, en fonction des ressources disponibles (CPU, RAM).

🔄

Controller Manager

Surveille l'état du cluster. Si tu demandes 3 réplicas d'un Pod et qu'un plante, il en recrée un autre automatiquement.

🗄️

etcd

La base de données du cluster. Stocke toute la configuration et l'état de Kubernetes. C'est le composant le plus critique à sauvegarder.

Les composants d'un Worker Node

🤖

kubelet

L'agent Kubernetes qui tourne sur chaque worker. Il communique avec l'API Server et s'assure que les conteneurs tournent comme demandé.

🌐

kube-proxy

Gère le réseau du node. Il s'occupe des règles de routage pour que les services soient accessibles depuis l'intérieur et l'extérieur du cluster.

🐋

Container Runtime

Le moteur qui lance réellement les conteneurs. Par défaut avec Kubernetes 1.20+ : containerd (pas Docker directement).

📦

Pod

La plus petite unité déployable dans K8s. Un Pod contient un ou plusieurs conteneurs qui partagent le même réseau et stockage.

📌
Pod vs Conteneur : la différence clé En Docker tu travailles directement avec des conteneurs. En Kubernetes, tu travailles avec des Pods. Un Pod est une enveloppe autour d'un ou plusieurs conteneurs. Dans 95% des cas, un Pod = un conteneur. Les pods partagent le même espace réseau (même IP) et peuvent partager des volumes.

Chapitre 03

Installation sur Ubuntu Server 24.04 LTS

Nous allons installer un cluster Kubernetes avec kubeadm, l'outil officiel de bootstrapping. Pour ce cours, tu peux utiliser une ou plusieurs machines virtuelles (VMs) ou physiques sous Ubuntu Server 24.04 LTS.

⚠️
Pour les tests mono-machine Si tu n'as qu'un seul PC/serveur, tu peux utiliser Minikube ou K3s qui sont plus simples à installer. Ce chapitre couvre kubeadm pour un vrai cluster de production. La section "Alternative avec Minikube" plus bas est recommandée pour débuter.

Prérequis système

Chaque machine du cluster (master et workers) doit respecter :

  • Ubuntu Server 24.04 LTS (noble)
  • Minimum 2 CPU et 2 Go de RAM par machine
  • Minimum 20 Go d'espace disque
  • Connexion réseau entre toutes les machines
  • Swap désactivé (obligatoire pour Kubernetes)
  • Accès root ou sudo
🚀
Recommandé pour débuter : Minikube sur une seule machine Minikube crée un cluster Kubernetes complet dans une seule VM ou directement sur ton Ubuntu. C'est parfait pour apprendre sans avoir plusieurs serveurs.

Option A — Installation avec Minikube (recommandée pour apprendre)

1

Installer kubectl (le client de ligne de commande)

Installation de kubectl

kubectl est l'outil en ligne de commande qui te permet de communiquer avec ton cluster Kubernetes. C'est comme le client Docker (docker) mais pour Kubernetes.

bash 
# Télécharger la dernière version stable de kubectl
$ curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"

# Rendre le binaire exécutable
$ chmod +x kubectl

# Déplacer dans /usr/local/bin pour qu'il soit disponible partout
$ sudo mv kubectl /usr/local/bin/

# Vérifier que kubectl est installé correctement
$ kubectl version --client
# Output : Client Version: v1.29.x
Explication des commandes
curl -LO-L suit les redirections HTTP, -O sauvegarde sous le nom original
$(curl ...)Substitution de commande : exécute la commande interne et insère le résultat (la version stable actuelle)
chmod +xAjoute le droit d'exécution sur le fichier téléchargé
sudo mv ... /usr/local/bin/Déplace dans le PATH système pour que tous les utilisateurs puissent l'utiliser

3

Installer Docker (driver recommandé pour Minikube)

Pourquoi Docker ?

Minikube peut utiliser plusieurs drivers (VirtualBox, KVM, Docker…). Le driver Docker est le plus simple sur Ubuntu Desktop/Server : il ne nécessite pas de virtualisation matérielle et tourne directement via les conteneurs.

bash 
# 1. Mettre à jour les paquets et installer les dépendances
$ sudo apt-get update
$ sudo apt-get install -y ca-certificates curl gnupg

# 2. Ajouter la clé GPG officielle de Docker
$ sudo install -m 0755 -d /etc/apt/keyrings
$ curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
$ sudo chmod a+r /etc/apt/keyrings/docker.gpg

# 3. Ajouter le dépôt Docker (Ubuntu 24.04 noble)
$ echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 4. Installer Docker Engine
$ sudo apt-get update
$ sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 5. Ajouter ton utilisateur au groupe docker (sans sudo)
$ sudo usermod -aG docker $USER

# 6. Appliquer le changement de groupe sans se déconnecter
$ newgrp docker

# 7. Vérifier que Docker fonctionne
$ docker run hello-world
# Output attendu : "Hello from Docker!"
Explication des étapes clés
keyrings/docker.gpgClé cryptographique pour vérifier l'authenticité des paquets Docker
$(dpkg --print-architecture)Détecte automatiquement l'architecture : amd64, arm64…
$VERSION_CODENAMEVariable du fichier /etc/os-release : vaut noble sur Ubuntu 24.04
usermod -aG dockerAjoute l'utilisateur au groupe docker pour lancer Docker sans sudo
newgrp dockerApplique le nouveau groupe dans la session courante sans se déconnecter
⚠️
Groupe docker appliqué Si tu ne lances pas newgrp docker, tu devras te déconnecter/reconnecter pour que Minikube puisse utiliser Docker sans erreur de permission.
4

Démarrer Minikube avec Docker

Puisque tu connais déjà Docker, Minikube peut l'utiliser comme driver (moteur de virtualisation) :

bash

Explication : minikube start
--driver=dockerUtilise Docker comme hyperviseur pour créer le node Kubernetes
--cpus=2Optionnel : nombre de CPUs alloués (défaut : 2)
--memory=4gOptionnel : RAM allouée (défaut : 2g)

Option B — Installation avec kubeadm (cluster multi-nodes)

Pour un vrai cluster avec plusieurs machines, voici les étapes complètes. Ces commandes sont à exécuter sur toutes les machines sauf indication contraire.

Étape 1 — Préparation du système (sur toutes les machines)

bash 
# ─── 1. Désactiver le swap (Kubernetes l'exige) ───
$ sudo swapoff -a

# Désactiver le swap de façon permanente (commenter la ligne swap)
$ sudo sed -i 's/^.*swap.*$/#&/' /etc/fstab

# ─── 2. Charger les modules kernel nécessaires ───
$ cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

$ sudo modprobe overlay       # Module pour containerd
$ sudo modprobe br_netfilter  # Module pour le réseau des Pods

# ─── 3. Configurer les paramètres réseau du kernel ───
$ cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

# Appliquer les paramètres sans redémarrer
$ sudo sysctl --system
Pourquoi ces configurations ?
swapoff -aKubernetes a besoin de contrôler précisément la mémoire des Pods. Le swap perturbe ces calculs.
overlayModule du système de fichiers utilisé par containerd pour les couches des images.
br_netfilterPermet à iptables de voir le trafic réseau des bridges (nécessaire pour le réseau Kubernetes).
ip_forward = 1Permet au nœud de faire passer des paquets réseau entre les interfaces (routage pour les Pods).

Étape 2 — Installer containerd (sur toutes les machines)

bash 
# Installer containerd via les dépôts Docker officiels

# Installer containerd
$ sudo apt-get update
$ sudo apt-get install -y containerd.io

# Générer la configuration par défaut de containerd
$ sudo mkdir -p /etc/containerd
$ containerd config default | sudo tee /etc/containerd/config.toml

# Activer SystemdCgroup (nécessaire pour K8s)
$ sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

# Redémarrer et activer containerd
$ sudo systemctl restart containerd
$ sudo systemctl enable containerd
$ sudo systemctl status containerd   # Doit afficher "active (running)"

Étape 3 — Installer kubeadm, kubelet, kubectl (sur toutes les machines)

bash 
# Ajouter la clé GPG de Kubernetes
$ curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.29/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

# Ajouter le dépôt Kubernetes
$ echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.29/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list

# Mettre à jour et installer les trois outils
$ sudo apt-get update
$ sudo apt-get install -y kubelet kubeadm kubectl

# Empêcher les mises à jour automatiques (stabilité)
$ sudo apt-mark hold kubelet kubeadm kubectl
kubeadm vs kubelet vs kubectl — les différences
kubeadmOutil d'installation et d'initialisation du cluster. Utilisé une seule fois pour bootstrapper. Comme un "installateur".
kubeletService système qui tourne en permanence sur chaque node. Il exécute les ordres du Control Plane et gère les Pods locaux.
kubectlClient CLI que TU utilises pour envoyer des commandes au cluster. C'est ton interface de travail quotidien.
apt-mark holdBloque les mises à jour automatiques de ces paquets pour éviter une version incompatible lors d'un apt upgrade.

Étape 4 — Initialiser le Control Plane (sur le master UNIQUEMENT)

bash 
# Initialiser le cluster (remplace 192.168.1.100 par l'IP de ton master)
$ sudo kubeadm init \
    --apiserver-advertise-address=192.168.1.100 \
    --pod-network-cidr=10.244.0.0/16

À la fin de l'init, vous avez un retour du type : "kubeadm join 192.168.3.145:6443 
--token tcekc8.ufhw7n92xj8psxbg
      --discovery-token-ca-cert-hash
sha256:2f199069f92bef6a7b08e7cdd0563039a7b8fae310c963617ed2623ab520843f"
        Noter le token généré ainsi que les chiffres apres sha256 ! 
$ mkdir -p $HOME/.kube
$ sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
$ sudo chown $(id -u):$(id -g) $HOME/.kube/config
Explication : kubeadm init
--apiserver-advertise-addressL'IP sur laquelle l'API Server écoute. Les workers se connecteront à cette adresse. Utilise l'IP de ta machine master sur le réseau local.
--pod-network-cidr=10.244.0.0/16La plage d'adresses IP réservée pour les Pods. 10.244.0.0/16 est requis pour le plugin réseau Flannel (le plus simple).
mkdir ~/.kube && cp admin.confLe kubeconfig est le fichier de configuration qui permet à kubectl de s'authentifier auprès du cluster. Sans cette étape, kubectl ne peut pas communiquer.

Étape 5 — Installer le plugin réseau Flannel (sur le master)

bash 
# Flannel gère le réseau entre les Pods sur différents nodes
$ kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml

# Vérifier que les pods système démarrent
$ kubectl get pods -n kube-system
# Attendre que tous les pods soient "Running"

Étape 6 — Rejoindre les Workers (sur chaque worker)

bash 
# La commande join a été affichée à la fin de "kubeadm init"
# Elle ressemble à :
$ sudo kubeadm join 192.168.1.100:6443 \
    --token abcdef.1234567890abcdef \
    --discovery-token-ca-cert-hash sha256:xxxxxxxxxxxxxxxxxxxxxxxx

# Si tu n'as plus le token, regénère-le depuis le master :
$ kubeadm token create --print-join-command

# Vérifier que le worker a rejoint (depuis le master) :
$ kubectl get nodes
# NAME       STATUS   ROLES           AGE
# master     Ready    control-plane   10m
# worker1    Ready    <none>          2m
Chapitre 04

kubectl — Maîtriser la CLI Kubernetes

kubectl est ton outil principal. Apprendre Kubernetes, c'est d'abord apprendre kubectl. La syntaxe générale est :

syntaxe 
kubectl [action] [ressource] [nom] [options]

# Exemples :
kubectl get     pods                    # Lister tous les pods
kubectl get     pods mon-pod             # Voir un pod spécifique
kubectl describe pod mon-pod             # Détails complets
kubectl delete  pod mon-pod             # Supprimer
kubectl apply   -f mon-fichier.yaml    # Créer/mettre à jour depuis fichier

Commandes kubectl essentielles

kubectl get — Lister les ressources

La commande la plus utilisée. Affiche les ressources du cluster.

bash 
$ kubectl get pods                          # Pods du namespace courant
$ kubectl get pods -A                       # Pods de TOUS les namespaces
$ kubectl get pods -o wide                 # + colonnes IP et NODE
$ kubectl get pods -o yaml                 # Format YAML complet
$ kubectl get pods -w                       # Mode watch (mise à jour temps réel)
$ kubectl get pods -n kube-system           # Dans le namespace kube-system
$ kubectl get all                           # Pods + Services + Deployments
$ kubectl get nodes                         # Lister les nodes
$ kubectl get services                      # Lister les services
$ kubectl get deployments                   # Lister les deployments
-A / --all-namespacesAffiche les ressources dans tous les namespaces
-o wideAffiche des colonnes supplémentaires (IP, Node...)
-o yamlSortie en format YAML (utile pour voir la configuration complète)
-o jsonSortie en format JSON (utile pour scripts)
-w / --watchMode surveillance : rafraîchit l'affichage automatiquement
-n / --namespaceSpécifie le namespace cible
-l app=nginxFiltre par label (ex: tous les pods avec le label app=nginx)
kubectl describe — Détails d'une ressource

Affiche les informations détaillées d'une ressource : configuration, événements, erreurs. C'est la commande à utiliser quand quelque chose ne va pas.

bash 
$ kubectl describe pod mon-pod
$ kubectl describe node mon-node
$ kubectl describe deployment mon-deploy
$ kubectl describe service mon-service

# La section "Events" en bas est précieuse pour débugger !
kubectl apply — Créer ou mettre à jour depuis un fichier YAML

C'est la façon "déclarative" de travailler avec Kubernetes. Tu écris ce que tu veux dans un YAML, et K8s s'occupe de le réaliser.

bash 
$ kubectl apply -f pod.yaml              # Créer/mettre à jour depuis un fichier
$ kubectl apply -f ./dossier/            # Tous les YAML d'un dossier
$ kubectl apply -f https://url/file.yaml  # Depuis une URL
-f / --filenameChemin vers le fichier YAML (ou dossier, ou URL)
--dry-run=clientSimule l'application sans rien créer réellement (vérification syntaxique)
--recordEnregistre la commande dans l'historique de la ressource
kubectl logs — Voir les logs d'un conteneur

Équivalent de docker logs. Indispensable pour débugger.

bash 
$ kubectl logs mon-pod                    # Logs du pod
$ kubectl logs mon-pod -f                 # Suivre les logs en temps réel (follow)
$ kubectl logs mon-pod --tail=50          # Les 50 dernières lignes
$ kubectl logs mon-pod --since=1h        # Logs depuis 1 heure
$ kubectl logs mon-pod -c mon-container   # Si le pod a plusieurs conteneurs
$ kubectl logs -l app=nginx              # Logs de tous les pods avec ce label
-f / --followMode streaming : affiche les nouvelles lignes au fur et à mesure
--tail=NN dernières lignes seulement
--since=durationLogs depuis une durée (1h, 30m, 5s...)
-c containerSpécifie le conteneur si le Pod en contient plusieurs
--previousLogs du précédent conteneur (utile si le pod a crashé)
kubectl exec — Exécuter une commande dans un conteneur

Équivalent de docker exec. Permet d'entrer dans un conteneur ou d'y exécuter des commandes.

bash 
$ kubectl exec -it mon-pod -- /bin/bash   # Shell interactif
$ kubectl exec -it mon-pod -- /bin/sh    # Si bash n'est pas dispo
$ kubectl exec mon-pod -- ls /app         # Commande sans mode interactif
$ kubectl exec -it mon-pod -c mon-container -- bash  # Conteneur spécifique
-it-i = mode interactif (stdin ouvert), -t = alloue un pseudo-TTY (terminal). Toujours mettre ensemble pour un shell.
--Séparateur entre les options kubectl et la commande à exécuter dans le conteneur. Important pour éviter les ambiguïtés.
-c containerCible un conteneur spécifique dans un Pod multi-conteneurs
kubectl delete — Supprimer des ressources
bash 
$ kubectl delete pod mon-pod              # Supprimer un pod
$ kubectl delete -f pod.yaml              # Supprimer ce qui est défini dans le YAML
$ kubectl delete pod --all               # Supprimer TOUS les pods
$ kubectl delete deployment mon-deploy    # Supprimer un deployment
$ kubectl delete -l app=nginx             # Supprimer par label
⚠️
Si tu supprimes un Pod qui appartient à un Deployment, Kubernetes le recrée automatiquement. Pour vraiment supprimer, il faut supprimer le Deployment.
Chapitre 05

Les Pods — L'unité de base

Le Pod est l'objet le plus fondamental de Kubernetes. C'est un wrapper autour d'un ou plusieurs conteneurs. En pratique, on ne crée presque jamais des Pods directement (on utilise des Deployments), mais comprendre les Pods est indispensable.

Créer un Pod en ligne de commande (méthode impérative)

bash 
# Lancer un pod Nginx (comme "docker run nginx")
$ kubectl run mon-nginx --image=nginx

# Vérifier que le pod est lancé
$ kubectl get pods
# NAME        READY   STATUS    RESTARTS   AGE
# mon-nginx   1/1     Running   0          30s

# Voir les détails du pod
$ kubectl describe pod mon-nginx
Explication : kubectl run
mon-nginxNom du Pod. Doit être unique dans le namespace.
--image=nginxImage Docker à utiliser (depuis Docker Hub par défaut)
--port=80Optionnel : documente le port exposé (n'ouvre pas vraiment le port)
--env="VAR=valeur"Définir une variable d'environnement
--labels="app=web"Ajouter des labels au Pod
--restart=NeverCrée un Pod simple (sans ReplicaSet). Par défaut crée un Deployment.
--rmSupprime le Pod quand il termine (utile pour des pods de test)

Créer un Pod avec un fichier YAML (méthode déclarative)

La méthode recommandée est toujours d'écrire un fichier YAML. Cela permet de versionner ta configuration, de la partager, et de la reproduire facilement.

yaml — mon-pod.yaml 
apiVersion: v1                    # Version de l'API Kubernetes pour cet objet
kind: Pod                          # Type de ressource
metadata:                           # Métadonnées de l'objet
  name: mon-pod-nginx               # Nom unique dans le namespace
  labels:                           # Labels : étiquettes clé=valeur
    app: web                        # Utilisé pour sélectionner ce pod
    env: production
spec:                               # Spécification : ce qu'on veut
  containers:                       # Liste des conteneurs du Pod
    - name: nginx                   # Nom du conteneur dans le Pod
      image: nginx:1.25             # Image Docker (toujours spécifier la version !)
      ports:                        # Ports exposés (documentation uniquement)
        - containerPort: 80
      resources:                    # Limites de ressources
        requests:                   # Minimum garanti
          memory: "64Mi"
          cpu: "100m"             # 100 millicores = 0.1 CPU
        limits:                     # Maximum autorisé
          memory: "128Mi"
          cpu: "500m"             # 500 millicores = 0.5 CPU
      env:                          # Variables d'environnement
        - name: NGINX_PORT
          value: "80"
Anatomie d'un YAML Kubernetes
apiVersionVersion de l'API K8s pour ce type d'objet. Les Pods = v1. Les Deployments = apps/v1.
kindType d'objet K8s : Pod, Deployment, Service, ConfigMap...
metadata.nameNom unique de la ressource dans son namespace.
metadata.labelsPaires clé-valeur libres. Permettent de sélectionner et filtrer les ressources.
specLa spécification : ce que tu veux que Kubernetes crée/gère.
resources.requestsRessources minimales garanties. Le Scheduler utilise ça pour choisir le Node.
resources.limitsMaximum autorisé. Si le conteneur dépasse, il est tué (OOMKilled pour la RAM).
cpu: "100m"Millicores CPU. 1000m = 1 CPU. 100m = 10% d'un CPU.
bash 
# Appliquer le fichier YAML
$ kubectl apply -f mon-pod.yaml

# Vérifier le pod
$ kubectl get pods -o wide

# Voir les logs
$ kubectl logs mon-pod-nginx

# Entrer dans le pod
$ kubectl exec -it mon-pod-nginx -- /bin/bash

# Supprimer le pod
$ kubectl delete pod mon-pod-nginx
# ou
$ kubectl delete -f mon-pod.yaml

Comprendre les statuts d'un Pod

StatutSignificationAction
PendingEn attente de planification sur un NodeNormal si bref, vérifier les ressources si long
ContainerCreatingImage en cours de téléchargementNormal, attendre
RunningPod en cours d'exécution ✅Tout va bien

CrashLoopBackOffLe conteneur plante en bouclekubectl logs --previous pour voir l'erreur

Chapitre 06

Les Deployments — Gérer des applications en production

En production, on n'utilise jamais des Pods nus. On utilise des Deployments. Un Deployment te permet de :

  • Lancer N réplicas (copies) de ton Pod
  • Gérer les mises à jour sans interruption (Rolling Updates)
  • Revenir en arrière (Rollback) si une mise à jour pose problème
  • Avoir une auto-réparation : si un Pod plante, K8s en recrée un
🔗
Chaîne de dépendances Deployment → ReplicaSet → Pods. Tu crées un Deployment, qui crée un ReplicaSet, qui crée et maintient les Pods. Tu n'interagis qu'avec le Deployment dans la pratique.

Créer un Deployment YAML

yaml — deployment-nginx.yaml 
apiVersion: apps/v1              # Les Deployments sont dans le groupe "apps"
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3                    # Nombre de copies du Pod à maintenir
  selector:                      # Comment le Deployment identifie "ses" Pods
    matchLabels:
      app: nginx                 # Gère les Pods avec ce label
  strategy:                      # Stratégie de mise à jour
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1               # Max pods supplémentaires pendant la MAJ
      maxUnavailable: 0          # Zéro pod indisponible (zéro downtime)
  template:                      # Template du Pod à créer
    metadata:
      labels:
        app: nginx               # DOIT correspondre au selector.matchLabels
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi"
          readinessProbe:             # Vérifie si le pod est prêt à recevoir du trafic
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
Champs importants du Deployment
replicas: 3Kubernetes va toujours maintenir 3 Pods en vie. Si un plante, il en recrée un autre.
selector.matchLabelsLe Deployment cherche des Pods avec ce label pour les gérer. Doit correspondre exactement aux labels du template.
strategy.RollingUpdateMise à jour progressive : crée de nouveaux Pods avant de supprimer les anciens.
maxSurge: 1Pendant une MAJ, K8s peut créer 1 Pod en plus (4 au lieu de 3) temporairement.
maxUnavailable: 0Zéro Pod indisponible pendant la MAJ = zero downtime.
readinessProbeK8s sonde le pod régulièrement. Si non prêt, aucun trafic ne lui est envoyé.
templateLe modèle de Pod que le Deployment va créer et répliquer.

Opérations sur un Deployment

bash 
# ─── Créer le deployment ───
$ kubectl apply -f deployment-nginx.yaml

# ─── Suivre le déploiement en temps réel ───
$ kubectl rollout status deployment/nginx-deployment
# Waiting for deployment "nginx-deployment" rollout to finish: 2 of 3 new replicas updated...
# deployment "nginx-deployment" successfully rolled out

# ─── Voir le deployment ───
$ kubectl get deployment nginx-deployment
# NAME               READY   UP-TO-DATE   AVAILABLE   AGE
# nginx-deployment   3/3     3            3           1m

# ─── Scaler : changer le nombre de réplicas ───
$ kubectl scale deployment nginx-deployment --replicas=5

# ─── Mettre à jour l'image (rolling update) ───
$ kubectl set image deployment/nginx-deployment nginx=nginx:1.26
# Les anciens pods sont remplacés progressivement par les nouveaux

# ─── Voir l'historique des déploiements ───
$ kubectl rollout history deployment/nginx-deployment

# ─── Rollback : revenir à la version précédente ───
$ kubectl rollout undo deployment/nginx-deployment

# Revenir à une version spécifique
$ kubectl rollout undo deployment/nginx-deployment --to-revision=2
Commandes rollout expliquées
rollout statusAffiche la progression d'un déploiement en cours. Bloque tant que le rollout n'est pas terminé.
rollout historyListe les révisions du deployment. Chaque apply ou set image crée une révision.
rollout undoRevient à la révision précédente. Utile si une mise à jour cause des problèmes.
scale --replicas=NChange le nombre de réplicas immédiatement. K8s crée ou supprime des Pods pour atteindre N.
set imageChange l'image d'un conteneur dans un deployment et déclenche un rolling update.
Chapitre 07

Les Services — Exposer les applications

Les Pods ont des adresses IP qui changent à chaque redémarrage. Un Service crée une adresse IP stable et un DNS stable pour accéder à un groupe de Pods. Il joue aussi le rôle de load balancer entre les réplicas.

🌐
Sans Service : Pod A connaît l'IP 10.244.1.5 de Pod B. Pod B redémarre, nouvelle IP 10.244.1.9. Pod A ne peut plus communiquer.

Avec Service : Pod A contacte le Service "backend" sur une IP stable. Le Service redirige vers le bon Pod, peu importe son IP.

Les 4 types de Services

TypeAccessible depuisUsage typique
ClusterIP Intérieur du cluster uniquement Communication entre microservices internes
NodePort IP du Node + port fixe (30000–32767) Développement, tests, accès direct
LoadBalancer IP publique fournie par le cloud Production sur AWS/GCP/Azure
ExternalName N/A (DNS alias) Pointer vers un service externe via DNS

Service ClusterIP (par défaut)

yaml — service-clusterip.yaml 
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:                    # Sélectionne les pods avec ce label
    app: nginx
  ports:
    - protocol: TCP
      port: 80               # Port du Service (visible côté client)
      targetPort: 80         # Port du conteneur dans le Pod
  type: ClusterIP             # Par défaut si omis

Service NodePort (accès depuis l'extérieur)

yaml — service-nodeport.yaml 
apiVersion: v1
kind: Service
metadata:
  name: nginx-nodeport
spec:
  selector:
    app: nginx
  ports:
    - protocol: TCP
      port: 80               # Port interne au cluster
      targetPort: 80         # Port du conteneur
      nodePort: 30080        # Port sur chaque Node (30000-32767)
  type: NodePort
💻
Avec Minikube : accéder au NodePort minikube service nginx-nodeport --url — donne l'URL complète pour accéder au service depuis ton navigateur.

Commandes Service

bash 
# Créer le service
$ kubectl apply -f service-nodeport.yaml

# Lister les services
$ kubectl get services
# NAME             TYPE       CLUSTER-IP    EXTERNAL-IP  PORT(S)       AGE
# nginx-nodeport   NodePort   10.96.45.11   <none>       80:30080/TCP  1m

# Accéder au service avec Minikube
$ minikube service nginx-nodeport --url

# Forwarder un port localement (pour tester rapidement)
$ kubectl port-forward service/nginx-nodeport 8080:80
# Maintenant accessible sur http://localhost:8080
kubectl port-forward

Crée un tunnel entre ton poste local et un Service ou Pod dans le cluster. Très utile pour tester sans exposer publiquement.

service/nginx-nodeportForwarder vers le Service (peut aussi faire pod/mon-pod)
8080:80Port local 8080 → Port du Service 80
--address=0.0.0.0Écoute sur toutes les interfaces (pas seulement localhost)

Les Namespaces — Isolation logique

Les Namespaces permettent de diviser un cluster en environnements logiques isolés. C'est comme avoir plusieurs "projets" Docker Compose sur la même machine, mais avec un niveau d'isolation réseau et de permissions configurables.

Chapitre 09

ConfigMaps — Configuration externe

Un ConfigMap stocke des données de configuration non sensibles (URLs, noms de base de données, paramètres d'application) séparément du code. L'idée : ne pas hardcoder la configuration dans les images Docker.

yaml — configmap.yaml 
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  # Clés simples (variables d'environnement)
  DATABASE_HOST: "mysql-service"
  DATABASE_PORT: "3306"
  APP_ENV: "production"
  LOG_LEVEL: "info"
  # Fichier de configuration entier
  nginx.conf: |
    server {
        listen 80;
        server_name localhost;
        location / {
            root /usr/share/nginx/html;
        }
    }

Utiliser un ConfigMap dans un Pod

yaml — pod-with-configmap.yaml 
spec:
  containers:
    - name: mon-app
      image: mon-image:1.0
      env:
        # Méthode 1 : une valeur spécifique
        - name: DATABASE_HOST
          valueFrom:
            configMapKeyRef:
              name: app-config    # Nom du ConfigMap
              key: DATABASE_HOST   # Clé dans le ConfigMap
      envFrom:
        # Méthode 2 : toutes les clés du ConfigMap en variables d'env
        - configMapRef:
            name: app-config
      volumeMounts:
        # Méthode 3 : monter comme fichier
        - name: config-volume
          mountPath: /etc/nginx/conf.d
  volumes:
    - name: config-volume
      configMap:
        name: app-config
Chapitre 10

Secrets — Données sensibles

Les Secrets sont comme des ConfigMaps, mais pour les données sensibles (mots de passe, tokens, clés API). Ils sont encodés en Base64 dans K8s.

⚠️
Base64 ≠ Chiffrement ! Les Secrets Kubernetes sont encodés en Base64, pas chiffrés. Ils sont plus sécurisés que ConfigMaps (accès RBAC distinct, pas affichés par défaut), mais pour une vraie sécurité en production, utilise Sealed Secrets ou HashiCorp Vault.

Créer un Secret

bash 
# Méthode 1 : en ligne de commande (K8s encode automatiquement)
$ kubectl create secret generic db-secret \
    --from-literal=username=admin \
    --from-literal=password=MonMotDePasse123

# Méthode 2 : depuis des fichiers
$ kubectl create secret generic tls-secret \
    --from-file=tls.crt=./cert.crt \
    --from-file=tls.key=./cert.key

# Encoder manuellement en base64 pour un YAML
$ echo -n "MonMotDePasse123" | base64
# TW9uTW90RGVQYXNzZTEyMw==
yaml — secret.yaml 
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque          # Type générique (autres types: kubernetes.io/tls, etc.)
data:
  # Valeurs encodées en base64 !
  username: YWRtaW4=                      # echo -n "admin" | base64
  password: TW9uTW90RGVQYXNzZTEyMw==      # echo -n "MonMotDePasse123" | base64

Utiliser un Secret dans un Pod

yaml 
spec:
  containers:
    - name: mon-app
      env:
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:            # secretKeyRef (pas configMapKeyRef)
              name: db-secret
              key: username
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
Chapitre 11

Volumes — Persistance des données

Par défaut, les données d'un Pod sont éphémères : si le Pod est supprimé, tout est perdu. Pour persister les données (base de données, fichiers uploadés...), on utilise des Volumes.

💾

PersistentVolume (PV)

Espace de stockage provisionné dans le cluster par l'admin. Comme un disque dur disponible.

📋

PersistentVolumeClaim (PVC)

Demande de stockage faite par un Pod. "J'ai besoin de 5 Go". K8s trouve le PV correspondant.

⚡

StorageClass

Définit comment les PV sont créés dynamiquement. Ex: SSD, HDD, NFS...

Exemple complet : PV + PVC + Pod

yaml — volumes.yaml 
# ─── 1. PersistentVolume (créé par l'admin) ───
apiVersion: v1
kind: PersistentVolume
metadata:
  name: mysql-pv
spec:
  capacity:
    storage: 5Gi             # 5 gigaoctets disponibles
  accessModes:
    - ReadWriteOnce          # Lecture/écriture par UN seul node à la fois
  persistentVolumeReclaimPolicy: Retain  # Garder les données après suppression du PVC
  hostPath:
    path: "/data/mysql"      # Dossier sur le node (pour tests, pas prod)
---
# ─── 2. PersistentVolumeClaim (demande du développeur) ───
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 3Gi           # Je demande 3 Go (K8s trouvera un PV >= 3Gi)
---
# ─── 3. Pod qui utilise le PVC ───
spec:
  containers:
    - name: mysql
      image: mysql:8.0
      volumeMounts:
        - name: mysql-storage
          mountPath: /var/lib/mysql   # Où monter dans le conteneur
  volumes:
    - name: mysql-storage
      persistentVolumeClaim:
        claimName: mysql-pvc         # Référence au PVC créé ci-dessus
AccessModes — Modes d'accès
ReadWriteOnce (RWO)Montable en lecture/écriture par UN seul node. Pour les bases de données.
ReadOnlyMany (ROX)Montable en lecture seule par plusieurs nodes simultanément.
ReadWriteMany (RWX)Montable en lecture/écriture par plusieurs nodes. Nécessite NFS ou stockage distribué.
RetainLes données restent après suppression du PVC. L'admin doit libérer manuellement.
DeleteLe volume physique est supprimé automatiquement quand le PVC est supprimé.
Chapitre 12

Ingress — Routage HTTP intelligent

Un Ingress est un reverse proxy géré par Kubernetes qui route le trafic HTTP/HTTPS vers les bons Services selon l'URL, le chemin ou le domaine. C'est l'équivalent d'un Nginx reverse proxy, mais déclaré en YAML.

🔄
Ingress Controller requis L'objet Ingress est une règle. Pour qu'elle fonctionne, tu dois avoir un Ingress Controller installé. Le plus populaire est nginx-ingress. Avec Minikube : minikube addons enable ingress.
bash — Activer Ingress avec Minikube 
# Activer l'addon ingress de Minikube
$ minikube addons enable ingress

# Vérifier que le controller est lancé
$ kubectl get pods -n ingress-nginx
yaml — ingress.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mon-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /   # Réécriture d'URL
spec:
  ingressClassName: nginx
  rules:
    - host: monapp.example.com        # Domaine
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service      # Service cible
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 3000
Projet 01

Application Web Nginx avec Scaling

Dans ce premier projet, tu vas déployer une application Nginx avec 3 réplicas, l'exposer via un Service NodePort, et tester le scaling automatique.

1

Créer le fichier de déploiement complet

yaml — projet1.yaml 
# ─────────────────────────────────────────────
# PROJET 1 : Nginx avec Scaling
# ─────────────────────────────────────────────

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-web
  labels:
    app: nginx-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-web
  template:
    metadata:
      labels:
        app: nginx-web
    spec:
      containers:
        - name: nginx
          image: nginx:1.25-alpine
          ports:
            - containerPort: 80
          resources:
            requests: { cpu: "50m", memory: "64Mi" }
            limits:   { cpu: "200m", memory: "128Mi" }
---
apiVersion: v1
kind: Service
metadata:
  name: nginx-web-service
spec:
  selector:
    app: nginx-web
  type: NodePort
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
2

Déployer et vérifier

bash 
$ kubectl apply -f projet1.yaml
$ kubectl get pods -w          # Suivre le démarrage
$ kubectl get all               # Voir tout ce qui a été créé
$ minikube service nginx-web-service --url
# Ouvrir l'URL dans un navigateur → Page Nginx
3

Tester le self-healing

bash 
# Supprimer un pod à la main
$ kubectl get pods
$ kubectl delete pod nginx-web-xxxxx-yyyyy

# Observer Kubernetes recréer le pod automatiquement !
$ kubectl get pods -w
# nginx-web-xxxxx-yyyyy   0/1   Terminating   ...
# nginx-web-zzzzz-wwwww   0/1   ContainerCreating   ...

Tester le scaling

$ kubectl scale deployment nginx-web --replicas=1

Projet 03

Architecture Microservices — Frontend + API + Redis

Ce projet déploie une architecture à 3 services : un frontend (Nginx), une API (Node.js) et un cache Redis. Il illustre la communication inter-services via les Services ClusterIP et l'exposition via Ingress.

yaml — microservices.yaml 
# ─── REDIS ───────────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
spec:
  replicas: 1
  selector:
    matchLabels: { app: redis }
  template:
    metadata:
      labels: { app: redis }
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports: [{ containerPort: 6379 }]
---
apiVersion: v1
kind: Service
metadata:
  name: redis-service
spec:
  selector: { app: redis }
  ports: [{ port: 6379, targetPort: 6379 }]
---
# ─── API BACKEND ─────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: node:20-alpine
          env:
            - name: REDIS_HOST
              value: "redis-service"    # DNS interne du Service Redis
            - name: PORT
              value: "3000"
          ports: [{ containerPort: 3000 }]
---
apiVersion: v1
kind: Service
metadata:
  name: api-service
spec:
  selector: { app: api }
  ports: [{ port: 3000, targetPort: 3000 }]
---
# ─── FRONTEND ────────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 2
  selector:
    matchLabels: { app: frontend }
  template:
    metadata:
      labels: { app: frontend }
    spec:
      containers:
        - name: frontend
          image: nginx:1.25-alpine
          ports: [{ containerPort: 80 }]
---
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
spec:
  selector: { app: frontend }
  ports: [{ port: 80, targetPort: 80 }]
---
# ─── INGRESS : routing /api → api-service, / → frontend ─
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: api-service
                port: { number: 3000 }
          - path: /(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: frontend-service
                port: { number: 80 }
💡
DNS interne Kubernetes Dans un cluster K8s, chaque Service est accessible par son nom depuis n'importe quel Pod du même namespace. redis-service, api-service sont des noms DNS valides à l'intérieur du cluster. C'est Kubernetes qui gère la résolution DNS automatiquement.

Cheat Sheet kubectl — Commandes essentielles

Cluster & Nodes

bash 
kubectl cluster-info                    # Infos du cluster
kubectl get nodes                        # Lister les nodes
kubectl get nodes -o wide               # Nodes + IPs
kubectl describe node <nom>             # Détails d'un node
kubectl top nodes                        # Utilisation CPU/RAM des nodes

Pods

bash 
kubectl get pods                         # Lister pods (namespace courant)
kubectl get pods -A                      # Tous les namespaces
kubectl get pods -o wide                # + IP et Node
kubectl describe pod <nom>              # Détails complets
kubectl logs <pod> -f                  # Logs en continu
kubectl exec -it <pod> -- bash         # Shell interactif
kubectl delete pod <nom>               # Supprimer
kubectl top pods                         # Utilisation ressources

Deployments

bash 
kubectl get deployments                  # Lister
kubectl scale deployment <nom> --replicas=N   # Scaler
kubectl set image deployment/<nom> <container>=<image:tag>  # MAJ image
kubectl rollout status deployment/<nom> # Statut MAJ
kubectl rollout undo deployment/<nom>   # Rollback
kubectl rollout history deployment/<nom> # Historique

Services

bash 
kubectl get services                     # Lister
kubectl describe service <nom>          # Détails
kubectl port-forward service/<nom> 8080:80  # Forward de port local
minikube service <nom> --url           # URL d'accès Minikube

Fichiers YAML

bash 
kubectl apply -f fichier.yaml           # Créer/mettre à jour
kubectl apply -f ./dossier/             # Tous les YAML du dossier
kubectl delete -f fichier.yaml          # Supprimer
kubectl apply --dry-run=client -f fich.yaml  # Test sans appliquer
kubectl get deployment <nom> -o yaml   # Exporter en YAML

Namespaces

bash 
kubectl get namespaces                   # Lister
kubectl create namespace <nom>          # Créer
kubectl get pods -n <namespace>        # Pods d'un namespace
kubectl config set-context --current --namespace=<ns>  # Changer namespace par défaut

Debugging

bash 
kubectl describe pod <nom>              # Voir les Events (erreurs)
kubectl logs <pod> --previous          # Logs du crash précédent
kubectl get events --sort-by=.lastTimestamp  # Événements triés
kubectl run debug --image=busybox --rm -it -- sh  # Pod de debug temporaire
kubectl exec -it <pod> -- nslookup mysql-service  # Test DNS interne

Astuce : Autocomplétion kubectl
Ajoute source <(kubectl completion bash) dans ton ~/.bashrc pour activer l'autocomplétion. Tu peux aussi créer l'alias alias k=kubectl et ajouter complete -o default -F __start_kubectl k pour que l'alias bénéficie aussi de la complétion.
